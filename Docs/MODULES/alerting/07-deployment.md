# `alerting` — 7. Deployment: threads, processes, files and the host

*Which thread runs what, what is shared, which file is written, what a second process does, and how
the headless host runs it?*

## Built: threads

`publish` runs on whichever thread raised the alert and never calls a channel
(`alerting/contracts/i_alert_publisher.py:11-14`). Each channel has its own daemon thread,
`alerting-lane-<channel>`, and one more, `alerting-housekeeping`, runs the flush every second
(`alerting/adapters/threaded_delivery_host.py:33-34`, `:56-72`); a lane that raises logs and carries
on at the next poll (`:94-103`). It is a thread and not an Engine `Scheduler` job because every
scheduled run puts two events on the bus (`threaded_delivery_host.py:3-7`).

The bot source's handlers run on the thread that wrote the bot (the bus is synchronous); they read
one bot and call `publish`, under one lock (`bot_alert_source.py:122-138`). The Discord call runs on
the lane `alerting-lane-discord`, so a slow Discord never holds a bot; one POST waits at most
`REQUEST_TIMEOUT_S` (`alerting/adapters/urllib_webhook_transport.py:31`).

## Built: the outbox file and its lifetime

The outbox is one connection shared behind a lock, one short transaction per call, WAL journal
(`sqlite_outbox.py:1-10`, `:92-124`); its file is `<data root>/state/alerts.sqlite3`
([`08-concepts.md`](08-concepts.md)). `boot()` starts the lanes and `shutdown()` stops them, then
closes the outbox; what is queued goes out at the next start (`alerting/module.py:111-133`).

## Built: a second process

A second process on the same data root is read-only (`EPIC-035H`): it opens no outbox, starts no lane,
subscribes no source, and its `IAlertPublisher` is the null one (`alerting/module.py:113-115`,
`alerting_bindings.py:132-139`). The `alert test` verb runs as a second process: it calls the channel
directly and writes nothing.

## Built: the headless host

On the headless host (`deploy/linux/sew-run.service`, generated by `scripts/render_service_files.py`)
the webhook arrives as a systemd credential, `$CREDENTIALS_DIRECTORY/alerting_discord_webhook`
(`deploy/linux/sew-run.service:48`, `scripts/render_service_files.py:91-93`), the route the mainnet
keys take (`src/support/secrets/adapters/systemd_credential_store.py:1-17`); systemd copies it at
start, so a rotated webhook needs a restart (`Docs/OPERATIONS/headless_runbook.md` §3).
