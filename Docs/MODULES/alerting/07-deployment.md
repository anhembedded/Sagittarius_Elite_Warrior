# `alerting` — 7. Deployment: threads, processes, files and the host

*Which thread runs what, what is shared, which file is written, what a second process does, and how
the headless host runs it?*

## Built: threads

`publish` runs on whichever thread raised the alert and never calls a channel
(`alerting/contracts/i_alert_publisher.py` → `IAlertPublisher`). Each channel has its own daemon
thread, `alerting-lane-<channel>`, and one more, `alerting-housekeeping`, runs the flush every
second (`alerting/adapters/threaded_delivery_host.py` → `LANE_THREAD_PREFIX`,
`HOUSEKEEPING_THREAD_NAME`, `ThreadedDeliveryHost.start`); a lane that raises logs and carries on at
the next poll (`ThreadedDeliveryHost._run_lane`). It is a thread and not an Engine `Scheduler` job
because every scheduled run puts two events on the bus (the docstring of
`threaded_delivery_host.py`).

The bot source's handlers run on the thread that wrote the bot (the bus is synchronous); they read
one bot and call `publish`, under one lock (`bot_alert_source.py` →
`BotAlertSource.on_bot_changed`). The Discord call runs on the lane `alerting-lane-discord`, so a
slow Discord never holds a bot; one POST waits at most `REQUEST_TIMEOUT_S`
(`alerting/adapters/urllib_webhook_transport.py` → `REQUEST_TIMEOUT_S`).

The fill source's handler runs on the bot's worker thread, like the others, and reads one bot through
the status query before it calls `publish` (`bot_fill_alert_source.py` →
`BotFillAlertSource.on_order_filled`); a grid that fills fast therefore pays one local read per fill on
its own worker, never a channel call. The fill bound runs on the publishing thread, inside the hub's
lock, and on the housekeeping thread for the skipped-messages line (`fill_backlog.py` → `FillBacklog`).

The Options page's actions (`EPIC-036D1`) run on the application's thread pool (`IThreadManager`), one at
a time, and their answers return to the UI thread through a queued signal
(`alerting/ui/options/alerts_action_relay.py`). They add no thread of their own and touch no lane: a
Send test posts from the pool thread, beside the lane, to the same webhook, which Discord rate-limits
per webhook, so it is a loud message the owner asked for and not a stream.

## Built: the outbox file and its lifetime

The outbox is one connection shared behind a lock, one short transaction per call, WAL journal
(`sqlite_outbox.py` → `SqliteOutbox._prepare`, `SqliteOutbox._transaction`); its file is
`<data root>/state/alerts.sqlite3` ([`08-concepts.md`](08-concepts.md)). `boot()` starts the lanes
and `shutdown()` stops them, then closes the outbox; what is queued goes out at the next start
(`alerting/module.py` → `AlertingModule.boot`, `AlertingModule.shutdown`).

## Built: a second process

A second process on the same data root is read-only (`EPIC-035H`): it opens no outbox, starts no
lane, subscribes no source, and its `IAlertPublisher` is the null one (`alerting/module.py` →
`AlertingModule.boot`; `alerting_bindings.py` → `bind_alerting`). The `alert test` verb runs as a
second process: it calls the channel directly and writes nothing.

## Built: the headless host

On the headless host (`deploy/linux/sew-run.service`, generated by
`scripts/render_service_files.py`) the webhook arrives as a systemd credential,
`$CREDENTIALS_DIRECTORY/alerting_discord_webhook` (its `LoadCredential=alerting_discord_webhook`
line; `scripts/render_service_files.py` → `alerting_credential_names`), the route the mainnet keys
take (the docstring of `src/support/secrets/adapters/systemd_credential_store.py`); systemd copies
it at start, so a rotated webhook needs a restart (`Docs/OPERATIONS/headless_runbook.md` §3).
