# `bots` — State machines

*Which states exist, which events move between them, and which moves are refused?*

Two machines, each declared as data in one file with its states and events (`code/quality.md` §3).
Any pair a table does not list is refused: `next_target` raises `InvalidBotTransitionError`,
`next_level_state` raises `InvalidLevelTransitionError`. The tables below are **generated** from the
code by `python3 scripts/render_bots_design_tables.py --write`, in the order the code declares them;
`tests/unit/scripts/test_render_bots_design_tables.py` fails when one differs from a fresh render. Do
not edit them by hand. Design: ADR 029 §3.1 and §3.2 ([`09-decisions.md`](09-decisions.md)).

## Built: the bot lifecycle

`bots/domain/bot_lifecycle_fsm_matrix.py` → `BotLifecycleState`, `BotLifecycleEvent`,
`BOT_LIFECYCLE_TRANSITIONS`: ten states and eighteen events. Two targets are not states, and the table
says so: `REMOVED` (`delete` from `DRAFT` or `STOPPED`; the store deletes the file) and `PRIOR`
(`reconcile_ok` from `RECOVERING` returns to the state the bot was in before the restart, which `Bot`
remembers as `recovering_from`; `BotLifecycleTarget`). `app_restart` is the restore rule written as a
transition ([`06-runtime.md`](06-runtime.md)). `resume` from `RECOVERING` is a self-loop (`BUG-204`):
the reconcile decides the next state, not the click.

`AWAITING_RECOVERY` (`EPIC-042`) is a halt a kind named transient: the ladder is off (not for the
exchange's pause, `EPIC-042F`: the cancels would be refused inside it, so the ladder rests until the
attempt cancels it), the base is kept, the exits are watched, and the bot waits for its cause to stay clear for the dwell, then resumes
through the person's Resume path (`condition_cleared`). Three events lead into and out of it
(`halt_transient`, `condition_cleared`, `budget_exhausted`); a person's `resume`, `stop`, `switch_off`,
`halt`, `fault` and a restart are declared too. `PAUSED` and `RECOVERING` have no `halt_transient` row:
the owner's Pause is never undone by a machine, and a restart's closed order session cannot take a
resume. A restart ends the wait in `HALTED`. The wait has no limit; after a quarter of an hour it raise
one event (`BotRecoveryStalledEvent`, built in `EPIC-042C`; its alert is `EPIC-042D`). The step by step is [`06-runtime.md`](06-runtime.md) and the reasons are
[the decision](../../../Tasks/epics/EPIC-042_halt_auto_recovery/DECISION_2026-10-17_halt_auto_recovery.md).

The sets the module asks of the table, rather than keeping lists of its own: `RUN_STARTING_STATES`
(a `start` here stamps a new run), `PRICE_STREAM_STATES`, `PRICE_STALENESS_HALTS`,
`RESUME_PROPOSES_STATES` (`HALTED` and `AWAITING_RECOVERY`: the states whose Resume re-plans) and
`RECOVERABLE_STATES`, in the same file.

## Built: a Grid level

`bots/domain/grid/grid_level_fsm_matrix.py` → `LevelState`, `LevelEvent`, `GRID_LEVEL_TRANSITIONS`:
five states and seven events. The live executor and the backtest share this table, so a fill means the
same thing in both. `ended` (cancelled, expired or refused without filling whole) returns a level to
`EMPTY` and the runtime counts the end; `adopt` is the reconcile finding an order carrying the bot's
tag at a level the saved state did not know; `settled` is a filled level returning to `EMPTY` once its
counter order is laid. `HOLDS_ORDER` is the set of states with an order on the exchange.

## Built: the protective stop's life cycle (Futures)

`bots/domain/grid/protective_stop_fsm_matrix.py` → `ProtectiveStopState`, `ProtectiveStopEvent`,
`PROTECTIVE_STOP_TRANSITIONS`: six states and eleven events, one machine **per protective order**
(a LONG or SHORT grid has one; a NEUTRAL grid has up to two). Its record is `bots/domain/grid/protective_stop.py` →
`ProtectiveStop`, kept in the Grid's runtime (`GridRuntime.protective_stops`) and written only when
there is one, so a Spot runtime and one saved before this existed read and write what they did
(`grid_runtime_codec.py` → `encode_runtime`, `decode_runtime`). Whatever a state names, the order is
sent only after its record is saved (`INTENDED`). `ABSENT` has no record and `ENDED` is dropped on
the next save. Any pair the table does not list is refused: `next_protective_stop_state` raises
`InvalidProtectiveStopTransitionError`. Why each row is there: `DECISION_2026-10-16` D5 to D8 and
[`06-runtime.md`](06-runtime.md).

The only way into `CANCELLING` is `exposure_closed` from `STANDING`: the bot's own exposure being
closed is the one reason a stop may go (`test_a_stop_is_cancelled_only_through_exposure_closed`).
A cancel that did not finish leaves `CANCELLING`; the next look ends the record when the order is gone, lets the very order go on standing (`exposure_reopened`) when the position is back on its side, and finishes the cancel otherwise, so no step takes a stop down before another stands (decision D7).
A `STANDING` stop that is on no open list while a position stands is placed again
(`missing_with_position`). With the account flat the order itself says how it ended, read by its
client id with no cache (`bots/application/services/orders/bot_account_reads.py` →
`BotAccountReads.order_status`): a trigger that traded is `triggered`; the exchange ending it
without a fill ("canceled by the system", check T2) is `expired`, and the record is dropped; an
answer that cannot be read counts as `triggered`, the side that ends flat. The Grid does not read the
order history for this: trading serves it up to 15 s old and does not attribute a conditional
order's fill to the bot (`DECISION_2026-10-16` D4, §8 A2).
