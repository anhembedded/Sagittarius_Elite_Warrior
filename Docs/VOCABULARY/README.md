# Vocabulary — the words this project uses, and what each one means

- **Purpose:** one place to look a term up while developing, and the **only** place a term is
  defined. Other documents (HLD, SDD, ADRs, task files) use the terms and link here; they do not
  redefine them. This is the same rule `CLAUDE.md` applies to rule files: a second copy drifts.
- **When to edit:** the commit that introduces a new term — in a document, an enum, a class name
  that other modules will see — adds its row here. A term that is not in this file is not yet
  part of the project's language.
- **How a row is written:** the term as it appears in code or documents; a one- or two-sentence
  definition a newcomer can act on; who owns it; where it is defined in code or design; and, where
  a confusion has actually happened, what it must not be mistaken for.
- **Language:** English (`ONBOARDING.md` §10). Where the user coined a term in Vietnamese, the
  original is quoted once.

## 1. Architecture terms

| Term | Definition | Owner | Defined in | Not to be confused with |
| :--- | :--- | :--- | :--- | :--- |
| **Bounded context** | A part of the system with its own language: at least one word means something different here than elsewhere, to the point that the code keeps two types. Cut by the six criteria C1–C6. | — | HLD §1 | a *screen* (a place to hang widgets) or a *layer* (a technical kind) |
| **Module** (`modules/<id>/`) | The code unit that owns one bounded context: `contracts/`, `domain/`, `application/`, `adapters/`, `ui/`, `module.py`. | **`contributor_id`** | The field on a contribution that says who made it: a `module_id`, or `"shell"` for the shell's own surfaces. Support packages never contribute — the module that wants a support widget contributes it. | — | SDD descriptor | a `module_id` in general |

| **`shell/`** | Robert Martin's "Main" component: the only code that knows every module. Holds the explicit module list, the surfaces, the CLI assembly. | shell | HLD §2.1 | `main.py` alone |
| **Contract** (`contracts/`) | The only importable surface of a module: ports, DTOs, events. Everything else in the module is internal. | each module | HLD §3.3 | the module's `application/` use cases (internal) |

| **DTO** | A flat, frozen dataclass carried across a module boundary. Never an entity. | owning module | HLD §3.3 | an entity or aggregate |

| **Shared Kernel** | In this repository, **exactly two** Engine symbols — `IDomainEvent`, `BaseEvent` — and a test locks that. Do not use the phrase for anything else. | Engine | `architecture-rule.md` | the Published Language |
| **Customer / Supplier** | Two contexts where the downstream (customer) depends on the upstream's contracts and the upstream does not know the customer exists. `strategy` is a customer of `trading`. | — | HLD §2.3 | — |
| **Open Host Service** | A context that publishes a general-purpose API for many consumers, in the Published Language. `market_data` is one. | — | HLD §2.3 | — |
| **Anticorruption Layer (ACL)** | A translation layer that keeps another model from leaking in. This repository has **one**: `binance_gateway` around the Binance SDK. The word is for a foreign model that genuinely leaks, not for any boundary. | the downstream side | HLD §2.3 | a **port**, which is the boundary itself rather than a translation across it |
| **Seam** | The extension point built on the first case: a port, a base class, a place enum, a list a new case is added to. Mandatory (Open/Closed). | — | `architecture-rule.md` §7.2.1 | a *variant* (below) |
| **Variant** | A second implementation or a feature nobody has asked for. Built only when a real case arrives (YAGNI). | — | `architecture-rule.md` §7.2.1 | a seam |
| **Verified fake** | The one in-memory implementation of a public port that ships with the port under `contracts/testing/`, and passes the same **contract suite** the real implementation passes. Consumers test against it; nobody `Mock`s a foreign port. | the provider module | HLD §10.3 | a `Mock(spec=IPort)`; a stub a consumer wrote for itself |
| **Contract suite** | The test module for one port, parametrised over `[fake, real]`, written by the provider and extended by consumers with the guarantees they rely on. | the provider module | HLD §10.3 | a unit test of the implementation |
| **Guard** | An architecture fitness function: a test, written with `ast`, that fails when a structural rule is broken. Three exist for the module split; their allowlist may only shrink. | `tests/unit/architecture` | HLD §6.1 | a unit test of behaviour |
| **Allowlist ratchet** | The list of known violations recorded when a guard is introduced; the guard fails on any new violation and on any listed violation that no longer exists, so the list can only shrink. | — | HLD §6.1 | a permanent exemption list |
| **Empty by design** (`EMPTY_BY_DESIGN`) | One named `(guard, root, pattern)` triple whose scan finding **nothing** is the rule being satisfied rather than the guard having lost its subject. Introduced `EPIC-025` PR 4.3l for the `.qml` ban: with ADR D21 met there is no `.qml` under `src/` to find, while every *other* empty scan still fails. It is not the exemption the row above warns against — it exempts one scan from the emptiness check only, never from its own rule, and a second test asserts the triple is a scan that is really registered, so the exemption cannot outlive what it exempts. | `tests/unit/architecture/scanned_roots_registry.py` | `EPIC-025E` §4.12 | an allowlist ratchet, which records violations; this records an expected absence |
| **Symbol lease** | `trading`'s record that one `owner_id` currently holds a symbol: it refuses a second claimer and refuses **orders** from any other owner (`ExecuteOrderSafetyGate.SYMBOL_LEASED`). `strategy` claims on arm and releases on disarm; a manual order carries `owner_id="manual"`, `OrderRequest`'s default. The holder is not exposed on the public port. **Shipped `EPIC-025` PR 2.1f**, with three things measured rather than as first written: `claim_symbol` answers a `bool` instead of raising a `SymbolAlreadyLeased` (a refusal is a value, like every other refusal in this module); it is **one symbol per owner**, so re-arming onto another symbol gives the first back rather than stranding it; and it is claimed by *arming*, never by enabling trading — a lease tied to the switch would be released by an Emergency Stop, exactly when an open position most needs its strategy to still own the symbol. In-process, like the rest of the session's state. | `trading` | HLD §3.4, SDD-04 | the two mechanisms below, which have different semantics |
| **Stream owner** (`IMarketStream.owner_id`) | A **namespace**: starting a stream replaces that owner's previous subscriptions and never touches another owner's; two owners may stream the same symbol; one owner may hold several streams. Today's `StartLiveStreamCommand.owner`. | `market_data` | SDD-06b | an exclusive lease |
| **Action ownership** (`ActionOwnershipTracker`) | A **fencing token** that *supersedes*: a second `begin_action` invalidates the first (`action_superseded`, `ActionOutcome.INVALIDATED`). Correct for UI actions; the **opposite** of a lease — never copy its shape for a resource that must refuse. | the card's Presenter | `ui/common/action_ownership_tracker.py` | the symbol lease |
| **Owner id** | The string naming who holds one of the three above. Stable, human-readable, usually a `module_id` or `"manual"`. Which semantics apply depends on the mechanism, not on the string. | the mechanism's module | HLD §3.4, SDD-06 | — |

## 2. Workbench (UI places)

The workbench model: the shell owns a small, fixed vocabulary of **places**; a module **chooses**
places, it never invents layout (HLD §4.6). Adding a place is an HLD change, not a module change.
This table is the canonical definition of the `Place` enum (SDD-01).

| Term | Definition | Geometry decided by | Exists today |
| :--- | :--- | :--- | :--- |
| **Surface** (= a **mode**) | A screen with **no business logic**: a nested `QMainWindow` (HLD §11) that asks the registry who contributes into each of its places and builds the widgets through the factories it is given; its dock layout is a **perspective** saved per user. Shell-owned surfaces: `trading`, `developer` (`welcome`, `dev_board` and `settings` were deleted by `EPIC-033C`, `033P` and `033E`). | — | 🔵 (the desks are still ordinary screens) |
| **Module-owned screen** | A screen a module owns because it hosts a workflow the user performs for its own sake (§4.6.2 question 1): `backtest`, `data_management`. It is still a mode (`QMainWindow`), and declares which places accept foreign contributions (`accepts=(RAIL, MODAL)`). | the owning module | ✅ (`ScreenRegistry`) |
| **Place** | A named slot a module may contribute a widget to. The full list is the rows below. | — | — |
| `SCREEN` | A navigation entry that opens a full page — a **mode** in the mode selector. | the shell (`QStackedWidget` of nested `QMainWindow`s) | ✅ `ScreenRegistry`, `NavLocation` |
| `HEADER` | Actions that apply to the whole page (enable, reload, emergency stop): a `QToolBar` of `QAction`s. | the toolbar | ✅ (as `PageShell.set_header` today; `QToolBar` after HLD §11) |
| `CONTEXT_BAR` | The current context the page works in (symbol, timeframe, connection): a second toolbar. | the toolbar | ✅ |
| `WORKSPACE` | The one large thing the page is about (a chart, a table, a form): the mode's central widget. Only `market_data` and `charting` contribute here. | the central widget — takes the remaining space | ✅ |
| `NAVIGATOR` | The left dock area: where the person picks or sets up what the mode's centre shows — the Bots list, Backtest's Run setup (HLD §11.2.1). A panel like any `RAIL` one, in the other dock area. | the left dock area; the user's saved perspective | ✅ (`EPIC-033L`) |
| `RAIL` | The dock area of **panels** (`QDockWidget`s), initially ordered by `order`, then as the user arranged them. Where most module widgets go. | the dock area; the user's saved perspective | ✅ (a fixed column today; docks after HLD §11) |
| `CONSOLE` | Log and diagnostics for that page: a bottom dock panel. | the bottom dock area | ✅ |
| `MODAL` | A `QDialog` the page opens and closes: names its action, has Cancel, validates before OK. Never a permanent resident. | `QDialog` — sized by content, centred | ✅ (overlay today; `QDialog` after HLD §11) |
| `STATUS_TILE` | A one-glance indicator (websocket pill, price ticker, run progress) in the `QStatusBar`. | the status bar | 🔵 |
| `DEV_PROBE` | A probe panel docked right in the Developer mode, only when `dev.mode` was true at boot (the Dev Board's dock area until `EPIC-033P`). | the Developer mode's right dock area | ✅ |
| **Panel** | A `QDockWidget` in a dock area whose content is one module-owned widget (a table on a model, a form, a summary); title and close button and nothing else of its own; no reference to sibling panels. Replaces the **card** (retired 2026-09-13, ADR D22 — *"các card cũ cũng rất là tệ"*). | the owning module | 🔵 |
| **Dialog** | A `QDialog` for an action that needs input and confirmation (place an order — F9 —, arm a strategy, pick a range, edit settings): names what OK does, has Cancel, validates before OK enables, reports in the status bar. | the owning module | 🔵 |
| **Mode** / **Perspective** | A mode is a top-level screen selected on the mode bar, with Ctrl+1… or in View (Qt Creator's term); the window opens on the last one used; its perspective is the user's dock layout for it, saved with `QMainWindow.saveState()` per mode and restored on return; "Reset layout" restores the contributed order. | shell | 🔵 |
| **The six modes** (`EPIC-033O`, approved) | Market (watch the live market), Trade (trade one venue by hand — Futures or Spot chosen by the venue selector — and see the account), Bots (create, judge, run and watch bots; a strategy armed on a venue is listed there until it becomes a signal-bot kind, `EPIC-029L`), Backtest, Data (keep history complete), Developer (only under `dev.mode`). Designed from the use cases in HLD §11.2; they replace Welcome, Dev Board, Watchlist, the two desks and the Settings route once built. | shell | 🔵 |
| **Options dialog** (Tools → Options) | The one dialog for configuration: sections on the left, pages on the right, OK / Cancel / Apply; each module contributes one page through `contribute_options_page` (an `OptionsPageContribution`, not a place), and the dialog drives it through apply, revert and dirty. Windows names it Options; it replaced the Settings route (`EPIC-033E`). | shell | 🔵 |
| **Command** (`QAction`) | One thing the user can do, as one `QAction` contributed by its module and shared by its menu entry, toolbar button and shortcut; the menu bar is the catalogue of every command (`ui-presentation-rule.md` §6). | the contributing module | 🔵 |
| **Native theme** | The app applies no stylesheet, palette, token or third-party theme; widgets look like the OS's. Colour appears only where it carries meaning (profit/loss, connection). A designed theme is deferred (ADR D21). | shell | 🔵 |
| **Contribution** | A declaration "put my widget in `<surface>.<place>`", made once in `module.contribute()` (or by the shell) as a frozen `ContributionDescriptor` (`contributor_id`, `surface_id`, `place`, `order`, `size_hint`, `factory`, optional `title`). Validated when contributed; the factory is lazy and runs only when the surface is built. | the contributor | HLD §4.3, SDD-01 | a widget instance |
| **Contribution kind** | What a contribution *is* for the shell: `screen`, `surface_widget`, `options_page`, `status_tile`, `dev_probe`. Kinds are application policy, never Engine mechanism. | shell | HLD §4.3 | a place (where it goes) |
| **CLI command declaration** | What `module.declare_cli()` hands the shell: a frozen `CliCommandDescriptor` (`name`, `handler`, `contributor_id`) collected by `shell/cli_registry.py`. A **separate** registry from `ContributionRegistry`, and HLD §4.3's sixth contribution kind `cli_command` is therefore **not** how this shipped (`EPIC-025` PR 1.3c-5): a command has no surface, no place, no order and no widget factory, so putting it through `ContributionDescriptor` would have meant inventing a surface for it. What the two registries share is the inversion and the file shape, not the descriptor. | the declaring module | SDD §2 | a `ContributionDescriptor`; the argument spec, which stays in `cli_commands.json` |
| **Size hint** (`SizeHint`) | `COMPACT` · `REGULAR` · `TALL` — the only thing a module may say about geometry; the place resolves it. | — | HLD §4.6.3 rule 1 | a width or a height |
| **Order** | An integer sort key within one `(surface, place)`; ties are broken by `(contributor_id, factory.__qualname__)`, so two modules choosing the same number render deterministically instead of refusing to boot. | the contributor | SDD rule 2 | a uniqueness key |
| **Panel** (as a runtime object) | What a factory returns: a View and its Presenter built together; the Presenter owns its Coordinators and its action ownership. Two surfaces get two panels from one factory; they share the module's feed, never an object. | the contributing module | SDD "Ownership" | a shared singleton |
| **Mirror rule** (retired, `EPIC-033P`) | Was: a `trading.rail` panel is also a `dev_board.rail` panel unless the module says otherwise. Gone with the Dev Board; what remains is HLD §4.6.3 rule 2, one widget in many places, never one copy per screen. | — | HLD §4.6.3 rule 2 | copying a widget |
| **Probe** (`dev_probe`) | A widget a module contributes to the Developer mode (the Dev Board until `EPIC-033P`) to answer *what is actually true inside me right now* — either by trying an exchange API it does not yet understand, through the module's real adapter and showing raw request and response, or by showing the module's own state, which is what the first one built does (`trading`'s session probe, PR 1.4c-4: the live-submission flag, the session's order count and the symbols it believes open). Deleted or kept deliberately once the use case has tests. | the contributing module | HLD §4.4 | a feature |
| **Developer mode** (`dev.mode`) | A configuration key read **once at boot** by one shared `ConfigManager`; when true, the Developer mode, its `developer` surface and every `DEV_PROBE` exist, and the backtest chart shows its FPS overlay. Toggled in Tools → Options → Developer (`EPIC-033C`; the Welcome screen until then), written through `IConfigWriter` to `user_config.json`, applied by a restart that keeps the script path and strips `--dev`. `--dev` wins for the current run. | shell | ADR D14, SDD-05 | a runtime switch |
| **UI map** | The generated table surface × place × module that a guard renders; fails on a widget contributed nowhere or a place that does not exist. | guard | HLD §4.6.3 rule 4 | — |

## 3. Domain terms, per bounded context

Words that mean different things in different contexts are listed **once per context** — that
difference is the reason the contexts exist (HLD §1.2).

### `market_data`

| Term | Definition | Defined in |
| :--- | :--- | :--- |
| **Candle** / `MarketData` | One OHLCV bar for a symbol and a `TimeFrame`. The type is in the Published Language; renaming it `Candle` is a recorded candidate. | `core/vo` |
| **Symbol** | A raw string such as `BTCUSDT`. No value object exists yet (recorded candidate). | — |
| **Shard** | One SQLite file holding the klines of one symbol/timeframe range. | `adapters/persistence` |
| **Gap** / **Coverage** | A missing range inside stored klines; the fraction of a requested range that is stored. `IRangeCoverage` reports it. | `contracts/` |
| **Sync** | Fetching klines from the exchange into the shards for one symbol/timeframe/range; progress is a `SingleSyncProgressEvent`. | `contracts/IMarketDataSync` |
| **Market stream** | The live kline websocket for one symbol/timeframe on one market, started and stopped by `owner_id`. Since `EPIC-028C` each market (Spot, USD-M Futures) has its own connection, and every `MarketTickEvent` names the market it came from; a consumer (`MarketTickFeed`, `MarketTickEventHandler`) keeps only its own market's ticks. | `contracts/IMarketStream` |
| **`StreamOutcome`** | What `IMarketStream.start`/`stop` answer: `success` (the owner's subscription set is now what was asked for) plus a `message` fit to show a user. `success=False` from `stop` means there was nothing to release — an ordinary state, not an error. | `contracts/IMarketStream` |
| **Market data venue** (`MarketDataVenue`) | Which endpoint set market data comes from (mainnet public, testnet). | `core/vo` |
| **Symbol metadata** (`SymbolMarketMetadata`) | One symbol's exchange order rules as filters: price min/max/tick, quantity min/max/step, minimum notional, plus `fetched_at` so staleness is a fact rather than a guess. Distinct from `trading`'s flat `SymbolOrderMetadata`, which carries the rounding scalars an order path needs and no bounds. | `contracts/symbol_market_metadata.py` |
| **Symbol metadata provider** (`ISymbolMetadataProvider`) vs **cache** (`ISymbolMarketMetadataCache`) | Two halves on purpose: the **cache** stores and is read on the Qt main thread; the **provider** fetches the catalog and may block, so only a worker calls it. A cache read that could make a network call is `BUG-045`/`BUG-107`'s defect, and a store nobody fills is `BUG-127`'s. | `contracts/i_symbol_metadata_provider.py` |
| **Market rule verification** (`MetadataVerificationStatus`) | What the Backtest screen says about *this* capital on *this* symbol against the exchange's filters: `VERIFIED` (checked, and it says whether it passes), `UNVERIFIED_MISSING` (no metadata for the pair **yet**), `UNVERIFIED_STALE` (metadata too old to trust). The two unverified states are honest transients since `BUG-127`; before it, `UNVERIFIED_MISSING` was permanent. | `contracts/symbol_market_metadata.py` |

### `trading`

| Term | Definition | Defined in |
| :--- | :--- | :--- |
| **Position** (`LivePosition`) | A position **as the exchange reports it**, read-only; the app never computes any of its fields. Leaves the module only as `PositionSnapshot`. | `domain/trading/live_position.py` |
| **Holding** (`SpotHolding`) | A Spot balance for one asset — asset, free, locked, dust threshold — never a `LivePosition` with an invented mark price, leverage or liquidation price (Spot has none of those). `ExchangeConnectionStatus.holdings` carries them; a Futures venue answers `None`. `EPIC-027H`. | `contracts/spot_holding.py` |
| **Order** | A real order sent to the exchange through `IOrderSubmission` — the only path. | `contracts/IOrderSubmission` |
| **Order intent** | What a caller *wants* (side, quantity, type, price, `owner_id`) before preview and rounding. | `contracts/dto` |
| **Trading session** | The app-level state "trading is enabled", with its limits, counters and symbol leases; snapshot as `TradingSessionSnapshot`. | `contracts/ITradingSession` |
| **Client order tag** (`client_order_tag`) | Six characters of `[a-z0-9]` an owner puts on its orders (a bot's id), carried in the client order id as `SEW-{tag6}-{hex10}`; untagged ids stay `SEW-{hex12}`. `tag_of` reads it back off any id, so a fill, an end or a history row names its owner. A malformed tag is refused when the request is built, before any network call. `EPIC-029` ADR D5. | `contracts/client_order_id.py` |
| **Owner budget** (`OwnerBudget`, `OwnerBudgetCaps`) | What one tagged owner may have on a Spot venue at once and how fast it may send: open orders, exposure (open BUY quote plus the inventory at cost), the spacing between its orders and an order rate. For that owner's orders it **replaces** the three signal limits (orders per session, positions per symbol, order interval); the per-order notional cap, the lease, the switch and the minimum notional still apply. A tagged order with no budget is refused (`OWNER_BUDGET_MISSING`), so a bot never falls back to the signal limits. Registered per session (`ITradingSession.register_owner_budget`), cleared by every enable, disable and Emergency Stop; the caps on any budget are configuration (`trading.bot_limits.*`, ADR O1). `EPIC-029` ADR D6. | `contracts/owner_budget.py`, `owner_budget_registration.py` |
| **Owner book** (`OwnerBook`, `OwnerBooks`) | Trading's own record of a budgeted owner on one venue: its open orders with what each commits, its **owner inventory**, and its recent sends. Seeded from the venue at registration and kept by the venue's emission path, which applies every fill and end to it **before** the event is published, so a subscriber always sees a book that holds what it was told. Not the bot's record of itself. `EPIC-029` ADR D6. | `application/owner_book.py`, `owner_books.py` |
| **Owner inventory** (`OwnerInventory`, `OwnerInventoryDeriver`) | The base an owner bought and still holds, net of fees charged in the base asset, with its cost (average cost). **Derived from exchange evidence**, never supplied by the owner: the fills of its tagged orders since its run started, joined to the order history by the exchange order id. A checkpoint lets a run longer than the venue's 30-day history be derived from it onward. Emergency Stop sells each owner's share under its tag, so a fresh derivation stays exact. `EPIC-029` ADR D6. | `contracts/owner_budget.py`, `application/owner_inventory_deriver.py` |
| **Trading switch event** (`TradingSwitchChangedEvent`) | Published once each time a venue's trading switch really changes: `ENABLED` after an enable commits, `DISABLED` when a disable turns trading off, `EMERGENCY_STOP` at the stop's step 1, before its cancels and sells. So a bot pauses the moment trading goes off and knows why. `EPIC-029` ADR D7. | `contracts/events/trading_switch_changed_event.py` |
| **Trading venue** (`TradingVenue`) | Where orders go: disabled, testnet. Live is restricted by a guard. | `core/vo` |
| **Venue context** (`VenueContext`, `IVenueContexts`) | Every live-trading port one enabled venue answers (credentials, metadata cache and provider, client factory, account reader, user data stream) as one immutable bundle. `IVenueContexts.get(venue)` is the only way to reach one: since `EPIC-028B` none of these ports is bound on its own. `DISABLED` is served only while nothing is enabled. `VenueAssembly` (composition) builds and caches one venue's parts under a lock; nothing else constructs them (guarded). | `trading/contracts`, `trading/composition` |
| **Primary venue** | The first enabled venue, or `DISABLED` when none is: the venue `resolve_trading_venue`, the single published ports (`IOrderSubmission`, `ITradingSession`, …), the Options dialog's Trading page, and `trade-once` address (the Dev Board did too, until `EPIC-033P` deleted it). Each **desk** addresses its own venue (`EPIC-028K`/`028L`). | `trading/composition` |
| **Venue trading ports** (`VenueTradingPorts`, `IVenueTradingPorts`) | What another module consumes for one venue: its order submission, trading session, account snapshot and equity curve, each stamping that venue on every command it sends. The single published ports are the primary venue's bundle. `EPIC-028B`. | `contracts/i_venue_trading_ports.py` |

| **Report** (`BacktestReport`, `BacktestReportProvenance`, `BacktestReportConfig`, `BacktestReportLoadResult`) | The persisted, portable snapshot of one run (`BOT-115A`) — what was asked for (`config`), what came back (`result`, a plain `BacktestResult`), and where it came from (`provenance`: engine/app version, strategy key, execution mode, data window). Deliberately independent of `BacktestRunConfig`/`BacktestExecutionMode` (`ui/logic/backtest_fsm_matrix.py`) rather than reusing them — those are UI-layer types, and importing one into `contracts/` would point a dependency outward (`architecture-rule.md` §3). Loading one is never all-or-nothing: `BacktestReportLoadResult.strategy_key_unknown`/`.metrics_mismatch` let a file with an unrecognized strategy or tampered numbers still display as dead data, distinct from `.error` (unreadable at all). | `modules/backtesting/contracts/backtest_report.py`, `backtest_report_loader.py` |

### `bots`

| Term | Definition | Defined in |
| :--- | :--- | :--- |
| **Bot** (`Bot`) | A persisted aggregate the user creates: a `BotId`, a definition (name, kind, venue, symbol and the kind's parameters as strings) and a lifecycle state. Immutable; every change returns a new value through the lifecycle table. Not a strategy: a strategy turns candles into signals, a bot owns a running plan and the orders behind it (`EPIC-029`, ADR D2). | `modules/bots/domain/bot.py` |
| **Bot id** (`BotId`) | Six characters of `[a-z0-9]`, random. The bot's file name, its lease owner and the `{tag6}` of its client order ids `SEW-{tag6}-{hex10}` (ADR D5). | `modules/bots/domain/bot_id.py` |
| **Bot kind** (`IBotKind`) | The seam a kind of bot plugs into: its `kind_id`, a verdict per check on the user's parameters, its chart overlay and its executor factory. Only Grid is built; signal, DCA, Futures Grid and trailing Grid are the recorded extension cases. | `modules/bots/contracts/i_bot_kind.py` |
| **Bot chart** (`BotChart`) | A bot's own candle chart with its overlay drawn over it. One class for the three surfaces: the planner preview (stored history, no network), the backtest result (the candles it ran over) and the running bot (streams under its own owner `bot.<id>`, ticks through `BotTickFeed`). Its loading and live candles are the desks' (`LiveCandleChart`). `EPIC-029G`, ADR D15. | `modules/bots/ui/chart/bot_chart.py` |
| **Bot overlay** (`BotOverlay`) | What a bot kind asks its chart to draw, as data: horizontal lines with a role (level, stop loss, take profit, range edge, average cost), bands (ATR zones, Bollinger) and fills. One drawer (`BotOverlayDrawer`) draws it for every surface, so a backtest and a live bot draw the same chart (ADR D16). A Grid's is computed by `grid_overlay` from its plan and, once it runs, its `GridActivity`. | `modules/bots/domain/bot_overlay.py`, `grid/grid_overlay.py` |
| **Bot lifecycle** | The nine states and fourteen events of ADR §3.1, declared only in `bot_lifecycle_fsm_matrix.py`; an undeclared pair raises `InvalidBotTransitionError`. `app_restart` is the restart rule (ADR D12) as a transition. | `modules/bots/domain/bot_lifecycle_fsm_matrix.py` |
| **Bot store** (`IBotStore`) | One JSON file per bot under `state/bots/`, schema-versioned and written atomically. Never an input to a safety check: inventory comes from exchange evidence (ADR D4, D6). A file it cannot read is refused by name, never dropped. | `modules/bots/contracts/i_bot_store.py` |
| **Verdict** (`Verdict`) | One check's answer about the user's parameters: OK, WARNING or REFUSED, a stable code, a reason and the numbers behind it. Only REFUSED blocks a start, and only for a certain loss or a certain rejection. The parameters stay the user's; a verdict never changes them. | `modules/bots/domain/verdict.py` |
| **Grid backtest** (`simulate_grid`, `GridBacktestResult`) | A Grid's parameters replayed on stored candles through the live executor's own reactions, so a replay and a running bot agree on what a fill does; it stops at the last candle, an exit or a halt, and a cancelled one is a value (`GridBacktestCancelled`), never a partial result. Not a backtesting-context **run**: that replays a strategy's signals on a paper exchange. `EPIC-029D`, ADR D14, D18. | `modules/bots/domain/grid/grid_simulator.py` |
| **Fill rule** (`FILL_RULE`) | The one stated rule for when a resting Grid order counts as filled in a replay: a tick through its level, never on touch; the order inside a candle from 1-second klines that span its low and high; one fill per level per kline; counter orders rest from the next one. Every result names it. ADR D14. | `modules/bots/domain/grid/grid_fill_rule.py` |
| **Coarse candle** (`coarse_periods`) | A candle a grid order could fill in, replayed without 1-second klines that span its low and high: one step, down then up (the adverse side first), listed in the result so it is never silent. | `modules/bots/domain/grid/grid_fill_rule.py` |
| **Buy-and-hold** (`BuyAndHold`) | The benchmark a Grid backtest is compared with: the whole capital bought at the first candle's open at the taker fee, valued at each candle's close on the same timestamps as the grid's equity. ADR D18. | `modules/bots/domain/grid/buy_and_hold.py` |

## 4. Process terms

| Term | Definition | Defined in |
| :--- | :--- | :--- |
| **North star** | The HLD: the one document that answers which modules, which boundaries, which criteria, which APIs. When code and HLD disagree, one is wrong and the discovering PR fixes it. The user's word: *"kim chỉ nam"*. | HLD README |
| **Walking Skeleton** | The thinnest end-to-end slice built first to prove every layer connects: Phase 0 = the mechanism plus `market_data`. | HLD §6.3 |
| **Strangler Fig** | Growing the new structure around the old and retiring the old piece by piece, so the app runs at every step. | HLD §6.3 |
| **Harvest** / **Lift** | Building a mechanism inside the app with an Engine-shaped layout and no app imports, then moving it into the Engine once the lift criterion holds (zero app imports; two surfaces or modules use it; API stable one phase). | HLD §8 |
| **Engine track** (E0–E3) | The Engine's schedule of lifts, aligned with the app phases. | HLD §8.4 |
| **Phase** (0–5) | One pull request that leaves the app running: mechanism + `market_data`; `trading` + surfaces; `strategy`; `backtesting`; `support/*`; Engine navigation. | `EPIC-025` |
| **Apply before you invent** | Survey existing solutions first; prefer applying; when not adopted, still apply the shape. | `ONBOARDING.md` §7 |
| **Board line** (`**Board:**`) | The one line a task or bug file carries for the board: the outcome while open, the decision or root cause once closed. `scripts/render_board.py` builds the task and bug board from these lines, so no pull request edits a shared list (`BOT-163`). Not the `Status` field, which says the state; the board line says what the reader needs from it. | `ONBOARDING.md` §6, `scripts/render_board.py` |
| **Documentation-only change** | A change whose every path is in the set `.claude/ONBOARDING.md` §7 defines (the one definition); such a change may be committed, pushed and merged without asking. | `ONBOARDING.md` §7 |
| **Use-case spec** (`SPEC-xxx`) | One file describing one thing a person does with the app: trigger, preconditions, flow, what must be true afterwards, the named failures, what it does **not** promise, the ports it crosses, and the evidence that proves each part. Ids are permanent. It is what a phase or a pull request is accepted against — not prose about intent. | `Docs/SPEC/README.md` |
| **User story** (`US-xx`) vs **spec** (`SPEC-xxx`) | A `US` is something somebody **wants**, recorded as a proposal with acceptance criteria. A `SPEC` is what the app **does**, or is specified to do, with the flow spelled out and the evidence named. A `US` becomes a `SPEC` when it is specified; neither file copies the other, and the only link is the SPEC's *Origin* line. | `Tasks/UserStory_Propose.md` · `Docs/SPEC/README.md` |
| **Stage gate** | The written, checkable criterion that ends one stage of `EPIC-026` and lets the next start; recorded as passed in the epic README §4 with its evidence, never inferred from code being merged. The user's word: *"lô trình"* (roadmap) was answered with gates rather than dates. | `EPIC-026` README §4 |
| **Soak** | Running the app unattended on Testnet for a fixed period (14 days in `EPIC-026O`) with every operational control on, then reconciling the trade journal against the exchange; a code change to any control restarts the count. | `EPIC-026O` |
| **Proven by** | A use-case spec's evidence table: for each promise, the test path that holds it (the path must exist — a guard checks) or the words **the user runs it** with what a person must see. Naming the human steps is how they stop being forgotten. | `Docs/SPEC/SPEC-000_template.md` §8 |
