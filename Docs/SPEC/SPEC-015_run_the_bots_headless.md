# SPEC-015 — Run the bots headless: `main.py run`

- **Status:** 🟡 partly built — the host, its signals, both stop policies, the lock refusal, the pre-flight gate, the health line and the resume of RECOVERING bots are built and proven; `--start-planned` reads the plan `bot apply` recorded (`EPIC-038I`); Ctrl-Break on Windows is proven by the adapter's own test, not by a Windows run; and the host is **not supported for unattended money** until `EPIC-036B`, `036C` and `036E` have merged.
- **Actor:** operator (a person who runs the bots on a server with no window, or the service manager that runs them for that person)
- **Origin:** `EPIC-038D`, from the owner's instruction of 2026-10-09 (run the bots from the command line on a VPS, Linux or Windows); decisions O1, O2, O4 (answered A on 2026-10-17: the owner's "stop and pause" on a running host, §3a), O8 and D9 of `DECISION_2026-10-09_headless_operation.md`.
- **Surfaces:** `main.py run` and its flags; `main.py status`, `bot list` and `bot order <id>` (the orders a bot's file records, stored not live; `BOT-187`) from a second process; `bot stop`, `bot pause`, `bot resume`, `bot start`, `bot edit`, `bot add` and `bot delete` from a second process through the command directory `state/control/` (`EPIC-038J`, `EPIC-038K`, `EPIC-038L`, `EPIC-045`); the host's log on standard output; `state/health.json`. No window.

## 1. Trigger

*"I want the app to keep my bots running on this machine until I tell it to stop, to stop cleanly when I do, and to tell me how it is."*

## 2. Preconditions

1. The checkout is installed with the headless requirements (`requirements-headless.txt`), the Engine pin installed (`scripts/engine_pin.py install`). No Qt is needed.
2. No other copy of the app holds the data root. A second copy would be read-only and trade nothing, so `run` refuses to be one (§5).
3. Each venue the bots trade on has a key the exchange accepts, read from the environment, a secrets file or the keyring (`credentials-present`). A key that can withdraw is refused (`no-withdraw-permission`). A first run with no key at all is refused with 5, by design; `--skip-preflight` runs it anyway.
4. The machine's clock is within the exchange's tolerance, the disk has room, the data root is writable (`main.py preflight` says each).

## 3. Main flow

1. The operator (or the service manager) starts `main.py run [flags]`.
2. The entry point takes the data root's instance lock first. If another copy holds it, it says why on standard error, exits `3` and builds nothing.
3. It builds the application **without booting it**, and checks what can be checked without the exchange: the flags (`2`), `--resume-recovering` or `--resume-halted` against the alert channels (`5`), `--start-planned` with no applied plan, or one it cannot read (`5`: only the operator can fix it, a restart cannot), and a mainnet `--resume-recovering` the operator did not confirm with `--confirm-venue` (`2`). A mainnet `--start-planned` bot the operator did not confirm is not refused here: step 6 skips it (`EPIC-045F`).
4. It runs the pre-flight, **before the bots are restored** (restoring reads the exchange and may cancel orders), unless `--skip-preflight` is given, which it logs at WARNING. A failed check ends the process with the code a supervisor keys on: `4` the machine, `5` only the operator can fix it (no key, a rejected key, a key that can withdraw), `6` the exchange cannot be reached and a restart can outlast it. Each failed finding is logged at ERROR with its remedy.
5. It starts listening for SIGTERM and SIGINT (SIGINT and SIGBREAK on Windows). A request that arrives while the bots are restored is remembered and honoured as soon as the host serves.
6. The application boots: the bots are restored (a RUNNING or PAUSED bot becomes RECOVERING and places nothing), the watches start, and the host's start-up steps run in order: the alert-channel warning, one WARNING per RECOVERING bot, then `--resume-halted`, `--resume-recovering` and `--start-planned` if given (halted first, so only bots halted before this start are re-planned). A request to stop that arrived before this point skips those that trade (logged): the host would otherwise open orders and then drain. `--resume-recovering` is refused with exit `2` before anything boots if it would touch a mainnet venue the operator did not type with `--confirm-venue` (decision O8); `--start-planned` instead skips a planned mainnet bot on an untyped venue, with a WARNING and a `PLANNED_BOT_NOT_STARTED` alert, and starts the rest (`EPIC-045F`). For `--resume-recovering` that means every saved bot a restart makes RECOVERING - RUNNING, PAUSED or RECOVERING in its file, as the lifecycle table says - because the refusal runs before the boot that makes them so.
7. The host says `BOOTING -> SERVING` (one INFO line per state change), tells the service manager it is ready if `--host-signal sdnotify` was given, and writes a snapshot and one health line at once, then every `--health-interval` (60 s) until it stops. Before each snapshot it asks the exchange its time, so the line's `skew_ms` is a number and `status` reports it.
8. The first SIGTERM or SIGINT starts the drain: `SERVING -> DRAINING`. The stop policy runs for at most `--stop-timeout` (25 s): `leave-orders` (the default) logs, at INFO, each active bot it leaves and how many orders it has resting, and places and cancels nothing for a Spot bot. For a Futures bot it first reads, fresh from the exchange, whether a stop on the exchange covers the bot's position (`EPIC-038M`, owner question O12): a covered bot, or a flat one with nothing resting, is left as it is; a bot whose stop is missing, not on the exchange, on the wrong side or unreadable, or that is flat with its ladder resting, or a NEUTRAL grid with its ladder resting, is closed through the Stop the Bots tab uses (cancel the ladder, close at market, reduce-only), named at WARNING and in the stop ledger until it reads STOPPED. The reading has half of `--stop-timeout`; a bot not read by then is closed unread and the log says the deadline made closing the safe side; `--on-stop stop-bots` asks for the Stop the screen asks for, for each active bot, and waits for STOPPED.
9. A second signal at any moment after the first - while the policy runs, while the probes are read, while the application closes the workers - ends the process at once with exit `0`. A policy that outlasts `--stop-timeout` is given up on, and the whole stop must end within `--stop-timeout` plus 30 s, or the host leaves anyway. Each time the host first writes the `STOPPED` snapshot (best effort, at most 2 s, because the process then skips the module's own last one) and logs, at WARNING, what it was doing and which bots it left, in what state and with how many orders resting; the next start reads each as RECOVERING. A service unit's `TimeoutStopSec` must be larger than `--stop-timeout` + 30 s + 2 s (`deploy/linux/sew-run.service` states the formula; `Docs/OPERATIONS/headless_runbook.md` installs it).
10. The application stops (`DRAINING -> STOPPED`): the scheduler, the host, then the modules, so the bots' workers close (`Bot price streams released, workers closed`) and the last snapshot says `STOPPED`. The entry point releases the lock and the process exits `0`.


### 3a. Control of the running host (`EPIC-038J`)

1. The operator runs `main.py bot stop|pause|resume|start|delete <bot_id>` (or `bot edit <bot_id> --set key=value ...`, or `bot add <plan.json> [--name X]`) in a second shell, as the host's account. This process is a read-only copy: `"read_only": true`, it takes no lock and changes no bot.
2. If no copy holds the data root's lock it says so, exits `10` and writes nothing. If the running copy has no `state/control/` (it is not a `run` host) or this account cannot write there, it exits `5`.
3. It writes `cmd-<id>.json` (a `sew.host-command/1` document: a 32-hex id, the action, the bot, the venue typed, the time) into `state/control/`, mode `0600`, by a write and a rename.
4. The `run` host, once a second, lists the directory and believes a file only if it is the host account's own, owner-only, in a directory nobody else can write, not a link and small. It refuses a malformed, replayed (id already in the audit), expired or unauthorised file without effect, and logs it at WARNING.
5. For a sound command it writes `received` to `state/control/audit.jsonl`, dispatches `StopBotForOperatorCommand`, `PauseBotForHostCommand`, `ResumeBotForHostCommand`, `StartBotForHostCommand` or `EditBotForHostCommand` (which dispatch the screen's own `StopBotCommand`, `PauseBotCommand`, `ResumeBotCommand`, `StartBotCommand`, `EditBotCommand`), writes the verdict, and removes the file.
6. The operator's process reads the verdict from the audit and prints the bot's own sentence. A host that never takes the file has it withdrawn; a host that takes it and records nothing is named as such.

## 4. What must be true afterwards

- The exit code is `0` after a requested stop, `3` for a held lock, `4`/`5`/`6` for a failed pre-flight, `2` for a refused request, `1` for a crash. There is no retry loop inside the host: the service manager restarts on `1` and `6` and not on `2`–`5`.
- The lock is free, and `state/health.json` says `STOPPED` (or `FAILED` after a crash), so `status` can tell a clean stop from a process that vanished.
- A bot that was RUNNING when the host stopped is RECOVERING after the next start, and stays RECOVERING until a person resumes it (decision O2). The host never resumes a bot by itself.
- With `leave-orders` a Spot bot's orders are still on the exchange and the host placed and cancelled nothing for it; a Futures bot is still there with its position, ladder and stop only if a stop covered its position, and is otherwise closed (flat, nothing resting).
- No credential appears in the log, the snapshot or any report.

## 5. When it goes wrong

| What goes wrong | What the operator sees | Why it is this and not a crash |
| :--- | :--- | :--- |
| Another copy holds the data root | Exit `3`; "Another copy of Sagittarius is already running on the same data … `run` needs to be the writable copy and starts nothing on a read-only one." | A read-only host would look alive to its supervisor and trade nothing; `3` is in the unit's `RestartPreventExitStatus` |
| A flag is wrong (`--stop-timeout 0`, an unknown `--on-stop`) | Exit `2`, a sentence naming the flag | argparse and `run_options_of` refuse before anything starts |
| `--start-planned` and no plan was ever applied, or the record `bot apply` left cannot be read | Exit `5` before anything boots; the message says to run `bot apply <plan.json>` (with the host stopped) or to leave the flag off, and repeats none of the damaged record | A host asked to start the planned bots that has no plan must not serve and say "nothing to start"; a restart cannot fix it, so the unit must not restart it (decision D9) |
| `--start-planned` meets a planned mainnet bot the operator did not confirm | That bot is skipped and stays at rest; the host boots and starts the rest of the plan (also when none could start). A WARNING and a `PLANNED_BOT_NOT_STARTED` alert name `bot start <id> --confirm-venue <venue>` | Decision O8 keeps the real-money question; `EPIC-045F` (ADR 045 D7, the owner's rule of 2026-10-21) stops one unconfirmed bot from leaving every other bot unattended (exit `2` is not restarted by systemd) |
| `--resume-recovering` or `--resume-halted` with no alert channel and no `--i-accept-silent-failures` | Exit `5`, nothing started | Decision O2: nothing resumes unattended while a failure can be silent |
| `--resume-halted` would resume a mainnet bot the operator did not confirm | The bot is skipped and stays as it was; a WARNING `[resume-halted]` names it and the `--confirm-venue` it needs. The run goes on | EPIC-042 D13: the Resume carries the real-money answer only for the venue typed; unlike a start, a skipped resume leaves the bot in the state it was already in |
| `--host-signal sdnotify` off Linux, or with no `NOTIFY_SOCKET` | Exit `2` naming the missing piece | The adapter cannot work there; a container without the socket mounted is the usual cause |
| The pre-flight fails | Exit `4`, `5` or `6` per decision D9; each failed finding at ERROR with its remedy | The same mapping `preflight` and `exchange-status` use (`EXIT_CODE_FOR_FAILURE`) |
| The exchange is unreachable at start | Exit `6` | A restart can outlast an outage; the unit restarts with a delay |
| No alert channel carries bot events | A WARNING at start: "no alert channel is configured for bot events; nothing will tell you if a bot halts" | Until `EPIC-036B`, a halt at 3 a.m. is silent, and the log says so first |
| A bot is RECOVERING after the restart | One WARNING per bot naming it and the move that is a person's (`bot resume <id>` from a second shell, the Bots tab, or `--resume-recovering`) | Decision O2 |
| A control command is malformed, replayed, expired, or its file is not the host account's own and owner-only (`EPIC-038J`) | A WARNING `[control] command <id> refused (<verdict>)`; the file is removed; one `audit.jsonl` line; the bot is untouched | A file the operating system does not vouch for is never believed; a command takes effect at most once |
| A control command's audit line cannot be written (`EPIC-038J`) | An ERROR; the command is not executed and its file is removed; the operator's command exits `11` after `--wait` | An action nobody can account for does not happen |
| `state/control/` cannot be made private to the host's account (`EPIC-038J`) | One ERROR `[control] off: <why>` at start; the host serves without control, and `bot stop` exits `5` | A directory another account owns is never adopted |
| The stop policy does not finish in `--stop-timeout`, the whole stop passes `--stop-timeout` + 30 s, or a second signal arrives (in any phase, `app.stop()` included) | A WARNING naming the phase, the bots left, their state and orders resting; exit `0` | The state is on disk; the next boot treats them as RECOVERING |
| The exchange cannot tell the clock (the probe fails) | `skew_ms=na` on the line; one WARNING per streak, one INFO when it works again | A snapshot must never wait on the exchange |
| The snapshot cannot be written (disk full) | ERROR `[health-snapshot] could not write the snapshot`; the host carries on, and `status` calls it stale | The snapshot reports the work; losing it must not stop the work |
| An unhandled exception | Exit `1`, the traceback on standard error and in the log; the snapshot says `FAILED` | The host adds no retry; the supervisor restarts and boot recovery does what it does after any crash |

## 6. What this use case does NOT promise

- **It is not supported for unattended money.** Bot events reach one alert channel, Discord (`EPIC-036G`), but the other sources are not built (`EPIC-036B`); and nothing watches the host from outside until the owner stores a check-in URL for the dead man's switch (`EPIC-036E1`, runbook §3b), so a halt or a dead host can still be silent. The WARNING at start says so; the runbook says so.
- **Stopping does not watch the orders it leaves.** With `leave-orders`, between the stop and the next start nothing looks at a stop loss or a take profit; a Futures position is left only under a stop on the exchange (decision O12, `EPIC-038M`). This is true under either policy (decision O1; recorded for `EPIC-036`).
- **A Futures close the host cannot finish is named, not forced.** The host never opens a venue's order session, so a RECOVERING Futures bot on a closed session whose stop does not cover it stays STOPPING and is named as left. `--on-stop stop-bots` still asks to keep and a Futures bot refuses it (decision O12 follow-up, open).
- **A running host is controlled for eight verbs only** (`EPIC-038J`, `EPIC-038K`, `EPIC-038L` and `EPIC-045`, decision O4, the owner's choice of a local command directory, and the owner's rule of 2026-10-21 that whatever the Bots tab does at runtime the host does too): `bot stop`, `bot pause`, `bot resume`, `bot start`, `bot edit`, `bot add`, `bot delete` and `bot move` reach it from a second shell, run as the account the host runs as, and the host runs the screen's own Stop, Pause, Resume, Start, Save, New bot, Delete or Venue change once and audits it (§3a). `bot move <id> --venue <venue>` (`EPIC-045G`) is the Bots tab's Venue field for **one Spot DRAFT that never ran**: the bot keeps its id and parameters, places no order and needs no `--confirm-venue`; any other bot, an unknown venue and a same-name bot already on the target venue are refused in words. `bot apply` still needs the host stopped. `bot start` starts a DRAFT or STOPPED bot only, through the Start the Bots tab and `--start-planned` run (so the readiness check refuses in words: one active bot per symbol, five per venue, a venue that holds a RECOVERING bot) and starts no other bot, so Stop, edit the plan, Start of one bot needs no host restart; a HALTED or AWAITING_RECOVERY bot is refused (its resume proposes a ladder a person reads: `run --resume-halted` or the Bots tab); a mainnet venue needs `--confirm-venue`, and without it nothing is opened or started (the refusal names the venue's RECOVERING bots, so the person sees that they wait: a bot a restart left RECOVERING is reconciled with the exchange, and its owner budget registered, only by its own Resume (`BOT-183`, `BOT-197`: no other bot's opening of the session resumes it), so a Start beside it would add a bot's orders to an account whose existing exposure has not been verified (owner decision of 2026-10-20, `BOT-201`: the refusal stays, with this reason)). `bot delete <id>` (`EPIC-045B`; the owner dropped it on 2026-10-17 and reversed that on 2026-10-21) runs the Bots tab's Delete for **one DRAFT or STOPPED bot**, under the Start lock, and sends nothing to the exchange; unlike the tab it keeps a bot whose record still shows a held base worth `10` quote units or more on a USD-stable quote (any base at all on another quote), a live order, an owed order or an open protective stop. `bot add <plan.json> [--name X]` (`EPIC-045A`) runs the Bots tab's New bot for **one plan entry**: the bot lands DRAFT, starts nothing, records no desired state and needs no `--confirm-venue`, so adding a designed bot is export, `scp`, `bot add`, `bot start`, with no host restart. An older host that receives a `start` command reads the unknown action as a malformed command, audits it and does nothing (the operator sees exit `1`); nothing is started by mistake. `bot edit <id> --set key=value ...` (`EPIC-038L`) changes the parameters of **one DRAFT or STOPPED bot** while the others keep trading: the host merges the settings into the bot's parameters and dispatches the screen's own `EditBotCommand` (the Bots tab's Save and `bot apply`'s EDIT), so the lifecycle table refuses every other state in words (stop it first with `bot stop`), the bot's kind refuses an unknown key or an unreadable value in words and **changes nothing**, a set that changes nothing is refused, and the bot lands on DRAFT. An edit places no order and needs no `--confirm-venue`, on a mainnet venue too: the money question stays at `bot start`, whose guard is untouched. The reply shows each `key old -> new`. The parameters are read first with `bot show <id> --params` (`EPIC-038L`): every stored key and value, sorted by key, as stored, from the bot's file, so the read works on the read-only copy with no host round trip; `--json` always carries them under `parameters` in the one-bot read. **The plan file is yours and is not updated, and neither is the applied record `state/bot_plan.json` (it holds a desired state per bot and no parameters): change the same value in `plan.json` too, otherwise the next `bot apply` of the old plan edits the bot back** (an EDIT entry lands on DRAFT again). An older host reads the command's new key `set` as unknown, audits it `malformed` and does nothing (exit `1`). A full `bot apply` (many entries, a prune) and editing a bot that is not at rest still need the host stopped (or the Bots tab); `EPIC-045C` decides the first.
- `bot apply` is a writable boot of the application: the restart rule runs before the diff is read, so a bot left RUNNING or PAUSED on disk is RECOVERING when `apply` looks at it, and an apply is best made on a stopped host's data root. `bot apply --dry-run` boots read-only and shows the states as the files record them.
- `--start-planned` starts the bots the **applied** plan says are running and that are at rest; it never reads the plan file the operator edits, so an edit counts only once `bot apply` has run. A plan that wants no bot running is a plan: the host says so at start. A bot an applied plan names that no longer exists is a WARNING, not a start.
- One `--confirm-venue` names one venue; a plan holding real-money bots on two venues is started one venue per run.
- `--resume-recovering` sends each RECOVERING bot its own Resume, which opens the venue's order session for it and reconciles that bot with the exchange; it does not start a bot and does not resume a HALTED one. `--resume-halted` (`EPIC-042E`) does that: it is a person's Resume and Confirm for every HALTED or AWAITING_RECOVERY bot, and touches no other state.
- Windows' Ctrl-Break and the Windows memory reading are implemented and tested on their own, but have not been run on a Windows machine by this task.
- `--host-signal sdnotify` does not work inside a container that does not mount systemd's notify socket.
