# PRO-014 — A command loads only the modules and libraries it needs, so a short command stops paying 3 s before its first log line

**Date:** 2026-10-17
**Status:** Accepted (2026-10-17, owner)
**Source:** The owner, 2026-10-17, from the VPS: every short command pays about 3 s before the application logs its first line (`main.py bot list` 3.7 s wall; the application itself 0.057 s of that). Asked to do it now and keep it as a proposal: *"không, là 2. liền, lưu vào proposal"* ("no, option 2, right away, save it as a proposal"): change the module loading immediately and keep this page as the record.
**Decision:** Accepted by the owner on 2026-10-17 in that sentence, under `ONBOARDING.md` §7 ("a proposal is not turned into code without an owner acceptance"). Delivered as [`BOT-188`](../completed/BOT-188_a_command_loads_only_the_modules_it_needs.md). The measurements below were taken before this page was written, in throw-away experiments in a container, to choose between the options; no code from them was kept.

## 1. Problem and evidence

**On the VPS** (Ubuntu, one small box, checkout at `/opt/sew`, run as user `sew`; the owner's measurements, 2026-10-17):

| Measurement | Result |
| :--- | :--- |
| `main.py bot list`, wall | 3.7 s |
| the application itself (compose, run the query, dispose) | 0.057 s |
| `python -c pass`, `sudo` | 0.033 s, 0.018 s |
| `-X importtime` cumulative, µs | `shell.composition_root` 2,026,350 · `shell.modules` 1,640,699 · `market_data.cli.stream_cmd` 940,090 (through `failure_exit_code` → `binance.exceptions` → the whole `binance` SDK 714,729, of which `dateparser` 342,758) · `bots.module` 704,026 (`bot_event_router` 330,654) · `trading.module` 367,919 |
| bytecode | the `sew` user cannot write `__pycache__`; `python -m compileall` as root (3,648 files): 3.66 s → 3.03 s |

So interpreter and `sudo` are not the cause; about 0.6 s is compilation and about 3 s is **import work**. A read-only command (`bot list`, `bot show`, `status`) needs the bots and operations contexts and their state readers, not the exchange SDK, the trading adapters or the market-data stream commands.

**In the repository** (checked at `db5a961`, 2026-10-17):
- `src/main.py` imported `sync`, `stream`, `trade-once`, `exchange-status`, `order-preview` and `order-dry-run` at its head; `stream_cmd` pulled `failure_exit_code`, which imported the SDK's exception classes to map exit codes.
- `src/shell/modules.py` listed seven `BoundedContextModule` **classes**, so reading the list imported every `module.py` and everything each binds.
- Seven places imported the SDK at registration time: `market_data` (`adapter_bindings`, `market_data_venues`), `trading` (`adapter_bindings` → `venue_assembly` → 25 adapters), `binance_endpoints.py` (a venue contract importing `binance.enums`), plus `pyarrow` in the export handler.
- The machinery to build on exists: `Deferred` (`src/core/contracts/deferred.py`), the CLI registry (`src/config/cli_commands.json`) and `command_access.py`, which already decides before boot whether a command is read-only.
- The Engine refuses a context whose declared `dependencies` are not registered (`ExtensionDependencyError`), and `bots` resolves `trading`'s venue ports even to list (`IBotKindCatalog` → `GridKind` → `IVenueTradingPorts`). Both were found by trying "bots only": it does not boot.

**Measured in the CI-like container** (this PR's task, Python 3.12, 4 cores, bytecode compiled, `bot list` against an empty data root, 21 interleaved runs of the master build and this build; the container is faster than the VPS, so absolute numbers differ and the ratio is what carries over): `bot list` median wall 2.07-2.12 s on master and 1.16-1.18 s on the branch (1.76-1.83x), import time alone 1.4-2.1x. The 2x asked for was not reached by wall time; see the task's notes for the table and what is left.

## 2. Intended outcome and scope

A command loads only the modules and third-party libraries it needs. Acceptance, measurable: `python -X importtime main.py bot list` shows the pre-log phase (import plus composition) at least 2× faster than the table above, with the owner's target of under 1 s on the VPS; the host (`main.py run`), the GUI and every command's behaviour and output unchanged; the whole test suite green.

Out of scope: a service that answers read commands from a resident process (a socket). It is a later option only, see §3 and §6. No Engine change.

## 3. Options and trade-offs

| Option | Benefit | Cost and risk | Evidence |
| :--- | :--- | :--- | :--- |
| Keep the current approach, add `compileall` to the runbook | 0.6 s with one command | The other ~3 s stays | VPS: 3.66 → 3.03 s |
| (c) Stop importing SDK exception classes to map exit codes | One file | The SDK is imported by six other places; saves nothing alone | repo grep above |
| (b) Lazy heavy imports at the adapters (`binance`, `dateparser`, `pyarrow`) | Removes the SDK (~0.4 s here) | Leaves every context's own ~1000 modules | importtime, below |
| (a) Contexts declared per command, composition root builds only those and their suppliers | Drops `strategy`, `backtesting`, `alerting`, `operations` for the bots reads; a new command is one JSON line; absent = all (safe) | Suppliers come with the context (the Engine requires it), so `bots` still registers `trading` and `market_data` | tried: "bots only" does not boot |
| **(a) + (b) + (c) together, the smallest set that meets the cut** | The SDK, the unrelated contexts, `pyarrow`, the indicator scripts, the interactive shell and the writable half of the bots' boot are paid by the run that uses them | Many `Deferred` strings, held by a guard that resolves each | this change |
| (d) A read path for `bots` that does not register `trading` and `market_data` at all | Would save about 0.1 s more (measured with the dependencies filtered away) | `bots` ports (`IVenueTradingPorts`) and the Engine's dependency check both assume the suppliers; a redesign of the read side, and an Engine change or a filtered `dependencies` | a throw-away hack in the container; "bots only" does not boot as is |
| (e) A resident process answering read commands over a socket | Near-zero per command | A second long-lived thing to secure and supervise; explicitly out of scope | — |

Rejected: lazy imports inside functions (`PLC0415` debt only falls, `quality.md` §2); editing the Engine to ignore missing dependencies (a separate repository, separate confirmation).

## 4. Recommendation

(a) + (b) + (c) as one change, each cut at the place that causes the cost:
1. `cli_commands.json` gains `"modules": [...]` on a command or verb. `command_access.py` reads it (`command_needed_modules`), `main.py` hands it to `create_app`, and `shell/module_selection.py` selects those contexts **and what they depend on**, in list order. Absent means every context.
2. `shell/modules.py` names each class by path (`ModuleEntry`), so the list is free to read; `register_modules` instantiates an entry when it registers it.
3. `main.py` names the headless commands and the interactive shell by `Deferred`; the venue adapters that import the SDK, the Parquet writer, the indicator scripts and the writable boot of `bots` are named the same way; `TradingModule.shutdown` visits only venues something built; the hosted live-stream adapter looks the stream up at `stop()`.
4. Guards that assumed `MODULES` is a list of classes or that imports are static are updated, and gain a guard that every `Deferred` literal in `src/` resolves.
5. Declared today: `bot list|show|export` → `bots`; `bot start|stop|pause|resume` → `bots`, `operations`; `status` → `operations`; `alert test` → `alerting`. Everything else declares nothing and loads everything.

Option (d) is the next step if the owner wants under 1 s on the VPS and this is not enough: it is a redesign of how `bots` reads, and should be proposed on its own.
