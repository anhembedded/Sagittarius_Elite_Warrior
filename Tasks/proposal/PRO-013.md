# PRO-013 — `trading` answers "what exactly will the exchange receive for this order?", and every module asks it

**Date:** 2026-10-15
**Status:** Proposed
**Source:** The owner, 2026-10-15, after BUG-212 (a Grid plan passed its checks, the bot then bought at market and halted on a sell below the 5 USDT minimum): *"lý ra mấy cơ chế vào lệnh, giao dịch … phải là 1 module riêng, để các module khác có thể dùng chung mới đúng nhỉ? trước mắt có module bot và trading đều dùng các logic đó"* (the order-entry and trading mechanisms should be one module others share; bots and trading both use that logic). Then: *"nhưng sau đó hãy phân tích tại sao lúc dev thì AI không nhận ra cần sửa ở trading module?"* (do it later, but analyse why the AI did not see during development that the fix belonged in the trading module). Timing agreed: after EPIC-039I (Futures Short and Neutral) merges.
**Decision:** Pending (owner)

## 1. Problem and evidence
The shared module already exists: `trading` places every live order, and ADR D17 (`EPIC-025/DECISION_2026-09-11_module_boundaries.md`) says *"`trading` owns what the venue accepts"*. Code checked on `master-warrior` 67b2bd3, 2026-10-15:
- **The primitives are shared.** `trading/contracts/order_quantity_rounding_policy.py` publishes `round_quantity_down`, `round_price_to_tick` and `is_notional_sufficient`; its docstring says publishing it was the answer *"rather than a second copy of `ROUND_FLOOR`"*. The Grid imports it (`grid_plan.py`, `grid_ladder.py`, `grid_replay.py`, `grid_fee_netting.py`).
- **The composition is not shared.** Turning an intent into the exact order the exchange will receive needs four steps: the fee taken in base, the step floor, the split of a held quantity over levels, and the filter judgement. No contract offers that whole answer, so each consumer assembles the four steps itself:
  - `bots/domain/grid/grid_order_sizing.py` and `grid_fee_netting.py`, unified only by BUG-212;
  - `bots/application/services/venue/exchange_rules.py`, which uses its own `ROUND_FLOOR`/`ROUND_CEILING`;
  - the manual order panel, in `trading/ui/desk/order_entry/order_entry_rules.py`, which is presentation code;
  - `strategy/domain/policies/position_sizing_bridge.py`;
  - the Futures position ladder in PR #521, `position_order_sizing.py`.
- BUG-212 is what a second assembly costs: the Plan's assembly and the executor's disagreed, and the check passed while the order failed.

## 2. Why the sessions did not put it in `trading` (the analysis the owner asked for)
Each cause is a fact checked on 2026-10-15. None is "the model was careless": each is a gap in the process that let a reasonable session stay local.
1. **The reuse catalog does not list it.** `.claude/rules/capabilities.md` is the table a session reads before building ("find what exists before you write"). It is generated from `Capability:` docstring blocks. `order_quantity_rounding_policy.py` has none, and no row covers rounding, fees, minimum notional or order feasibility. The rule's only synonym for "round" points to display formatting (`APP_VALUE_FORMATTER`). A session that followed the rule found nothing.
2. **The Reuse section exempts the domain.** `.claude/templates/task.md` §3a asks for the catalog row checked *"for each UI or application need"*, and accepts *"None: no UI or application need"*. Order sizing lives in the Grid's domain, so its tasks could truthfully answer None, and review check A7 passed.
3. **Scope rules pull towards the local fix.** `ONBOARDING.md` §7 makes "modify code outside scope" an approval item, and task files list the files to change inside their own module. A session that sees the missing whole in `trading` must stop and ask. One that assembles the steps locally needs no one. The rules reward the second.
4. **No guard sees a second assembly.** The boundary guards check *imports* (`test_module_boundaries.py`). Bots imports the primitive correctly, so they pass. Nothing detects "the same four steps composed again", and no test held the Plan's assembly to the executor's until BUG-212.
5. **The systemic scan searched by name, not by concept.** `fix-bug-rule.md` §2 asks for a scan of the defect family. In BUG-212 it searched the Grid's own functions (`_counter`, `sizing`) and stayed in `bots`. "Who else turns an amount into an order?" is a question about a concept, and a name grep does not answer it.
6. **No memory across sessions.** EPIC-029 (Grid), EPIC-034 (constraints), BUG-212 and EPIC-039 were written by different sessions. Each read the code next to its task, and none held the picture of all consumers. The catalog is meant to be that memory (cause 1).

## 3. Intended outcome and scope
- **One contract in `trading`, `OrderFeasibility`.** It takes a symbol's filters, the fee model, a side, a price and an amount, which may be a quantity, a quote value, or a held quantity to split over N levels. It returns the exact quantity and price that will be sent, their notional, and every filter refusal with its numbers. It covers Spot and Futures through the venue profile.
- **The Grid planner, its executor, the Futures position ladder, the manual order panel and strategy sizing call it**, and the PRO-012 drawing tool will too. Each keeps only its own decisions: which levels, which side, how much capital.
- **Closing causes 1–5:**
  1. A `Capability:` block on the new contract, so the catalog row exists.
  2. Task template §3a also covers domain needs that touch exchange rules.
  3. An architecture guard: no module outside `trading` calls `quantize` on a step, or composes fee netting with a step floor. The allowlist only shrinks.
  4. Review rubric check A7 asks "does this compute something `trading` owns?".
  5. `fix-bug-rule.md` §2 adds "scan by concept: every consumer of the same exchange rule", with this case as the example.
  6. A case study, `Docs/CASE_STUDIES/CS-*_order_assembly_outside_trading.md`, recording that the gate was green while BUG-212 was live.

Out of scope: any change to thresholds, to what is sent, or to real-money behaviour beyond making every path agree. This is a refactor under green tests.

## 4. Options and trade-offs
| Option | Benefit | Cost and risk | Evidence or precedent |
| :--- | :--- | :--- | :--- |
| Keep the current approach | No work | Every new consumer (Futures Short and Neutral, PRO-012) assembles the steps again; BUG-212 can recur on another path | Five assemblies today (§1) |
| A new "execution" module beside `trading` | A visible home | A third place between the owner of exchange truth and its consumers; contradicts ADR D17; moves code without removing the duplicated composition | ADR D17 |
| `trading` publishes the whole answer and consumers call it (recommended) | One assembly; Plan, screen and executor cannot disagree; a guard keeps it so | A refactor across `bots`, `trading` UI and `strategy` on the real-money path; needs property tests that old and new agree before switching | The rounding policy already crossed this boundary for the same reason (EPIC-025 PR 2.1d) |

## 5. Recommendation
`trading` publishes `OrderFeasibility`, and every consumer is moved onto it one at a time behind a property test that the old and new answers are equal. The process fixes 1–5 and the case study ship in the same epic, so the next session finds the contract before writing a sixth assembly. Start after EPIC-039I merges, so the refactor does not race the Futures executor work. Each step gets a reviewer session, because it is on the real-money path.
