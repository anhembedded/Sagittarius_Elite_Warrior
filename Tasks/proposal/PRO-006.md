## 1. Problem and evidence

On 2026-10-03 the current tree was read by a survey of `src/modules/` (method: file reads and
`grep`; each claim below cites its file). Nothing here is inferred from task files. Paths without a leading `Docs/`, `Tasks/` or `src/` are under `src/modules/`.

### 1.1 A strategy is a setting of a desk, not a thing that runs

- Each desk embeds the strategy card in `trading/ui/dashboard/dev_board_widgets/strategy_card.py`.
  The card has a strategy combo, a timeframe combo, % capital, leverage, a params button, and
  Arm/Disarm buttons. `desk_view.py:100-103,135-152` places it next to Enable/Disable and
  Emergency Stop.
- **The symbol a strategy trades is whatever the chart is showing when Arm is pressed.**
  `desk_strategy.py:65` passes `get_active_symbol=lambda: chart.shown_symbol`. Changing the chart
  is therefore part of configuring the strategy, and nothing on the screen says so.
- `IStrategyArmingControl` offers `arm(config)`, `disarm()` and `saved_selection()` and nothing
  else (`trading/contracts/i_strategy_arming_control.py:30-45`). There is no pause and no resume.
  There is no state a person can watch except "armed with config X".
- The strategy has no name, no running PnL of its own, and no list of the orders it placed.
  - Client order ids are `SEW-` plus 12 hex characters (`trading/contracts/client_order_id.py:28-40`).
    They record neither the source nor the strategy.
  - Fills cannot be attributed to the strategy after the fact.
- The Dev Board shows the same card, wired to the **primary venue only**
  (`strategy/composition/port_bindings.py:157-160`).

### 1.2 One strategy per venue, one symbol per strategy, by structure

- `VenueStrategySessions` holds one `LiveStrategySession` per venue
  (`strategy/application/services/venue_strategy_sessions.py:29-45`). The session has one config/engine/coordinator
  slot, and `arm()` replaces it (`strategy/application/services/live_strategy_session.py:91-93,160-179`).
- `dispatch_tick()` drops every tick that is not the armed symbol and interval. Its docstring
  says: *"Multi-symbol live trading needs one session each, not one engine fed everything"*
  (`live_strategy_session.py:198-222`).
- The lease owner of every strategy is the single constant `STRATEGY_OWNER = "strategy"`
  (`strategy/contracts/strategy_owner.py:25`).
  - That file's docstring already anticipates a second instance with a different owner value.
  - `DECISION_2026-09-11_module_boundaries.md` §7 item 15 anticipates the same.
- The seam keyed by symbol that `EPIC-025C` planned (`EPIC-025C_phase2_strategy.md:31-33`) was
  never built.

### 1.3 What already exists and can be reused

- **Six strategies are registered explicitly** (`strategy/composition/state_bindings.py:70-75`).
- **Each strategy declares typed parameters** (`input_int/float/bool/string` → `ScriptInput`,
  with default, min/max, options, group and step; `src/support/indicators/scripting/inputs.py:24-56`).
  - `StrategyCatalogService.params_form()` / `validate_params()` already turn that schema into a
    form.
  - Backtest uses this form, and so does the live params dialog
    (`src/support/ui_kit/param_form/strategy_params_dialog.py:86`).
  - A per-strategy parameter panel therefore already exists as data.
- **Symbol lease.** One owner per symbol. A manual order is refused with `SYMBOL_LEASED` while a
  strategy holds the symbol (`trading/application/trading_session_state.py:238-273`;
  `execute_order/handler.py:141,207`).
- **Emergency Stop is per venue** (`emergency_stop/handler.py:110`). It does three things:
  1. disables trading;
  2. cancels every open order;
  3. closes Futures positions, or sells Spot holdings above the baseline.

  It does **not** disarm the strategy and does not release the lease. This is deliberate: the
  Symbol-lease entry in `Docs/VOCABULARY/README.md` says the position most needs its owner after
  an Emergency Stop.
- **Each venue has its own saved config.** `LiveStrategyConfigStore` writes
  `trading.<venue>.live_*` to `src/config/user_config.json`, and boot re-arms each enabled venue
  (`strategy/module.py:273-294`).
- `SPEC-010` ("arm a strategy") and `SPEC-007` ("Emergency Stop") are reserved but unwritten
  (`Docs/SPEC/README.md:66-69`).

### 1.4 Not present

- A bot entity or bot id.
- Grid or DCA execution of any kind; `grep` finds no `grid`, `dca` or `bot_id` in `src/`.
  Grid bots are explicitly deferred (`EPIC-028/README.md:99`).
- A backtest of resting order ladders. The only "ladder" in the code is the backtest's scale-out
  take-profit (`backtesting/contracts/broker_simulation_config.py:74`).

### 1.5 Unknowns

- Whether Binance's own Grid/DCA products should be used through their API, or whether the app
  should run its own ladders. This proposal assumes the app runs its own ladders, because they
  then reach Testnet and the fake exchange the same way every other order does. This has not been
  checked against Binance's current bot API.
- How many concurrent bots the in-process tick path can carry. No measurement exists.

## 2. Intended outcome and scope

**Outcome.** A top-level **Bots** tab is where every piece of automated trading is created,
started, watched, stopped and deleted. The desks become what their name says: manual trading,
with a read-only view of any bot on the same venue.

### 2.1 Settled with the user on 2026-10-03

| Question | Answer |
| :--- | :--- |
| What is a "bot type"? | **Signal strategies and Grid/DCA.** Signal bots run the six strategies that exist today. Grid and DCA are new execution models, delivered in later phases (§4). |
| How many bots per venue? | **Many, delivered in phases.** Designed for many bots from the start: each has an id, and each holds its own symbol. The first delivery keeps today's one bot per venue. |
| Do the desks still control strategies? | **No. The desks are manual only.** The strategy card leaves both desks. A desk shows a read-only badge ("Bot *EMA trend* running on BTCUSDT") and the bot's overlay on the chart, with a link to the Bots tab. The Dev Board keeps its card as a developer tool. |
| What happens when I trade manually on a symbol a bot holds? | **The order is refused, and the refusal offers a takeover.** The lease still refuses the manual order. The refusal names the bot and offers "Stop bot to trade manually". Two order sources never act on one position. |

### 2.2 Success criteria (today → done)

| Criterion | Today | Done |
| :--- | :--- | :--- |
| Where automation is configured | The strategy card on each desk and on the Dev Board | The Bots tab only (the Dev Board card remains a developer tool) |
| How a bot's symbol is chosen | Whatever the chart shows at Arm | An explicit field of the bot |
| Lifecycle a person can see | Armed / not armed | Draft → Running → Paused → Stopped, plus *Halted* after an Emergency Stop |
| Bots per venue | 1, by structure | Many, each on its own symbol (from phase 2) |
| Attribution | None; client order id is `SEW-` + random | Every order and fill names its bot; each bot shows its own PnL and orders |
| Bot types | Signal only, as a desk setting | Signal, Grid, DCA, behind one common shell |
| Parameter panel | A dialog behind a button | The bot type's own panel, generated from its declared schema |

### 2.3 Out of scope

- Mainnet, which stays behind `EPIC-026`'s gates (`PRO-005`).
- Margin, Isolated and Cross trading.
- Binance's hosted bot products.
- Copy trading.
- Running more than one bot on the same symbol.
- Changing the six strategies themselves.

| B. Add a Bots tab that drives today's per-venue arming slot | Small; reuses `IVenueStrategyControls` as is | The Bots tab becomes a second place for the same single slot. It cannot grow to many bots, attribution or Grid/DCA without being rebuilt. | `IVenueStrategyControls` (`EPIC-028K`) |

## 4. Recommendation

**Option C.** Phases are ordered so that each one is useful when it ships, and each one proves the
next phase's foundation.

### 4.1 The Bot entity

- **Bot.** A named, persisted instance of `(kind, venue, symbol, config)` with a lifecycle and an
  id. This is a new vocabulary entry. It is distinct from the `BOT-nnn` task-id prefix.
- **Bot kind.** A plug-in seam. Each kind supplies three things:
  - its parameter schema, which generates the panel;
  - its executor;
  - its overlay.

  The first kind is `signal`, which wraps today's `StrategyEngine` and `LiveTradingCoordinator`.
  `grid` and `dca` come later.
- **Ownership.** The bot's id is its lease owner, as `strategy_owner.py` already anticipates. A
  bot's client order ids carry a short bot tag (direction only: `SEW-{bot6}-{hex10}`, 21 of
  Binance's 36 characters). Fills and PnL can then be attributed.
- **Lifecycle.** Draft → Running ⇄ Paused → Stopped.
  - **Halted.** An Emergency Stop on the venue halts every bot on it. The lease is kept, consistent
    with §1.3. Only a person resumes a halted bot.
  - **Takeover.** "Stop bot to trade manually" stops the bot and releases its lease. Any open
    position stays and becomes manual. The dialog says so before it acts.
- **Placement.** A new `bots` module owns the entity, the store and the lifecycle, and contributes
  the `bots` route.
  - The `signal` kind reaches `strategy` through published ports, as
    `DECISION_2026-09-17_strategy_ui_contributes_rather_than_being_imported.md` requires.
  - `trading` stays the only executor of orders.
  - The exact module split is settled in the epic's decision record, not here.

### 4.2 The Bots tab

- **Left:** the list of bots. Each row shows name, kind, venue, symbol, state pill and PnL.
- **Right:** the selected bot.
  - **Common shell:** the header with state and Start/Pause/Stop, venue and symbol, risk cap, PnL,
    and the bot's own orders, fills and log.
  - **Kind toolbar and panel:** signal parameters, grid bounds and levels, or DCA steps.
- **New bot:** a dialog that picks kind → venue → symbol → parameters.

### 4.3 Phases

| Phase | Delivers | Proves |
| :--- | :--- | :--- |
| **P0 — Seams** | The Bot entity, id, kind seam, store, per-bot lease owner and tagged client order id. The `trading.<venue>.live_*` keys migrate once into one bot per venue. No UI change. | That one bot per venue behaves exactly as today's arming |
| **P1 — Bots tab, signal bots** | The tab, the common shell, signal panels generated from the schema, an explicit symbol, Pause/Resume, Halted after an Emergency Stop, and takeover on a lease refusal. The desks lose the strategy card and gain the read-only badge. `SPEC-010` is written as "run a bot". | The user's problem (§1.1) is solved for the strategies that exist |
| **P2 — Many signal bots** | One session per bot, a symbol per bot, a notional cap per bot, and PnL and orders attributed per bot | Many bots on one account without interference |
| **P3 — Grid bot** | A fill-driven ladder executor (Spot first, then Futures). Its ladder state is persisted and reconciled against open orders at boot. Session limits are reconsidered for ladders. | The kind seam carries a non-signal model |
| **P4 — DCA bot** | Safety-order steps and take-profit on the ladder executor from P3 | Reuse of the P3 executor |
| *(Optional) P5 — Backtest ⇄ Bot* | "Run as bot" from a backtest result, and "Backtest this bot". Grid/DCA here need a ladder simulator. | One config serves both backtest and live |

### 4.4 Dependencies and risks

- **Grid/DCA place many resting orders.**
  - `max_orders_per_session` and `min_order_interval` (`trading_limits.py:42-61`) were written for
    one signal at a time. P3 must decide whether these limits apply per bot or per venue.
  - The four limits are configuration, and changing them follows `ONBOARDING.md` §7.
- **Grid/DCA have no backtest today** (§1.4). Running them live with no historical evidence goes
  against the direction set in `Tasks/ROADMAP.md` (trustworthy backtests first). The decision §5
  asks for addresses this.
- **Throughput.** With many bots, every tick fans out to N sessions. P2 measures this before it
  raises any limit.
- **`EPIC-026`'s operational stages (`PRO-005`) assume one strategy per venue.** If this proposal
  is accepted, the soak and monitoring tasks there should name bots.

The user decides, under `ONBOARDING.md` §7:

1. **Accept Option C and the order P0 → P4.** Acceptance commits the project to:
   - a new `bots` module;

   only if DCA matters more to you.
