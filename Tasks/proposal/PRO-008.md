# PRO-008 — A long-running host proves its resources stay flat, instead of hoping

**Date:** 2026-10-13
**Status:** Proposed
**Source:** The owner, after the VPS sizing measurement: *"hình như mình chưa có task do mem leak? những app long run có phải do các thông số nào nữa ko nhỉ? có những quy trình gì?"* (we seem to have no task for memory leaks; what else breaks long-running apps, and what processes exist?). They then asked for a proposal rather than a task: *"hay tạo proposal thui, từ từ"*.
**Decision:** Pending (the owner).

## 1. Problem and evidence
The headless host is meant to run for weeks unattended, but nothing checks that its resources stay bounded over time.

**Established:**
- **Memory is printed, never judged.** The health line carries `rss_mb` (`Docs/OPERATIONS/LOGGING.md`). Nothing compares it over time or alerts on growth.
- **The memory ceiling only limits the damage.** `deploy/linux/sew-run.service` sets `MemoryMax=1G` with `Restart=on-failure`. A leak becomes a silent restart, and the cause is never found.
- **The 14-day soak was never run.** `EPIC-038` phase 2 requires a 14-day simulated soak on the fake exchange, with memory bounded and the health line never stopping. Its README records that the machinery is built but the run is not.
- **The testnet soaks wait on the owner.** The 14-day testnet soak of `EPIC-026O` fell with D6, which the owner rejected on 2026-10-07. The soaks of `EPIC-029H` and `EPIC-039L` wait on the owner's own run.
- **The idle baseline is known.** Measured on 2026-10-13 at `65e2d69`, sampled from `/proc` for 130 s on a machine with no network: idle RSS 142 MB, 28–31 threads, 0.1 % of one core. With one Grid bot on the fake exchange, the process peaked at about 176 MB. These figures are in the VPS handbook's sizing section.

**Unknown:**
- RSS with live TLS websockets: the fake exchange opens none.
- Growth over days: nothing has run that long.
- Whether every in-memory collection that grows with time has a cap. Candidates include the trade-id duplicate set, the owner order ledger and order history. None has been checked.

**Why it matters:** the failures that are typical for a long-running process grow slowly and look like something else. Over weeks they include:
- **Resources that leak:** memory, file descriptors, sockets, threads and asyncio tasks; unbounded queues and caches.
- **Time boundaries:** Binance cuts streams at 24 h; listenKey renewal; funding every 8 h; the 30-day history window; clock drift.
- **Disk:** the database and its WAL, logs, checkpoints.
- **Exchange-side drift:** rate-limit weight, and the bot's book drifting from the exchange.
- **Hidden loops:** a rising restart count, frequent reconnects, a slowing event loop.

## 2. Intended outcome and scope
A claim that "the host's resources are flat over N days" is backed by a check that fails when they are not, and a slow leak in the field is seen as a trend before the ceiling kills the process.

**Success criteria:**
- Every in-memory collection that grows with time has a stated bound, and a guard or review item enforces it.
- A short leak test per long-lived component: repeat one operation many times and show that memory and object counts are flat.
- A time-compressed soak on the fake exchange with injected faults (outages, a stream cut at 24 h, a restart). The slope of RSS, file descriptors and threads after warm-up must be within a stated budget.
- The health line also carries open file descriptors, threads, the longest internal queue, event-loop lag and restarts since boot. The runbook says which trend to alert on.

**Out of scope:**
- Buying a larger VPS.
- A scheduled restart as a fix. It hides the cause.
- The alert channel itself (`EPIC-036`).

## 3. Options and trade-offs
| Option | Benefit | Cost and risk | Evidence or precedent |
| :--- | :--- | :--- | :--- |
| Keep the current approach: `MemoryMax` plus restart, and a human reads `rss_mb` | Nothing to build | A leak is seen only as restarts, or never. The 14-day soak stays a promise. Real money would run on an unmeasured process | `EPIC-038` phase 2 marked not run |
| Run the owner's 14-day testnet soak only (`039L`) | Real network and real streams | 14 days per attempt. Without trend metrics, a slow leak still passes unnoticed, and a fix needs another 14 days | `EPIC-029H`, `EPIC-039L` |
| **Resource budget: bounded collections, short leak tests in CI, a nightly time-compressed soak, trend metrics on the health line** | Leaks are caught in hours on the fake exchange, before the testnet soak. The testnet soak then has numbers to read | Some build work. The soak's time compression needs an injectable clock, which already exists as a seam for the risk watch. A nightly job costs CI minutes | Freqtrade issue #10933: outage-driven growth killed by the OOM killer (`EPIC-038` research §8). The `EPIC-038` soak machinery is already built |

## 4. Recommendation
Adopt the resource budget, delivered before the `EPIC-039L` testnet soak so that the soak has trends to read. Suggested order:
1. Audit and bound the growing collections. This is cheap and may find the leak before any test does.
2. Add the health-line fields and the runbook's alert thresholds.
3. Add the short leak tests to the unit tier.
4. Add the nightly time-compressed soak, reusing `EPIC-038`'s machinery.

**Open questions:**
- Whether the nightly soak is a GitHub Actions schedule (minutes, public log) or runs on the owner's VPS.
- The numeric slope budget, to be set from the first nightly run.
