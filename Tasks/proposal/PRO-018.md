# PRO-018 — A theme inside the UI rule: follow the OS scheme, and give profit, loss and state colours from one meaning table that reads in light, dark and high contrast

**Date:** 2026-10-19
**Status:** Proposed
**Source:** The owner, 2026-10-19: *"làm task theme UI, với 1 task là tui muốn dùng rich cho VPS, đánh giá và làm nhé"* ("do a UI theme task, and one task where I want to use `rich` on the VPS: evaluate it and build it"). The owner's own rule, `ui-presentation-rule.md` §1, says that visual design (colours, icon set, branding) is deferred by the user and that the app uses stock Qt widgets in the platform's look. This proposal therefore separates what a theme can be inside that rule from what would need the rule changed.
**Decision:** Pending. Part A below is inside the rule and is delivered as [BOT-196](../backlog/BOT-196_bots_tab_colours_profit_loss_and_state_from_one_meaning_table.md) once this is merged. Part B changes the rule and is only listed.

## 1. Problem and evidence

Checked at `f83e5a21` (2026-10-19) by reading the code and by running Qt 6.11.1 offscreen; no screenshot was taken.

**What the Bots tab shows today.**
- *Profit and loss.* The Bots table (`src/modules/bots/ui/bots_screen/bots_table_models.py` → `BotsTableModel`) has `Grid profit` and `Total PnL` money columns. They print as numbers (`core/vo/number_text.py` → `money_text`: two decimals, `-9.00` for a loss, no sign on a profit) in the platform's text colour. The detail panel (`bot_facts.py`) and the ladder table (`BotLadderTableModel`) do the same. **No Bots-tab figure is coloured.**
- *State.* A state is a word in its own column (`state_text`). `_ATTENTION_STATES` (`HALTED`, `AWAITING_RECOVERY`, `ERROR`) are drawn **bold**; the module's comment says "the emphasis is bold, never a colour".
- *Connection.* `identity_strip.py` writes `"<venue>: <status> · <detail>"` into two stock labels; the status is a word (`Connected`, `Not connected`, `Connecting…`; `connect_words.py`). Not coloured.
- *The meaning table exists but the Bots tab does not use it.* `src/support/ui_kit/meaning_colours.py` → `Tone`, `tone_colour`, `PROFIT_COLOUR`, `LOSS_COLOUR` is "the app's one meaning table"; only the backtesting module uses it, through the table model's `ForegroundRole` (`metrics_detail_model.py` → `_role_data`). Its two colours are the chart's bull and bear (`#26a69a`, `#ef5350`, written only in `support/charting/contracts/series_colours.py`).

**Is that table readable?** WCAG contrast of those two colours as text, computed by hand with the standard relative-luminance formula: profit `#26a69a` is 3.0:1 on white and 5.6:1 on `#1e1e1e`; loss `#ef5350` is 3.5:1 on white and 4.8:1 on `#1e1e1e`. Normal text needs 4.5:1, so **in a light scheme both are below it**. Nothing in the table looks at the scheme, and a fixed colour set on a cell would also override Windows High Contrast, which the rule requires to stay usable (`ui-presentation-rule.md` §1: "Usable in Windows High Contrast").

**What the OS-theme support is today.** The app is stock Qt, so the palette follows the platform; `QGuiApplication.styleHints().colorScheme()` exists in this Qt (returned `Unknown` offscreen). `QStyleHints` has no high-contrast query in PySide6 6.11.1 (checked: its attributes are `colorScheme`, `colorSchemeChanged`, `setColorScheme`, `unsetColorScheme`). So the app already "follows the OS light and dark setting"; what is missing is a colour that reads on both.

**What the rule and its guards allow** (read, not guessed):
- Colour is allowed **only** where it carries meaning (profit/loss, connection state), from `QPalette` roles or one named meaning table, never an RGB literal, never alone: a sign, word or icon goes with it. `[guard: test_stock_controls_only.py]`
- `test_stock_controls_only.py` counts calls (`setStyleSheet`, `setPalette`, `apply_role`, ...) and any `#rgb`/`#rrggbb` string in `src/`, with one exemption, the series table. It does **not** count a named colour (`QColor("darkgreen")`; `chart_card/theme.py` already uses `"goldenrod"`, `"firebrick"`, `"steelblue"`).
- `test_app_styling_only_shrinks.py` holds hand styling at zero; `test_no_global_stylesheet.py` forbids an app-wide style sheet; `test_workbench_conformance.py` checks table configuration, alignment and fonts. A `ForegroundRole` returned by a table model's `_role_data` is the pattern the rule and the backtesting module already use.
- A label (`QLabel`) cannot be coloured without a palette override or rich text, neither of which the rule's no-palette-override clause welcomes.

**Unknowns.** How Windows High Contrast reaches a Qt 6.11 palette on the owner's machine (not run here: no Windows). Whether the owner wants a "+" on a profit; see Part A.

## 2. Intended outcome and scope

A theme here means: the app looks like the platform, in whichever scheme the OS is in, and the few colours that carry meaning stay readable in it.

**Part A, inside the rule (delivered as BOT-196):**
1. The meaning table gains a **palette-aware lookup**: the profit, loss and caution colours are chosen by the scheme of the table's own background (`QPalette.Base` lightness): a dark variant for light backgrounds, a light variant for dark ones, all **named** colours (no hex), each at least 4.5:1 against the extreme of its scheme. In Windows High Contrast the lookup returns nothing and the platform's text colour stays.
2. The Bots tab uses it: `Grid profit` and `Total PnL` (by the sign of the figure), the `State` column (RUNNING positive; PAUSED, RECOVERING, AWAITING_RECOVERY caution; HALTED, ERROR negative; the rest unchanged) and the ladder's net columns. The word or the minus sign is always in the cell; bold stays on attention states.
3. Tested through the table (`ForegroundRole` of the model) in light, dark and high contrast, no widget, English strings; `preview.py` already holds a bot in every lifecycle state and gets one losing and one winning bot.

**Part B, needs the owner's rule changed (listed, not built):**
- B1. Colour in a `QLabel` or the identity strip (connection `Connected` green / `Not connected` red, the detail panel's profit lines): needs rich text or a palette override on a stock label; the rule says no palette override.
- B2. A custom light/dark/branded theme, a style sheet, an accent colour, a fixed font: "visual design is deferred by the user", `test_no_global_stylesheet.py`, `test_app_styling_only_shrinks.py`.
- B3. A colour of one's own for a state beyond meaning (a coloured row, a badge): "colour only where it carries meaning".
- B4. A user-selectable theme in Options that overrides the OS scheme (`setColorScheme`): the rule says OS theme.
- B5. An explicit `+` on positive profit (`+1.23`) in the shared formatter: not a rule change but a display change to every money column, so it is left to the owner.

Out of scope: charts (the series table), the headless CLI (PRO-017), trading code, anything not named.

## 3. Options and trade-offs

| Option | Benefit | Cost and risk | Evidence or precedent |
| :--- | :--- | :--- | :--- |
| Keep the Bots tab uncoloured | Rule-clean today; no work | The owner's profit/loss at a glance is missing, and the existing table is unreadable in a light scheme if someone starts using it | Current code |
| A. Palette-aware meaning table plus Bots tab (recommended) | Inside the rule; readable in light, dark and high contrast; one table for the app; testable without a widget | One new lookup and a mapping per table; backtesting keeps its present call until it opts in | `meaning_colours.py`, `metrics_detail_model.py`, WCAG 2.x contrast |
| A2. As A, but reuse the chart's bull and bear hex | Zero new colours | 3.0:1 on white for profit text; fails the readable-in-light goal | Computed in §1 |
| B. Custom theme (style sheet, own palette, branding) | Full control of the look | Reverses §1 of the owner's rule and three guards; the owner defers visual design | `ui-presentation-rule.md` §1 |

## 4. Recommendation

Option A. Add `tone_colour(tone, palette)` beside the existing `tone_colour(tone)`; the old call keeps its behaviour so backtesting is untouched here (migrating it is a separate, optional task). Named colours: profit `darkgreen` on a light base and `lightgreen` on a dark one; loss `firebrick` and `lightcoral`; caution `saddlebrown` and `darkorange` (computed 6.7 to 7.4:1 in their own scheme). The scheme is read from the palette the model is asked with (`QPalette.Base` lightness), so it needs no scheme-change signal: a view asks `data()` on every repaint. High contrast is detected on Windows by one probe behind a small class the tests replace; elsewhere it is "not high contrast".

Dependencies that could change this: B5 (the owner may want the `+`); how High Contrast behaves on the owner's Windows machine, which BOT-196 cannot prove from a Linux session (the unit test proves the lookup, not the machine).
