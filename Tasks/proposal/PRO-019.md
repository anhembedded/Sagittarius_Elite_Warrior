# PRO-019 — A log viewer inside the app colours plain log lines at the screen; the stored record keeps its exact bytes

**Date:** 2026-10-20
**Status:** Accepted (2026-10-20)
**Source:** The owner, 2026-10-20, in Vietnamese: *"cac log ma co [Param] thi param phai co mau luon ban, tham khao internet cac rule lam mau cho log, sau do app dung giup tui, vao tat ca cac log, neu can thi build log manager"* ("logs that carry a [Param] must colour the param too; research on the internet the rules for colouring logs, then apply them for me across all the logs, and build a log manager if needed").
**Decision:** Accepted by the owner on 2026-10-20, option C, in their words *"đồng ý, làm theo đề xuất C"* (agreed, build option C), relayed by the coordinator. The scope of the first build is a delegated **Agent decision** (section 5), which the owner may veto. Delivery: [BOT-199](../backlog/BOT-199_the_logs_viewer_colours_the_params_of_a_plain_log.md).

**What "param" means (owner's correction, 2026-10-20, relayed by the coordinator).** *"parm y toi la khi ban in log. vi du: \"This bot name {$bot.name}\" thi bot.name la parm, tui ki vong cai do phai khac mau"* = a **param** is the value the code substitutes into a log message, e.g. `logger.info("Bot %s: exit slice %d of %s -> %s %s", bot_id, index, piece, ...)` (`src/modules/bots/application/kinds/grid/stop/grid_exit_slices.py`): `bot_id`, `index`, `piece` are params and must be coloured differently from the fixed text around them. So the **central requirement is exact params: the arguments of the log call** (`record.args`). A bracket tag (`[boot-recovery]`) is a second, minor colour; a `key=value` or number heuristic is only a fallback. (My first draft read "[Param]" as the tags and `key=value` pairs; that was a guess and is superseded.) The problem this creates: a viewer that sees only the final plain line cannot know which words were params. Section 4 compares the four ways to get them exactly under the fixed constraints.

## 1. Problem and evidence

On the VPS the owner follows `journalctl -u sew-run -o cat -f` in an SSH terminal. The lines are plain: a WARNING, a tag and a `qty=… price=…` all look alike, so the eye cannot find the one that matters in a screen of INFO. `PRO-017` / `BOT-195` coloured the **reports** (`bot list`, `status`) with `rich`; logs were left out on purpose. Checked at `5477ce6b` (2026-10-20) by reading the code and docs; nothing was run against a real VPS.

**What a log record is today (established).**
- Format fixed by `logging-rule.md` §8 and `Docs/OPERATIONS/LOGGING.md` §3: `%(asctime)s - %(name)s - %(levelname)s - %(message)s` (`src/config/app_config.json` `LOG_FORMAT`; same string in `src/shell/cli_log_routing.py` `_LOG_FORMAT`). The CI run-log scan reads `- (WARNING|ERROR|CRITICAL) -` and operators grep the same way. The Engine owns the console handler (`PRO-017` §1, `ONBOARDING.md` §2) and is not changed.
- Where it goes: stdout under systemd (the journal, `-o cat`), a file per short CLI run (`<data root>/logs/cli-*.log`), `log.file` if set, stderr for WARNING+ of read-only commands (`LOGGING.md` §1, §1b). None of these is a terminal the app controls.
- Shapes found by grep over `src/`: a **leading tag** (`[health] state=SERVING up=3600s bots=running:3,… tick_age_s=2`), a **bot prefix then tag** (`Bot %s: [boot-recovery] …`), a **trailing tag** (`Bot %s: halted (%s); closing the position [halt-closes-position]`), **`key=value`** (`qty=%s price=%s`, `stream_down_s=0`, `skew_ms=-120`), **comma-separated `name:count`** (`bots=running:3,paused:1`), one **non-bracket tag** (`BACKTEST_TRACE action=…`, `logging-rule.md` §8), tracebacks on following lines (ERROR with `exc_info`), and many lines with **no tag** at all. Tag shapes are therefore not uniform; the survey in the code PR lists the ones a viewer cannot recognise.
- Bot ids are 6 characters of `[a-z0-9]` (`src/modules/bots/domain/bot_id.py`, `BOT_ID_ALPHABET`, `BOT_ID_LENGTH`).
- **How many call sites, measured** (AST scan of `src/**/*.py` at `5477ce6b`, 2026-10-20; a call counts when its receiver is named like a logger, so an oddly named logger would be missed): **808** log calls. **615** (76 %) are `%`-style with arguments (**598** distinct templates; 1 176 `%s`, 128 `%d`, 65 `%f`/`%.2f`, 40 `%r`, 0 dict-style `%(name)s`); **66** (8 %) are a literal with no argument, so they have no params at all; **94** (12 %) are **f-strings**; **33** (4 %) pass a variable as the template (`logger.warning(message, *args)`); 0 use `.format` or `"..." % x` inline. `ruff`'s logging rules (`G`) are not selected in `pyproject.toml` (`extend-select`), and `logging-rule.md` does not forbid f-strings, so 94 f-string calls exist and nothing stops a new one. Tags: about 234 of 799 messages (by a regex over the first string) start with a bracket tag or `Bot %s: [tag]`, about 90 end with one, 88 distinct tags.
- **Who owns the console handler.** A quiet CLI command's console is the app's own `_CliConsoleHandler` (stderr, WARNING and above, `src/shell/cli_log_routing.py` → `CliLogRouting.apply`). `run`, `sync`, `stream` and `trade-once` keep the **Engine's** `StreamHandler` on stdout (`keeps_console_log`); the app already removes that handler for quiet commands, so changing its **formatter** from app code needs no Engine file change, but replacing the Engine's handler for `run` would be new behaviour (to verify in the task). Under systemd, stdout is the journal, never a terminal.
- `rich` is already pinned (`BOT-195`); the meaning-table pattern exists in `src/shell/rich_text_report_renderer.py`.

**Unknowns.** Not measured: how the owner's terminal (colour depth, background) renders the 16 ANSI colours; the journal's real volume per day on the VPS (matters only for `--since` speed); `journalctl` output of a multi-line message (assumed one `-o cat` line per line of text, which is how continuation lines of a traceback arrive).

## 2. Research: how colour is done for logs

Fetched or searched 2026-10-20. Where a page did not say a thing, it is marked *not stated*; nothing below is from memory.

| Source | What it says | Take-away for this app |
| :--- | :--- | :--- |
| [journalctl(1)](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html) | On a tty, lines are coloured **by priority**: ERROR and above red, WARNING yellow, NOTICE highlighted, INFO normal, DEBUG grey. Colour is the viewer's job (not stored). `SYSTEMD_COLORS=false` gives monochrome; `$NO_COLOR` or `$TERM` indicating no colour disables it. | The whole-line level colour is the baseline operators already know: red/yellow/normal/grey. Copy it. |
| [rich `RichHandler`](https://rich.readthedocs.io/en/stable/reference/logging.html) | Time, level and message in columns, level colour-coded, message syntax-highlighted by `ReprHighlighter` (numbers, strings, URLs, paths, `key=value`-like); `rich_tracebacks`, `keywords` (words highlighted in every message). | It is a **handler**, i.e. it colours at write time, which `PRO-017` §1 rejected. Its **highlighter** is what a viewer can reuse on a line already written. |
| [structlog console output](https://www.structlog.org/en/stable/console-output.html) | `ConsoleRenderer` colours only if stdout is a TTY; `FORCE_COLOR` forces, `NO_COLOR` disables all styling and overrides `FORCE_COLOR`; keys one colour, values another (example: keys cyan, values green); exceptions pretty-printed; described as "mainly a development helper". | Keys and values get **different** styles; colour is a development/terminal affair, not a stored format. |
| [coloredlogs API](https://coloredlogs.readthedocs.io/en/latest/api.html) | Defaults: critical bold red, error red, warning yellow, debug green, info unstyled, verbose blue; fields: asctime green, name blue, hostname magenta, programname cyan. Defaults stay inside the **eight-colour ANSI palette** "for consistent display across terminals". `$NO_COLOR` (any value, even empty) is a hint not to colour; the formatter is chosen by `isatty`. | Same level ladder as journalctl; stick to the basic palette; name/namespace gets its own hue; an empty `NO_COLOR` still counts. |
| [hl](https://github.com/pamburus/hl) (log viewer) | Reads files and **stdin pipes** (`tail -f x \| hl -P`); `--color auto\|always\|never`; themes tagged dark/light/16color/256color/truecolor; filters `-l` level-and-above, `--since/--until` with relative times (`-3h`), field filters, `-F` follow. | The exact shape of the proposed tool: a viewer in a pipe with level/time/field filters and follow. Confirms the filter set (`--level`, `--since`, `--follow`). |
| [lnav](https://www.linuxlinks.com/lnav-2/) and [its release notes](https://newreleases.io/project/github/tstack/lnav/release/v0.13.1-beta4) | A log navigator that reads timestamps and levels from the file itself; warnings yellow and errors red; log formats may define **highlights** per pattern; "the default terminal colors will now be used in the default theme" and highlight/identifier colours are checked for **high contrast against the background**. The hotkey docs ([lnav hotkeys](https://docs.lnav.org/en/latest/hotkeys.html)) say filters and a shorter timestamp column exist. *Exact default colours: not stated in what I fetched.* | The viewer should derive meaning from the line (not from the writer), prefer the terminal's default colours, and never pick a colour that can vanish on a background. |
| [ccze man page](https://manpages.debian.org/testing/ccze/ccze.1.en.html) | A log **colorizer** that reads a log on stdin, colours by plugin per log type, offers ansi/curses/html output, a user colour rc file, and `wordcolor` (colour keywords in unparsed input). *How it colours levels, IPs, numbers: not stated on the page.* | The pipe-filter idea is old and proven; unparsed lines are passed through (and keyword-coloured at most). One theme file is optional, not needed first. |
| [NO_COLOR](https://no-color.org/) | When present and **not an empty string**, software that adds ANSI colour by default should not (this is the site's wording; coloredlogs documents the empty string as also counting, so I treat *present* as the rule). It is a hint to the software, not to the terminal. `FORCE_COLOR` (2023) is the opposite request. | `NO_COLOR` set means plain bytes. Not `FORCE_COLOR`-driven by default; one explicit `--color always` is enough. |
| [rich Console](https://rich.readthedocs.io/en/stable/console.html) | `is_terminal`; without `force_terminal` rich strips control codes when not on a terminal; `NO_COLOR` removes **only colour**, bold and underline stay; `TERM=dumb`/`unknown` disables colour and style; `FORCE_COLOR`. | Same conclusion as `PRO-017`: decide "colour or not" ourselves (`isatty`, `TERM`, `NO_COLOR`) and hand rich a console that cannot emit anything when the answer is no. |
| [WCAG 2.1 SC 1.4.1 Use of Color](https://www.w3.org/WAI/WCAG21/Understanding/use-of-color.html) | "Color is not used as the only visual means of conveying information"; a colour difference counts as an extra cue at 3:1 contrast. | The level word (`WARNING`) and the tag text are always printed; colour only adds. A param is never conveyed by colour alone. |
| [Terminal colours are tricky (jvns.ca)](https://jvns.ca/blog/2024/10/01/terminal-colours/) and [How to choose colors for CLI apps (xoria)](https://blog.xoria.org/terminal-colors/) | Terminals assign their own RGB to the 16 ANSI colours; blue on black is a common complaint; themes that use only the 16 colours avoid mismatch but express less. A search of dircolors-solarized and irssi-solarized shows the same community rule: stay readable under the terminal's **default** palette. *No formal standard found; this is convention.* | Use the 16 named ANSI colours only (no 256, no truecolor); avoid plain blue and black-on-black; use `dim` for the timestamp (not "bright black" as a colour, which vanishes in some themes). |
| [Twelve-Factor, Logs](https://12factor.net/logs) | Logs are an event stream, "one event per line", exception backtraces may span lines; the app writes unbuffered to stdout and "never concerns itself with routing or storage"; the environment captures and routes. | The app stays a plain emitter; presentation is a separate consumer of the stream. |
| [Python `logging` docs](https://docs.python.org/3/library/logging.html) | A `LogRecord` keeps the call's `msg` (the format string) and `args` ("the tuple of arguments merged into `msg`") **apart**; `message` is computed as `msg % args` only when a handler formats the record (`Formatter.format`, `getMessage()`); with no `args`, no `%` operation happens. `style` applies to the *format string of the formatter*, not to the messages. | The params exist only at the moment of formatting, inside the process. After that they are bytes in a line. This is the fact the four options below are about. |
| [Colorize your arguments (Medium, Analytics Vidhya, 2020)](https://medium.com/analytics-vidhya/python-logging-colorize-your-arguments-41567a754ac) and [ChromaFormatter](https://pypi.org/project/chromaformatter/5.0.6) | Both do it at **emit time** in a `logging.Formatter`: wrap each placeholder (or each formatted argument) in ANSI codes, then format the message; the article notes the legacy `%s` style needs separate handling. ChromaFormatter exposes `arg_start_color` / `arg_end_color`. *I read search summaries, not the code.* | Emit-time colouring of `%`-args is a known, small technique (option B). It colours the stream, so it must be limited to a terminal handler. |
| [structlog API: `ConsoleRenderer`, `KeyValueRenderer`, `LogfmtRenderer`](https://www.structlog.org/en/stable/api.html) | In structlog the event is a fixed string plus **key/value pairs kept apart** until the renderer runs; `ConsoleRenderer` styles `kv_key` and `kv_value` separately (`ColumnStyles`), `KeyValueRenderer` and `LogfmtRenderer` emit plain `key=value` with no colour parameters. *The stdlib `PositionalArgumentsFormatter` section was past the part of the page I could read.* | Exact value colouring comes from keeping values apart from the text (structured logging, option D), not from reading the final line. |
| [lnav release notes](https://newreleases.io/project/github/tstack/lnav/release/v0.14.0-beta3) | lnav has no automatic notion of "the substituted value": a log format may define **highlights** (a regex and a style) per field or per line; the identifier/highlight colours are contrast-checked. *I found nothing that says lnav detects interpolated values by itself.* | A viewer that colours params without help is a regex heuristic (option A), even in the best tool. Exactness needs a pattern per message: option C is that, generated from the source. |

**Rules I take from the research (each is in at least two sources above).**
1. Colour at the viewer, never in the stored record (journalctl, 12-factor, structlog "development helper").
2. Level ladder: CRITICAL bold red, ERROR red, WARNING yellow, INFO default, DEBUG dim/grey, TRACE dim (journalctl, coloredlogs, lnav).
3. The substituted values are the loudest non-level colour (owner's requirement; Python docs, Medium/ChromaFormatter, structlog key/value styles); timestamp dimmed; logger namespace one fixed hue; the bracket tag is the strongest non-level accent; keys and values in different styles; numbers lightly; ids distinct (structlog, coloredlogs, rich highlighter).
4. Colour is never the only signal (WCAG 1.4.1): every word stays printed.
5. Off when not a terminal, when `NO_COLOR` is non-empty, when `TERM=dumb`; an explicit flag may override upward (`NO_COLOR` spec, structlog, rich, hl `--color`).
6. Basic 16-colour palette, no hard-coded backgrounds, no `bright black`/blue for body text (coloredlogs, lnav contrast note, jvns/xoria).
7. Continuation lines (traceback) belong to the record above them (12-factor; rich tracebacks).

## 3. Intended outcome and scope

**Outcome.** The params of a log call (`record.args`) are coloured differently from the fixed text of the message, in the places a person reads: a terminal running the app, and the journal or a file through `$M logs`. Stored bytes are unchanged. On the VPS:

```text
journalctl -u sew-run -o cat -f | $M logs                 # live, coloured
$M logs --file /var/lib/sew/logs/cli-….log --level warning --since 2h
journalctl -u sew-run -o cat --since today | $M logs --bot uie03d --tag reduce-only-refused
$M logs --follow --file <path>                             # tail a growing file
```

**Success criteria.**
1. **Exact params:** for a log call written with `%`-style arguments or an f-string (**84 %** of the call sites above have no params or `%`-args, **96 %** counting f-strings), the words the code substituted are the words the viewer colours, proven by a test that formats every catalogued template with sentinel arguments and checks the parsed spans.
2. Not a terminal, `NO_COLOR` non-empty, `TERM=dumb`, or `--no-color`: output equals input byte for byte (filters aside), proven on golden lines. The stored/streamed record is the same bytes as today (the CI scan, `grep`, journal untouched).
3. Level, timestamp (dim), logger name, **param (the central colour)**, bracket tag (minor colour) and the traceback block are styled by **one named meaning table**; the words are still printed (colour is never the only signal).
4. A line the viewer cannot match to a template is printed with the heuristic fallback (tag, `key=value`, ids, numbers), marked in the tests as inexact; a malformed line never raises; a traceback stays attached to its record.
5. Filters: `--level`, `--bot`, `--tag`, `--since`, `--follow`, `--no-color`.
6. The viewer reads what the app writes: a test runs the app's real formatter over a record and parses it back; a guard fails when a log call exists that the catalogue does not hold.
7. No change to emitted records, the Engine, the CI scan, trading, order or stop/close code.

**Out of scope.** Changing any log call or format; `RichHandler` or any colour at write time; a persistent index, search UI or database of logs; remote collection (Loki etc.); colouring the desktop log pane (a different surface, `PRO-018` territory); a theme file and light-theme variants (seam only); converting the 94 f-string calls to `%`-style and the 33 variable-template calls (a follow-up list and a ratchet guard, not a mass edit).

The four ways to know which words were params, under the fixed constraints (stored bytes, CI scan, journal and Engine unchanged). "Exact" means the coloured words are exactly the substituted arguments.

| :--- | :--- | :--- | :--- | :--- |

## 5. Recommendation

**Option C as the core, option A as its fallback, option B as a cheap second step, D rejected.** Reasoning: the owner reads the **VPS journal**, where the process is not on a tty, so B alone would colour nothing there; C colours the plain line wherever it goes and is exact for 88 % of the call sites (96 % with the 66 no-param calls counted as trivially exact), the same source of truth (the call sites) the guard keeps honest; A covers the rest and is labelled inexact. B is small and exact for `%`-args but only for a foreground run, so it waits until the owner asks for it (P7: seam now, variant later: the meaning table and the span model are shared, so B is a second producer of the same spans). D changes every call site and the record format and is not wanted.

Structure (names indicative; the task fixes them):

```text
build/CI : AST pass over src/ ──► template catalogue (committed, with the commit it was built at) ◄── guard: stale or missing call site fails
viewer   : plain line ─► LogLineParser ─► LogRecord(ts, logger, level, message, continuation[])
                                   │ message ─► TemplateMatcher(catalogue) ─► param spans (exact)   | none or ambiguous ─► heuristic spans (inexact)
                                   │ unmatched line ─► passthrough (printed as is)
                       LogFilter (level, bot id, tag, since) ──► keeps record + continuation together
                       LogMeaningTable (one table: level, timestamp, logger, PARAM, tag, traceback → rich style)
                       colour decision: isatty ∧ TERM≠dumb ∧ NO_COLOR empty ∧ not --no-color ∧ rich importable
                            yes ─► RichLogPrinter (16 named colours)      no ─► the input line, unchanged
input: stdin (default) | --file PATH [--follow]
```

- **Matching.** A template `Bot %s: exit slice %d of %s -> %s %s` becomes `^Bot (.+?): exit slice (-?\d+) of (.+?) -> (.+?) (.+?)$`; ties between templates go to the one with the most fixed characters; a `%s` hole that holds a bracket tag constant is shown in the tag colour, not the param colour. f-strings are split the same way (`f"{_TAG} {report.source} detail:\n..."` gives a tag hole, a param hole and fixed text).
- **Reading the journal directly** (`--journal`) stays with the pipe `journalctl … -o cat | $M logs`.
- **Level `--level`** is "this level and above"; **`--bot`** matches the 6-character id as a whole word; **`--tag`** matches `[tag]` anywhere in the message; **`--since`** takes `2h`, `30m`, `today` or an ISO time; `--follow` polls a file with an injected clock and sleeper.
- **Palette (first cut, 16 named colours):** CRITICAL bold red; ERROR red; WARNING yellow; INFO default; DEBUG/TRACE dim; timestamp dim; logger namespace cyan; **param bold green** (the loudest non-level colour, as asked); bracket tag magenta (minor); traceback dim red. Final values live in the one table and are pinned by golden tests.
- **Constitution check (P1 to P11).** P1 the catalogue is generated and guarded, the colour decision is code; P2 the catalogue is generated from the source and the viewer states the commit it was built at, nothing hand-listed; P3 the format is cited from `LOGGING.md` §3, one pattern constant; P4 the round-trip and sentinel-argument tests prove spans, not just absence of errors; P5 repo mechanisms (`rich`, the meaning-table pattern, the AST guard style) over invention, industry rules cited in section 2; P6 the mechanism (knowing the params) is fixed at its source, the call sites, not guessed at the screen; P7 one input family now, B, `--journal`, themes as seams; P8 tests only added, and a ratchet guard on new f-string calls is proposed as a follow-up; P9 decided by delegation below; P10 units on `--since`; P11 this document is the contract.
- **Agent decision (delegated, owner may veto).** Build the viewer in option C with fallback A, with `--level`, `--bot`, `--tag`, `--since`, `--follow`, `--no-color`; do **not** build B, storage, index, search UI or `--journal` now. It touches no dependency (rich already pinned), no setting, no Engine file, no trading code, is reversible (delete one package, one generated file, one command), so it falls under "Settle an owner decision that carries a recommendation" in `ONBOARDING.md` §7. If the owner wants B (colour on the foreground run) or the larger "manager" (D), that is a separate task or proposal.
- **Where it lives.** A pure package under `src/support/` (catalogue builder, matcher, parser, filter, meaning table, printer; no Qt, no Engine import), a script to regenerate the catalogue, and a command `logs` declared in `cli_commands.json` that does not boot the application. Task `BOT-199` confirms the declaration the "every command declares where its log goes" guard demands.
