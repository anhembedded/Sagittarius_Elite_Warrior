## 1. Problem and evidence

On the VPS the owner reads `bot list`, `bot show`, `bot order` and `status` in an SSH terminal. Their text is padded columns of plain characters. The owner wants `rich` (tables, colour) there. The evaluation below answers the questions that decide whether that is safe. Checked at `f83e5a21` (2026-10-19) by reading the code, and by installing `rich` 15.0.0 into a throwaway Python 3.12 venv and running it; nothing was run against the real CLI.

**What the CLI prints today.** Every report command builds a `Report` (`src/core/contracts/report.py` → `Report`, `ReportSection`, `ReportRow`, `ReportCell`) holding a JSON-ready `payload` (the contract with scripts, keys pinned by `test_the_bot_report_payload_keys_are_pinned`) and a neutral `layout` of sections of rows of cells with a column width. `emit_report` (`src/support/cli_host/report_output.py` → `emit_report`) selects a renderer by name from `ReportFormats` and writes `renderer.render(report) + "\n"` to stdout. Only two renderers are registered (`src/support/cli_host/report_formats.py` → `ReportFormats.default`): `text` (`adapters/text_report_renderer.py` → `TextReportRenderer`: cells padded with `ljust`, joined by one space) and `json` (`adapters/json_report_renderer.py`). **There is no `key=value` output format.** `IReportRenderer`'s docstring names it as a possible future renderer; `key=value` in the code is the input form of `bot edit --set key=value`. So the machine formats today are `--json` and the exit code, and the human format is the text one. The text is pinned byte for byte by golden tests (`tests/unit/presentation/cli/test_exchange_status_text_is_unchanged.py`, `tests/unit/modules/bots/cli/test_bot_ladder_reports.py` and the other `test_bot_*` files).

**Which of those `rich` may touch.** Only the text renderer's output to a terminal. JSON is produced by a different class from the same `Report` and `rich` never sees it. The text format is also read by people through pipes (`bot list | grep RUNNING`, `bot list > file`), and by `awk` on the padded columns, so its bytes are a de-facto contract; `rich`'s default table draws box characters (`┏━┳━┓`), which I confirmed it does even with no terminal and no colour. Therefore `rich` may be used **only when the text format is selected and stdout is an interactive terminal**; in every other case the existing `TextReportRenderer` runs and the bytes do not change. This is stronger than "no ANSI when piped": it keeps the whole text byte-identical when piped.

**Behaviour when stdout is not a terminal.** `sys.stdout.isatty()` is false under systemd (journal, `StandardOutput=journal`), under `ssh host cmd`, in a pipe or file, and in cron. `rich`'s own `Console.is_terminal` and `color_system` reflect that (measured: a `Console(file=StringIO())` reports `is_terminal False`, `color_system None`). I do not rely on `rich` to degrade; the renderer chooser checks `isatty()`, `TERM != "dumb"` and `NO_COLOR` unset itself and picks the plain renderer. `NO_COLOR` is honoured by `rich`, but it still emits bold and underline (measured: `NO_COLOR=1 FORCE_COLOR=1` leaves a colour system), so the chooser treats `NO_COLOR` as "use the plain renderer" rather than as "rich without colour": simpler, and it matches what the operator asked. Width: `rich` reads the terminal size and falls back to 80 columns when it cannot. A `bot list` row is wider than 80 characters (ten cells), and `rich` shortens a cell that does not fit, which would hide an id or a state. So the rich renderer is chosen only when the terminal is at least as wide as the table's natural width; on a narrower terminal the plain renderer runs (the operator then sees what they see today).

**The Discord and alerting path.** `alert test` prints a `Report` for the operator (`src/modules/alerting/cli/alert_cli_handler.py`); the message Discord receives is built in the alerting module (`src/modules/alerting/application/`) and never passes through a renderer. Nothing sent to Discord, to the health line (`operations/application/health_line.py`) or to a file is rendered by the text renderer. So `rich` cannot reach Discord. The only text consumers are the terminal and whatever the operator pipes.

**Logging.** `rich` provides a `RichHandler`. It does not belong in logging here, for three reasons: (1) the host's log goes to standard output captured by the journal (`headless_runbook.md` §10), and ANSI sequences stored in the journal make `journalctl` output, `grep` and the log viewer noisy; (2) the log line format is fixed by `logging-rule.md` and `LOGGING.md` §8 and the Engine owns the console handler (`cli_log_routing.py` replaces it; the Engine is not changed, `ONBOARDING.md` §2); (3) a log line is a record, not a report. So `rich` is **not** used for logging. The proposal covers only interactive report tables and status.

**Windows and the Python floor.** `rich` 15.0.0 is pure Python, `Requires-Python >=3.9`, classifiers for 3.9 to 3.14, Windows, macOS and Linux; the repo's floor is 3.12 (`install-rule.md` §1b). On Windows `rich` uses the Windows console API or ANSI where the console supports it and falls back to ASCII box characters on a legacy encoding. `colorama` 0.4.6 is already in the lock (via `pyqtgraph`, `pytest`); `rich` does not need it.

**Licence and size.** `rich` MIT; its two runtime dependencies are `markdown-it-py` (MIT) and `mdurl` (MIT); `pygments` (BSD-2-Clause), which `rich` lists as a dependency, is **already pinned** in `requirements.lock` (`pygments==2.21.0`). New packages in the lock: `rich`, `markdown-it-py`, `mdurl`. Installed size measured on 3.12: `rich` 1.4 MB, `markdown_it` 0.4 MB, `mdurl` 0.04 MB, about 1.9 MB new on the VPS (pygments, 5 MB, is already there for the dev set but **not** for the headless set: `requirements-headless.txt` has no pytest, so on the VPS the real new weight is about 7 MB with pygments). Import cost measured: `import rich.console, rich.table` 7 to 26 ms cumulative on a warm run, against the 3 s a `bot list` already takes on the first VPS (`headless_runbook.md` §2, `PRO-014`); the import is lazy (only on the terminal path), so piped runs and `--json` pay nothing.

**Pure-Python install on the VPS (`install-rule.md`).** `pip install -r requirements-headless.txt -c requirements.lock` installs `rich` as a wheel, with no compiler and no system library. Pinning follows the repo's way: the direct name goes in `requirements.txt` and `requirements-headless.txt` (unpinned names, as every other direct dependency), and `requirements.lock` gets exact versions regenerated with `uv pip compile requirements.txt --universal --python-version 3.12 -o requirements.lock`; `test_every_requirement_is_pinned_in_the_lock` and `test_headless_requirements_name_no_qt_package` keep the three files agreeing. I resolved the pins in a scratch venv: `rich==15.0.0`, `markdown-it-py==4.2.0`, `mdurl==0.1.2`. A VPS that pulls the new code but does not reinstall the requirements would otherwise crash on `import rich`; the design imports `rich` inside the terminal path and falls back to the plain renderer on `ImportError`, so an old venv keeps working.

**Unknowns.** Not measured: `rich` on a real Windows service console (NSSM) or `conhost`; the Windows runbook steps are themselves unrun (`headless_runbook.md` §0). Not measured: `rich`'s table in a terminal narrower than 120 columns for `bot list`, which BOT-195 tests with a fixed `Console(width=...)`.

## 2. Intended outcome and scope

**Outcome.** On an interactive terminal, with the text format, `bot list`, `bot show`, `bot order` and the other reports built from a `Report` print as a `rich` table with a header, aligned columns and colour that carries meaning (state: RUNNING, PAUSED, HALTED; profit and loss signs), and titles for sections. In every other case the output is the existing bytes.

**Success criteria.** (1) `--json` output is byte-identical with and without a terminal. (2) The text output with stdout not a terminal, with `NO_COLOR` set, with `TERM=dumb`, with `--verbose` and with `rich` missing is byte-identical to today's, proven against the existing golden strings. (3) With a terminal, the output holds ANSI sequences only on that path. (4) A colour never stands alone: the state word and the sign are still printed. (5) `rich` is pinned in `requirements.txt`, `requirements-headless.txt` and `requirements.lock`. (6) The headless runbook says what changes and how to turn it off.

**Out of scope.** `rich` in logging; `rich.progress` or live displays; a `key=value` renderer (it does not exist; a separate proposal if wanted); the desktop UI (PRO-018 and the UI rule); `status`'s health line; colour themes beyond one meaning table for the CLI.

## 3. Options and trade-offs

| Option | Benefit | Cost and risk | Evidence or precedent |
| :--- | :--- | :--- | :--- |
| Keep the plain text renderer | No new dependency; bytes pinned | The owner's request is not met | Current code |
| A. `rich` for the text report on a terminal only; the plain renderer for everything else (recommended) | Tables and colour where a person reads; every machine and piped byte unchanged; no behaviour change in the journal, Discord or JSON; falls back if `rich` is absent | One more renderer and a small chooser; three new pinned packages (~2 MB); a second layout to test | `IReportRenderer` / `ReportFormats` exist for exactly this (Open-Closed); `rich` honours `NO_COLOR`, but the chooser decides |
| B. `rich` for every text output, trusting `rich` to degrade | Simplest code | `rich` draws box characters even when piped: every `grep` and golden test changes; breaks scripts reading the padded columns | Measured: `Console(file=StringIO())` printed `┏━━━┳━━━┓` |
| C. `rich` also as the logging handler (`RichHandler`) | Coloured logs on the console | ANSI in journald, the Engine owns the handler, the log format is a rule | `cli_log_routing.py`, `logging-rule.md` |
| D. Hand-written ANSI colour with no dependency | No dependency | Re-implements tables, width, Windows and `NO_COLOR` badly (`CONSTITUTION.md` P5: apply a vetted library) | `rich` is the standard library for this |

## 4. Recommendation

Option A. Register a third renderer behind the existing seam and add one small chooser, so no report command changes:

```
emit_report(report, args, formats)
  name == "json"            -> JsonReportRenderer          (never rich)
  name == "text":
     stdout.isatty() and TERM != "dumb" and NO_COLOR unset
     and terminal width >= table minimum and rich importable
                            -> RichTextReportRenderer      (lazy import)
     otherwise              -> TextReportRenderer          (today's bytes)
```

The `Report`'s layout is already sections of rows of cells with a width; the rich renderer draws a section as a `rich.table.Table` when its rows have the same number of cells (the list), and as a two-column key and value block when a row is label and value (`bot show`). Colour comes from one small named table in the renderer (state word to style, sign to style), never from the `Report`, so the contract stays neutral. Phase 1 builds this and nothing else.

Dependencies that could change the recommendation: none found. If the owner prefers not to widen the dependency set, Option "keep" is the fallback.
