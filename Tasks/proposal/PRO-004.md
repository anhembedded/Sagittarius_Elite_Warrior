## 1. The Problem in Overview

The user's diagnosis is correct, but **the mechanism behind the disease is not the one we
assumed**.

Measured directly on `src/` (664 `.py` files, 74,371 lines): the number of times one screen
imports the internals of another screen is **0** (there is exactly one *comment* that
cross-references another screen, at `dashboard/coordinators/indicator_coordinator.py:2`).
In other words, the app does **not** suffer from "imports going everywhere".

The real disease lies elsewhere and is worse: **no unit of code owns a bounded context** — a
region of the system, in the Domain-Driven Design sense, inside which a business term has
exactly one meaning and one owner. When two screens need the same business behaviour and no
owner exists, there is nobody to call — so the path of least resistance is to **copy**. The
measured result:

- **132** method names are defined in more than one screen; of these, **59** exist in
  **exactly the pair** `dashboard` + `trading`.
- Verified as near-verbatim copies (the only difference being `set_status` versus
  `_append_log`): `trading_presenter.py:628-700` ↔ `dashboard_presenter.py:1247-1300`
  (`_run_enable`, `_run_disable`, `_on_enable_trading_completed`,
  `_on_disable_trading_completed`).
- 26 Presenter methods, 26 ViewModel members and 7 View fragments are duplicated between
  `trading` and `dashboard`/`dev_board_panel`.
- The `LiveOrderBookCoordinator` docstring **admits it outright**: `EPIC-023A` needed
  identical behaviour on the Dev Board and *"copy-pasted all six methods plus the two
  backing dicts"*.

This disease has already produced real bugs, and the repository's boards record them in
full:

| Record | Symptom | Structural cause |
| :--- | :--- | :--- |
| `BUG-117` | PnL in the Positions table froze; the first fix proposed placing a `QTimer` in **each** Presenter | No module **owns** the "open positions" read-model, so every screen keeps its own copy |
| `BUG-112` | "Enable trading" required a strategy to be loaded — a genuine UX deadlock | The **Trading** context depends on the *state* of the **Strategy** context |
| `BOT-126` / `BUG-085` | Two screens fight over one live stream; `stop()` on one screen kills the other's stream | Nobody owns the stream subscription |
| `EPIC-023A` | Dev Board copied 6 methods + 2 dicts from Trading | No ownership boundary exists |
| `BOT-128` / `BOT-129` | Table lost columns / screen got squeezed — had to be fixed **generally** rather than patched screen by screen | Shared UI is one flat heap that nobody owns |

(A *read-model*, above, is a flat, display-ready projection that one part of the system
publishes so that others need never touch its entities.)

**Thesis:** the app **already has** a Microkernel — a small core that knows nothing about
concrete features and loads them as plugins — but only for *screens* (`EPIC-016`, complete),
and it has only *one* enormous service module (`BinanceBotModule`, 750 lines). What is
missing is **vertical ownership (a bounded context)**, not a plugin mechanism.

## 3. Why This Is Not "Rearranging Folders to Look Nice"

The context boundaries in this app are **real**, and the current code has **already been
forced** to keep two separate types for the same word:

- `domain/trading/live_position.py::LivePosition` — a snapshot **reported by the exchange**,
  read-only; its docstring says *"this app never computes any of its fields, only parses
  them off the wire"*.
- `domain/backtesting/paper_exchange.py::_OpenPosition` — **simulated** bookkeeping,
  mutated by the app itself on every tick.

These two `Position`s differ in **meaning, lifecycle, and who is allowed to change them**.
That is precisely the definition of two bounded contexts — and the app has paid the price
for them *before* it had a name for them. The same holds for `Order` (a real order versus a
simulated fill) and `Candle` (market data versus a model to draw).

Further evidence: `application/use_cases/` **has** grouped itself by context for a long time
— `trading/`(27), `backtest/`(15), `sync/`(8), `stream/`(6), `database/`(9) — with only
`queries/`(31) and `commands/`(3) still grouped by *technical kind*. The `domain/` layer is
the opposite: only `trading/`(13) and `backtesting/`(12) have the shape of a context; the
market-data concept is scattered across `entities/market_data.py`,
`value_objects/timeframe.py`, `value_objects/market_data_venue.py`,
`models/data_gap.py`, `events/market_tick_event.py` — there is **no** `market_data/`
package.

Put differently: **the app has already grown context boundaries in its lower half, and has
none in its upper half.** This proposal finishes the job; it invents nothing.

## 4. Proposed Decisions

### 4.1. Three Kinds of Unit, Not One

The original sketch had two compartments (`modules/` + `core/`). With only two, `core/`
swells: `chart_card` (27 files), `kit/style.py` (673 lines), health, the log viewer,
config… are all "shared". The proposal is **three kinds, each with its own rule**:

1. **Bounded Context Module** (`modules/`) — has its own business language, owns its own
   data, and has entities and rules that nowhere else **may** modify.
2. **Support Module** (`support/`) — a **technical** capability used by several contexts,
   with **no** business language. It still has a `contracts/` directory, but business
   rules are forbidden inside it.
3. **Kernel Service** — cross-cutting, **injected** into modules, **never** a module itself:
   the DI container, the event bus, config, logging, the thread manager, navigation,
   diagnostics/health.

> ⚠️ **Do not reuse the term "Shared Kernel"** for `core/`. In this repository,
> `architecture-rule.md` already defines Shared Kernel as **exactly 2 symbols**
> (`IDomainEvent`, `BaseEvent`). Reusing the term for a different meaning would break a
> rule that a test currently locks down. Proposed names: `core/contracts/` (kernel
> contracts) and `core/vo/` (language-neutral value objects: `Symbol`, `TimeFrame`,
> `OrderSide`).

The rule for entering `core/`: **nothing enters until it has ≥2 consumers in 2 different
modules** — the same spirit as `architecture-rule.md` §6.3 (*"promote when a second
consumer actually appears — never before"*), with a guard test that blocks `core/` from
importing `modules/*`.

### 4.3. A Module Is an Engine `IExtension` — **No** New `IModule`

The original sketch proposed an `IModule` contract. **The proposal is to drop it**, because
the Engine already has `IExtension`, and the Engine itself calls `IModule` *legacy*. A third
`IModule` would be a **third coexisting notion of "module"** (`IExtension` + the legacy
`IModule` + `AbstractScreenModule`) — exactly the kind of "bad design" the user's criterion
wants to avoid.

Instead, each bounded context module is **one `IExtension`**, plus three UI hooks that the
app defines itself (the Engine has none yet):

```python
class BoundedContextModule(IExtension[IEngineContext], ABC):
    """module_id is a PUBLIC CONTRACT: it appears in routes, in persisted ui_state,
    in event names. Renaming it is a breaking change and requires a state migration."""
    module_id: str
    descriptor: ExtensionDescriptor          # dependencies=("market_data",) -> the Engine topo-sorts

    # --- already in the Engine ---
    def register(self, ctx) -> None: ...     # ONLY declares DI. No resolve, no I/O, no Qt.
    def boot(self, ctx) -> None: ...         # after EVERY module has registered -> may resolve
    def shutdown(self, ctx) -> None: ...

    # --- added by the app ---
    def contribute(self, reg: IContributionRegistry) -> None: ...  # screen, nav item, settings section, overlay...
    def subscribe(self, bridge: QtEventBridge) -> None: ...        # the module's own subscriptions
```

Three rules turn this from a formal contract into a working one:

1. **`register()` must not `resolve()`** → load order cannot affect the outcome. The entire
   class of bugs "A loaded before B, so the resolve returned `None`" disappears.
2. **Dependencies are declared through `ExtensionDescriptor.dependencies`**, and may point
   only at the `module_id` of a module whose `contracts/` one actually uses — the Engine
   already fails fast on cycles.
3. **A module must be constructible without Qt** → the `domain/` + `application/` layers
   can be tested without an event loop (the original sketch's "independent testability"
   criterion); a guard test blocks `PySide6` in those two layers.

A measured risk worth recording: `StdLibContainer.singleton()/bind()` **overwrites
silently** — there is no `try_bind`, and no detection of two modules claiming the same
abstract. A `registrations()`-based check is needed in `boot()` (the Engine already exposes
`registrations()`).

### 4.4. How Modules Talk to Each Other — Exactly Two Runtime Channels

The original sketch said "the shell or the event bus". An event bus alone **cannot solve
request/response** (`backtesting` **needs an answer** to "give me klines"). The
classification is made explicit, and there are **only two channels**:

| Channel | Use when | Mechanism (already available) | Example |
| :--- | :--- | :--- | :--- |
| **Domain event** (notify, fire-and-forget) | "X has happened", many listeners | `IEventPublisher` → bus; listen through `QtEventBridge` | `OrderFilled`, `PositionChanged`, `MarketTick` |
| **Contract port** (request/response, synchronous) | A needs a **result** from B | An ABC in `modules/B/contracts/`, dispatched through `ICommandDispatcher` (CQRS — every request travels as a named command or query object) | `backtesting` → `market_data.contracts.IHistoricalKlines` |

A third channel is **not a runtime channel**: the **read-model DTO** — when A needs to
*display* B's data, B publishes a flat DTO in its `contracts/`; A never touches B's
entities.

This matches the existing `architecture-rule.md` §6 exactly (*"truth của HỆ THỐNG hoặc cần
bởi ≥2 screen → Event Bus + đúng 1 Feed normalizing"* — "truth of the SYSTEM, or needed by
≥2 screens → Event Bus + exactly 1 normalizing Feed") — it only adds that the Feed in
question **belongs to the module that owns the context**, not to `ui/common/`.

**The FORBIDDEN list (enforced by guard tests):**
- `modules/X` importing `modules/Y/{domain,application,adapters,presentation,ui}/**`;
- importing another module's internal QML component;
- using another module's repository or DB session (the SQLite file is shared, but **each
  module owns its own schema namespace**);
- X subscribing to an **internal** event of Y (an event not in `contracts/` does not exist
  as far as the outside world is concerned).

The only public surface of each module is **`modules/X/contracts/`** — ABCs + DTOs + event
types. Everything else is internal.

### 4.5. Contribution Points — the Missing Piece of Idea 2

Navigation only solves "open another module's screen". But this app has four places where a
module must **contribute** into the surface of the shell or of another module *without
either side knowing the other* — the exact mechanism VS Code extensions use. A
*contribution point* is a named slot a host declares and any module fills by registration,
so the host renders content it never imported.

| Contribution point | Who contributes | Who renders |
| :--- | :--- | :--- |
| Screen + nav item | every module | the shell (`ScreenRegistry` — **exists**; only the hard-coded tuple needs to go) |
| Settings section | `trading` (venue, limits, credentials), `market_data` (venue, DB directory), `ui_kit` (font/theme) | the Settings surface in the shell |
| Chart overlay / indicator | `strategy`, `support/indicators` | `support/charting` |
| Status/health tile, environment banner | every module | the shell console (replacing the global hook `set_environment_banner_factory`) |

Without this mechanism the Settings screen would be forced to import the config of **every**
module — recreating exactly the coupling we are removing.

### 4.6. Dev Board and Trading Become **Surfaces**, Not Modules

> **Settled 2026-09-11 (user):** Trading = the real use-case screen; Dev Board = a developer
> screen for testing and **exploring the API** (*"khi dev nếu API nào của sàn chưa rõ thì tạo
> 1 UI để test API đó"* — "during development, if some exchange API is unclear, build a UI to
> test that API"). Both are surfaces; the Dev Board is gated by `dev.mode`, and a
> **`dev_probe`** contribution point is added — HLD §4.3–§4.4.

This is the direct answer to the 59 duplicates measured in section 1.

Today `trading` and `dashboard` (the Dev Board) are **two screens** that each rebuild the
same business behaviour. In the new design both are **composition surfaces** at the shell
layer: they *lay out* the widgets and read-models that `modules/trading` /
`modules/strategy` / `support/charting` **contribute** — they contain no business logic.
The consequence: exactly **one** `_run_enable`, **one** `LiveOrderBookCoordinator`, one
owner of the positions read-model (the thing `BUG-117` was missing).

### 4.7. Keeping the Split from Rotting — Enforcement

This repository has already proven that a rule only survives when a guard test — a test that
inspects the source tree rather than behaviour — enforces it
(`test_quick_widget_only_in_embed.py`, `test_only_the_session_factory_constructs_binance_client.py`,
`test_one_event_is_not_subscribed_by_two_presenters.py`). **Three guards** are needed,
written with `ast` — **not regex** (the lesson of `BOT-133`: the first regex version went red
on the API's own *documentation*):

1. `test_module_boundaries.py` — `modules/X` may import only `modules/Y/contracts/**`. It
   carries an **allowlist that may only shrink, never grow** (a ratchet) — the same idea as
   the baseline-gated `mypy` gate already in use.
2. `test_module_domain_is_qt_free.py` — no `PySide6` inside `modules/*/{domain,application}`.
3. `test_core_has_no_module_imports.py` — `core/` does not import `modules/*`.

The sanity tier **gains no new tests** (`testing-rule.md` §1: *"Adding a feature/screen adds
zero new tests to `tests/sanity/`"*) — sanity already scans "every navigable route, every
screen package on disk"; the new registry fits into that as it stands.

## 5. Three Places Where the Original Idea Should Be **CORRECTED**

### 5.1. The Shell **Cannot** Be a QML `ApplicationWindow` + `StackView`

The original PlantUML placed the shell in QML. This is a hard constraint, settled **twice**
and written into the rules: `qml-rule.md` §0 — *"**QML can be nested inside QtWidgets. Qt
does not support the reverse.**"* → *"**Shell** (`main_window.py`, `QStackedWidget`,
`Sidebar`) — **QtWidgets forever**. **Chart** — **QtWidgets forever**"*; and `EPIC-015` §1
settled that *"shell + chart pyqtgraph ở lại QtWidgets **vĩnh viễn**"* ("shell + pyqtgraph
chart stay in QtWidgets **permanently**"). `chart_card` is 27 files / ~4,000 lines of
pyqtgraph — it cannot live inside a `StackView`.

→ **Proposal:** the shell stays QtWidgets; `StackView` → `QStackedWidget` (already there, via
`PresenterManager`); the navigation target is **a screen factory that returns a widget**; a
QML screen is simply a widget wrapped by `QuickSurface`. **Everything else in the original
design stays 100% as it was** — a microkernel does not require the shell to be QML.

### 5.2. `IModule` → Use the Existing `IExtension` (Section 4.3)

### 5.3. "Each Module Owns Its Own QML" — Right Direction, but **Currently Conflicts with a Rule and Lacks Infrastructure**

Two measured problems:

1. **Rule conflict:** `qml-rule.md` §0.2/§1 fixes `src/presentation/ui/qml/` as the
   *"official place"* and *"1 QML widget = 1 directory"*.
2. **Missing infrastructure:** **there is no `QQmlApplicationEngine`** in either repository —
   every `QQuickWidget` creates its own `QQmlEngine` inside `create_quick_widget()`, and
   there is only **one** hard-coded import path, for the Engine's `Sagittarius/UI`. The app
   **has no `qmldir`** and no `qmlRegisterType`. So the `register_qml_types(engine)` of the
   original sketch **has no engine to register into**.

→ **Proposal: split it in two.** QML *specific to one module* moves to `modules/X/ui/`; QML
that is *shared* stays in `support/ui_kit`. To do that we must: (a) **explicitly amend**
`qml-rule.md` §0.2 (following the `EPIC-003` precedent: when a proposal contradicts a rule,
**update the rule file**, never quietly ignore it); (b) add a per-module import-path
mechanism to `QuickSurface` (each module declares its QML root, and `QuickSurface` adds it
to the engine of the `QQuickWidget` it builds). This is an item that **may have to be done
on the Engine side** — exactly as the user predicted.

## 6. What Must Be Done on the Engine Side — and the Good News

The Engine's `ui-architecture.md`, §1, ownership table: **"Runtime | Engine owns: Shell,
regions, navigation, screen lifecycle"**. By the Engine's own rule, then, a
`NavigationService` **belongs to the Engine**, not to the app.

And the Engine **already has an epic for exactly this**: `EPIC-001D — Runtime, Regions & Slot
Registry` (🔵 Backlog, P2, dependencies satisfied). Its stated goals:

- the shell owns chrome, navigation, the overlay host and named regions;
- a registry that screens **contribute** into;
- a unified screen lifecycle (`mount`/`unmount`/`ui_mode`/`shutdown`) plus a conformance suite;
- **"Navigation derived from screen self-description, not wired by hand"**;
- *"Decided 2026-08-23: the UI Engine's own runtime lifecycle becomes a real `IExtension`"*;
- and it **records the very gap itself**: *"the UI Engine has **no connection at all** to
  Sagittarius Engine's own extension system … `pyside_mvc` implements `IExtension`/`IModule`
  nowhere (grep confirms zero matches)"*.

→ **Conclusion:** the Engine half of idea 2 **has been planned since 2026-08-23**. This
proposal **must not build a parallel version** — it must coordinate:

| Belongs to the Engine (`EPIC-001D`) | Belongs to the app (proposed `EPIC-025`) |
| :--- | :--- |
| `NavigationService` / region / slot registry, screen lifecycle + conformance suite | 4 bounded context modules + `support/*` + `core/contracts` |
| Per-module QML import path for `QuickSurface` (if 5.3 is settled) | `IContributionRegistry` (settings section, chart overlay, status tile) — **app policy** |
| The UI runtime as a real `IExtension` | The concrete route table, 3 boundary guard tests |

The dividing principle: **the Engine takes the *mechanism*, the app keeps the *policy*.**

An operational risk already checked: the app **does not pin** `sagittarius-engine` (it is
absent from `requirements.txt`/`pyproject.toml`) — so a new Engine API reaches the app
through a reinstall plus `EngineCapabilityValidatorExtension` (which currently declares
**1** capability). Every Engine API this step needs must be added to
`engine_capabilities.py`, using the mechanism `BOT-133` built.

## 7. Migration — Strangler Fig, the App Runs at Every Step

A *strangler fig* migration grows the new structure around the old one and moves
responsibilities across piece by piece, so the old code shrinks until it can be removed while
the system keeps running throughout. No big bang here. **Not out of fear of technical risk**
(the user has said they are not afraid of it), but because this app runs for real with
Testnet money every day, and the most effective bug-discovery channel we have today is
precisely *the user running it and sending real logs* (`BUG-111` → `BUG-117` all came from
it). Losing the ability to run for one week means losing that channel.

| Phase | Content | Done when |
| :-: | :--- | :--- |
| 0 | The mechanism (`core/`, `shell/`, `BoundedContextModule`, `IContributionRegistry`, 3 guards with **allowlist = current state**, `support/binance_gateway`) **+ `modules/market_data`** — a Walking Skeleton: the thinnest context that touches every channel | Data Management + the CLI run through the module; the allowlist shrinks by the market_data part |
| 1 | `modules/trading`; Trading + Dev Board become **surfaces**; the first `dev_probe` | **59 → 0** duplicates; the user runs Testnet exactly as before |
| 2 | `modules/strategy` (Core); `claim_symbol`; `StrategyContext` pointing the right way | arm/disarm/tick → order |
| 3 | `modules/backtesting`; an ACL around `PaperExchange`; delete dead use cases | backtest bit-identical |
| 4 | `support/{charting,indicators,ui_kit}`; delete `ui/common/` and `binance_bot_module.py`; settings = surface | allowlist **empty** |
| 5 | Engine `EPIC-001D`/`TASK-043`: `NavigationService`, regions, conformance suite | `main_window.py` imports no screen |

(A *Walking Skeleton* is the smallest end-to-end slice that exercises every architectural
seam; an *ACL*, anti-corruption layer, is a translation layer that keeps one context's model
out of another's.)

> This order **differs** from the first draft (market_data → backtesting → strategy →
> trading): the user delegated the decision to doctrine; the reason for the change is
> recorded in ADR D5 — `trading` comes right after the skeleton because that is where the 59
> duplicates and the real bugs (`BUG-111`→`117`) are arising; `backtesting` moves back
> because it has the fewest wires and is the largest.

Each phase = 1 PR, CI green, the app runnable. **The allowlist only shrinks** → progress
cannot go backwards.

This order also satisfies the condition set by `EPIC-024C` (*"không đảo thứ tự B/C:
modularize trước khi có consumer thật là thiết kế đoán mò"* — "do not invert the B/C order:
modularizing before a real consumer exists is guesswork design"): the real consumer already
exists — `EPIC-024B` (manual order placement) **has its code merged** (PR #184/#193) even
though its status line on the board still says 🔴 (exactly the warning of `ONBOARDING.md`
§12.2: *"trạng thái trong task file có thể cũ hơn code"* — "the status in a task file can be
older than the code"). The proposal is to close line `B` before opening `EPIC-025`.

## 8. Relationship to `EPIC-024C`

`EPIC-024C_modularize_trading_core.md` §2 states the thesis of this proposal precisely:
*"Không có khái niệm 'module' cho service phía sau UI trong toàn bộ app —
`BinanceBotModule` (656 dòng) là nơi đăng ký DUY NHẤT cho mọi thứ… **mẫu để chép là
`AbstractScreenModule`**"* ("There is no notion of a 'module' for services behind the UI
anywhere in the app — `BinanceBotModule` (656 lines) is the ONLY registration point for
everything… **the template to copy is `AbstractScreenModule`**").

→ **Proposal: `EPIC-024C` is absorbed by `PRO-004`/`EPIC-025`** (`EPIC-024C` moves to
`cancelled/` with the reason written out — this repository does not delete cancelled tasks),
because:
- the scope of 024C (3 modules: Market Connector / Market Order / Strategy Engine) is a
  **subset** of the map in section 4.2;
- doing 024C on its own would build the module mechanism a **first time** for services, and
  then `EPIC-025` would build it a **second time** for the whole app — exactly the kind of
  duplicated mechanism that `ONBOARDING.md` §12.5.1 (*"luôn chọn general solution"* —
  "always choose the general solution") forbids.

## 9. Alternatives Considered and Rejected

| Alternative | Why rejected |
| :--- | :--- |
| Keep layer-first; remove the 59 duplicates only by promoting them into `ui/common/` | That is **exactly** how the 9 current items got into `ui/common/`, and they still have only 2 consumers. Without an owner, duplicate number 60 will happen anyway. It is a hot fix in the sense of `bug-fix-rule.md` §2 |
| Create a base class `TradingScreenPresenter` for Trading + Dev Board | **`EPIC-019` §3 has already rejected this option**: *"đi ngược hướng composition-qua-Coordinator đã chốt từ `EPIC-003`/`EPIC-013`"* ("goes against the composition-through-Coordinator direction settled since `EPIC-003`/`EPIC-013`"); a thick base class *"lặp lại đúng sai lầm God Presenter"* ("repeats the very God Presenter mistake") |
| Big bang: build the new `modules/` and port everything in 1 PR | ~3,900 tests mirror the old layout; the app would be unrunnable for many days → the most effective real-bug discovery channel is lost |
| Write our own `IModule` + `ModuleRegistry` + `NavigationService` on the app side | The Engine already has `IExtension` + `ExtensionManager` (topo-sort, fail-fast on cycles, rollback), and `ui-architecture.md` §1 settles that navigation **belongs to the Engine**. Writing our own = a third notion of module + an ownership dispute with `EPIC-001D` |
| One DB / one process per module (microservices) | No real need; the SQLite shards are shared today. "Can be split out later" is a **design property**, not a deployment plan (section 11) |

| Risk | Level | Mitigation |
| :--- | :--- | :--- |
| `TradingSessionState` is mutable state shared by 3 Presenters (`trading:234`, `settings:143`, `dashboard:534`) + 3 handlers + the websocket thread | 🔴 | Do it last, in Phase 4; `modules/trading` owns it, and the outside reads only through a contract/read-model |
| `binance_bot_module.py` (750 lines) becomes a new god file if it is not dissolved | 🟠 | Each module does its own `register()`; this file withers into a **list of modules** |
| ~3,900 tests mirror the old layout → an enormous diff | 🟠 | Tests move **together with** their module, phase by phase; **section 12, question 3** needs the user's decision: colocate `modules/X/tests/` or keep the `tests/` mirror |
| Ownership dispute with `EPIC-001D` on the Engine side | 🟠 | Settle the split table in section 6 **before** coding; every new Engine API goes into `engine_capabilities.py` |
| DI overwrites silently when 2 modules claim the same abstract | 🟡 | Check through `registrations()` in `boot()` (the Engine already exposes it) |
| `qml-rule.md` §0.2 must be amended | 🟡 | Amend explicitly, following the `EPIC-003` precedent; never quietly ignore |
| Effort estimate | — | **Not yet accurate.** 6 phases (0–5), one PR each; only phase 0 can be estimated (building the mechanism + 3 guards, no migration) |

## 11. Anti-Goals (Deliberately NOT Doing)

- No microservices / no multi-process. "Can be split out later" is a **design property**.
- No hot-reloading of modules.
- No plugin API for third parties (every module is first-party) → no need for public
  semver-style contract versioning.
- No 1 DB per module (SQLite stays shared; each module owns a **schema namespace**).
- **No change of business behaviour during the migration.** Pure refactoring — the
  constraint `EPIC-024C` §4 already set: *"modularize là đổi ranh giới code, không đổi logic
  nghiệp vụ"* ("modularizing changes code boundaries, not business logic").
- No turning Coordinators into DI-discovered things: `async-ui-action-rule.md` §2 forbids a
  Coordinator that *"resolves its own container or is independently discoverable/DI-registered"*.
  Modules register; a Coordinator is still owned by its Presenter and injected through the
  constructor.
