# ADR — `bot apply` beside a running host is the same plan, carried out entry by entry through the command directory

**Epic:** [EPIC-045](README.md)
**Date:** 2026-10-22
**Status:** Accepted
**Decided by:** the owner for the slice itself (D5 of [the add and delete record](DECISION_2026-10-21_add_and_delete_on_the_running_host.md): "bot apply nằm cạnh bot add", and the rule that whatever the Bots tab does at runtime the host does too); the author session for the design below under ONBOARDING §7, on the points the coordinator listed (document size, partial results, the applied-plan record, coexistence with `bot add`, prune), each reversible and touching no real money, dependency, setting or Engine file

## 1. Context
- ✅ `bot apply plan.json [--prune]` reads a plan, compares it with the stored bots (identity: `name` + `venue`) and carries out each change through the Bots tab's own commands: `CreateBotCommand`, `EditBotCommand`, `DeleteBotCommand` (`src/modules/bots/application/plan/plan_applier.py` → `PlanApplier`). It then rewrites the applied-plan record `state/bot_plan.json` (per bot id: name, venue, desired state) from the entries that now match the plan; `run --start-planned` reads only that record.
- ✅ Beside a running host the second process is a read-only copy of the data root: it exited `3` (before C) when `apply` would change bots (`src/modules/bots/cli/bot_plan_verbs.py` → `ApplyBotPlanVerb.run`), and `--dry-run` works there (it only reads).
- ✅ The host already takes `add` (create one DRAFT from a plan entry), `edit`, `delete` (with its exposure refusal) and `move` from `state/control/`. A command file is one JSON document of at most 4096 bytes (`MAX_COMMAND_BYTES`), strictly shaped (`host_command_codec.py`, `host_command_rules.py`), audited and replay-protected.
- ✅ An entry's `params` that `add` carries are bounded (`MAX_SETTINGS_PER_EDIT` settings); `add` is create-only, refuses a duplicate identity and records no desired state.
- 🟢 The owner, 2026-10-21: "bot apply nằm cạnh bot add" (apply sits beside add, not in place of it) and "whatever the UI can do at runtime, the VPS must be able to do".
- ✅ The coordinator's brief for this slice: split or single document, an honest per-entry result with no all-or-nothing pretence, a mainnet start never implicit, the applied-plan record coherent with `--start-planned`, coexistence with `bot add`, and `--prune` on a running host for bots at rest only, reusing the delete refusals.

## 2. Decisions
| # | Decision | Status | Decided by | Consequence |
| :-- | :--- | :--- | :--- | :--- |
| C1 | `bot apply` is one verb that works in both situations. With the data root's lock free it is the offline apply it is today. When a host holds the lock it no longer exits `3`: it computes the same diff (read-only, as `--dry-run`) and **carries it out through the command directory**, one command per change, waiting for the host's answer to each. `--dry-run` is unchanged. | Accepted | 🤖 agent | The operator types the same command whether the host runs or not; nothing about a plan file changes. |
| C2 | **Split per entry, never one document.** A plan of any size becomes N small command files, each inside the 4096-byte limit; no document ever carries the whole plan. The plan is validated whole **before the first command is sent** (parse, the entry bounds `add` already enforces, the entry count), so a plan that cannot be carried is refused with nothing changed. | Accepted | 🤖 agent | No plan-size ceiling beyond the entry bounds; a malformed plan changes nothing. |
| C3 | A new action `apply-entry` carries one plan entry (the existing `entry` key) and its `desired_state` (one new optional key, a closed word: `running` or `stopped`), with `bot_id` the fixed word `plan`. The host handler runs the **same `PlanApplier`** on a plan of that one entry under `BotCommandLock`: no bot of that identity → the tab's `CreateBotCommand` (DRAFT); one that differs → the tab's `EditBotCommand` (full parameters, as offline); one that matches → nothing; a bot the lifecycle table does not allow to be edited → the same `BLOCKED` "needs stop first" the offline apply prints. It then upserts that bot's row in the applied-plan record. | Accepted | 🤖 agent | The create/edit logic is not forked (P3/P5): offline and beside a host are one code path, and the answer for an entry is the offline answer in the same words. |
| C4 | **Partial results are per entry and honest.** The sequence is plan order, creates and edits first, deletes last. A refusal of one entry (blocked, refused by the bot's command, bad value) never stops the others, exactly as offline. The report lists every change with the host's sentence for it, and anything **not sent** because the host stopped answering is listed as not sent, never as done. Exit `0` all done or nothing to do; `2` an entry needs attention; `10` no host is running and `5` the running copy takes no commands (both before anything was written, so nothing changed), `11` the host stopped answering, as every host verb. A host that goes away mid-plan leaves the earlier entries applied and says so. A command the host **took** but recorded no outcome for may still have run, so it is reported "sent, outcome unknown", never as not sent or unchanged. | Accepted | 🤖 agent | The plan is not all-or-nothing and is never reported as if it were; re-running the same plan is safe because every command is idempotent in outcome (C3). |
| C5 | **`apply` never starts a bot and never places or cancels an order.** A created bot is DRAFT; an edited bot goes through the edit lifecycle; a recorded `running` desired state is a wish that only `run --start-planned` (and its mainnet confirmation, decision D7 of the add record) or `bot start` acts on. | Accepted | 🤖 agent | A mainnet start is never implicit; the real-money questions stay at `bot start --confirm-venue`. |
| C6 | **The applied-plan record stays what an offline apply would have left.** Offline, the record is rewritten from the plan: a row for each entry that now matches, none for any other bot. Beside a host: `apply-entry` upserts the row of its entry; a new action `unplan` (`bot_id` the bot's id) removes the row of a bot the plan does not name; the host's `delete` also removes the deleted bot's row. The client sends `unplan` for every recorded row whose bot the plan does not name and `apply-entry` for every plan entry, so after a complete run the record equals the offline one. A run cut short leaves the rows of the entries that were applied and the old rows of those that were not: a row is only ever written for a bot that matches what was applied. | Accepted | 🤖 agent | `run --start-planned` and `state/bot_plan.json` stay coherent: a bot is never started on a wish whose parameters were not applied. The record has one writer, the host. |
| C7 | **Coexistence with `bot add`.** `add` stays as it is: create-only, strict on a duplicate, records no wish. `apply-entry` is the declarative upsert and records the wish. An entry added by `bot add` and later named by a plan is matched by identity and edited or left, never duplicated. | Accepted | 🤖 agent | The owner's D5 stands: `apply` beside `add`, neither replaces the other. |
| C8 | **`--prune` on a running host deletes only bots at rest.** The unnamed bots the diff says `DELETE` are sent as `delete` commands, which the host judges again at the moment it runs (the lifecycle table, and the exposure refusal of decision D4 of the add record: a held base worth the dust figure or more, a live order, an order owed). A bot that is not at rest, or that holds exposure, is `BLOCKED` in the report, not an error of the run. | Accepted | 🤖 agent | Prune reuses the delete refusals; it cannot orphan an order. |
| C9 | `desired_state` and `plan` are the only new document vocabulary: two action words (`apply-entry`, `unplan`), one new key (`desired_state`), one new subject word (`plan`). Each is shaped strictly in `host_command_rules.py` and refused on every other action; an older host reads them as malformed and changes nothing. | Accepted | 🤖 agent | The trust boundary does not widen beyond what `add` already carries plus one closed word. |

## 3. Alternatives considered
- **One command carrying the whole plan:** rejected. A plan outgrows 4096 bytes at about a dozen bots, so it would silently cap plan size or force a raise of the limit on the trust boundary; and one document makes partial results awkward (a host crash mid-document leaves no per-entry account).
- **A multi-command session (begin, entries, commit) with the host assembling the plan:** rejected. It needs host-side state across command files (a half-assembled plan to expire, to recover and to audit), which is exactly the all-or-nothing pretence the brief forbids, for a plan small enough to send entry by entry.
- **The client composes `add`/`edit`/`delete` from its own diff and the host trusts it:** rejected for create and edit. `edit` merges settings (it cannot drop a parameter) and `add` records no wish, so the result would differ from an offline apply; and the diff the client saw may be stale by the time the command runs. The host re-judges each entry at the moment it runs (C3). `delete` keeps the client's choice of bot because the host judges it again (C8).
- **Let the client write `state/bot_plan.json`:** rejected; the host owns the data root and a second writer is the failure its lock exists for.
- **Keep the exit `3` and tell the operator to stop the host:** rejected; it is the very restart (every RUNNING bot through RECOVERING and a manual resume) the owner's rule removes.
