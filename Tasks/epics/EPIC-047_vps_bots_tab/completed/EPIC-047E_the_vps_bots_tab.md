## 1. Context and problem
The owner added a rule on 2026-10-27: in the VPS tab all Binance data comes through the VPS and the app connects to nothing at Binance. Today the detail and the chart reach Binance through the desktop's own container (the table in the [decision record](../DECISION_2026-10-27_a_vps_bot_reaches_binance_only_through_the_vps.md)'s §1), so 048B's second pull request, which removes the container reach, and 047H, which gives the host the missing sources, are both prerequisites. Until 047H lands, this task may build everything that reads no market data and no refreshed facts (the connection line, the commands, the list and the detail from the bot files and the host-facts file).

After EPIC-048B the Bots screen receives host facts through queries and events only, and the pure assessment runs on the desktop. A remote dispatcher and event stream over the transport of 047D can therefore stand behind the same screen. De-risk R1 rendered the real view from six wire-borne reads with the detail equal to the in-process one. The owner's pain (charter §1.2): the VPS is read through SSH text, plans reach it by export, `scp` and `M bot add`, and the desktop and the VPS read different exchange accounts.

## Implementation notes (written when done)
### PR 1 — the remote backend behind the doors (in review)
**Reuse (`capabilities.md`):** `ICommandDispatcher` (used: a second implementation, the screen is untouched), `IHostControl` (used: the link implements it), `LinkSupervisor` / `ILinkObserver` / `RevisionGate` (used: 047D), `MemoryEventBus` (used as the tab's private bus), `ICandleFeed` (a second implementation), the handlers' own pure functions (`venue_choices_of`, `plan_risk_of`, `host_run_facts`, extracted from the handlers so the host and the desktop run one rule), `occupancy_of`, `export_plan`. Nothing in `ui/` changed.

**Where it lives, and why.** The bots-specific part is `modules/bots/adapters/remote_host/` (it names the queries and commands); the part that needs the transport and the operations documents is `shell/vps_link/`, because a module may not import `support/wire/desk` and `operations` is imported by the shell alone. They meet at two ports in `bots/contracts/`: `IHostWorld` (what the host last published) and `IHostControl` (`core/`). The decoded `BotList` reaches the shell through `bots/link.py` → `decoded_bot_list`, as `BotList` is an application result.

**Decisions (agent, under the Constitution; the coordinator may veto):**
1. *Answers from a value, not from a service.* `RemoteQueries.answer` is a function of one immutable `HostWorld`; the dispatcher never waits on the link for a read, so the screen's pool is never held by a slow VPS.
2. *A gap is a sentence.* A fact the host never published is `NOT_PUBLISHED_BY_THE_HOST` in the problem field the screen already shows; the Run facts have no honest default (the caps), so that read fails and Start keeps waiting (`NotPublishedError`), as the screen does for a failed read.
3. *A Start that carries unsaved edits is refused with "Save the changes first".* The in-process Start saves the edits only if the bot is ready; two host requests cannot promise that, and an edit saved by a Start the host then refuses would change a stored bot the person did not agree to. A rename is refused for the same reason. This changes nothing a command does on the Bots tab; the VPS tab sends less. (Owner may want Save-then-Start in one act; that is a host verb, not this tab.)
4. *The answer to the real-money question travels as the venue typed.* A command that carries `real_money_confirmed` sends `confirmed_venue = the bot's venue`, as `--confirm-venue` does; the host judges it. The tab composition (PR 2) must make the question a typed one (G3, AC4): this slice does not ask anything.
5. *A refusal in the host's words has no `BotRefusal` code.* The wire carries none, and an invented code would claim a reason the host never gave; `refusal` is `None` and the screen shows the words (it reads no code).
6. *Confirm resume names the proposal the screen was shown.* The host's confirmation requires a fingerprint; the Resume reply prints it in words, `proposal_in` reads it (pinned by a test against the host's own sentence), and the dispatcher keeps the last one per bot.
7. *A command lost in flight is `NO_ANSWER`, is never sent again, and blocks another command on the same bot.* Its id is in the `UnansweredLedger` (`IUnansweredCommands`); the dispatcher refuses a new command on that bot (an Add on `new-bot`) with the id in the words, until PR 3's reconcile settles it from the host's audit. Until then the block holds across a reconnect (v1 limit: a person checks `M bot show` / the audit). **Stop and Pause pass the block** (`REDUCES_EXPOSURE`): applied twice they do the same as once, and the control that lowers exposure is never the one withheld. A bot is also held to one command at a time inside the dispatcher (`IN_FLIGHT_WORDS`), so two presses within the host's wait cannot both reach it; the screen's own action tracker serialises its buttons too, but the guarantee does not rest on it.
9. *A host file that is not live is not answered from.* The bridge keeps the last document of a host that stopped writing (`STALE`); `HostWorld` carries each file's `HostFile` (state, age at the look), the queries take a non-live file out and put "the host has not written its facts …, it may have stopped" in the field the screen shows a problem in (the Run facts fail the read, so Start waits), and the line says "host quiet". `last_frame_at` is the last frame of any kind and proves the link only.
10. *Confirm resume carries `real_money_confirmed` like the three other verbs* (a field with a default on `ConfirmBotResumeCommand`; the Bots tab sets it after its question; the in-process handler ignores it), so the host judges the typed venue the same way for all four and a test pins which commands send it.
8. *The Connect step's account snapshot is put together from three published reads* (exchange facts, planner inputs, symbol rules), each with the host's read time; `holdings` is empty because the host publishes the bot's balances and not the account's list, and nothing in `bots` reads it (`SpotHolding` is forbidden in `bots` anyway).

**v1 limits (decisions 3, 5 and 6 settled by the coordinator on 2026-10-28, no veto):** a Start with unsaved edits and a rename are refused in words; a refusal in the host's words carries no invented `BotRefusal`; Confirm resume uses the fingerprint the Resume printed. Each is reversible and changes no threshold or what a command does on the Bots tab.

**Decision (coordinator, 2026-10-28, ONBOARDING §7 default; the owner may veto in their own words): no masked exchange account.** The epic's O5 asked the line to show the account masked ("…1a2b"). The host publishes whether a venue has a key and no part of it (`HostHeldFacts`, 047B); no tail or fragment derived from an API key is published or shown. The line shows what the host already publishes: host, venues with a key saved, connected, data age (`shell/vps_link/host_state_line.py`). Constitution check: P1 a test pins the line's words and the facts carry no key field; P3 no second source of identity; P6 nothing patched, the gap is stated; P7 a tail is one optional field in `HostHeldFacts` and one word in the line, built when asked; P8 no ratchet loosened; it touches a secret, so it stays unbuilt until the owner asks.

**Verification (PR 1).** `tests/unit/shell/vps_link/` runs the real `LinkSupervisor`, `LinkHostWorld` and `LinkHostControl` against the real `BridgeSession` over the bridge tests' fake ports: the picture follows snapshot, events, a cut and the next welcome; every query the screen asks; every command with a host verb reaches the host's door as that verb (checked against the parity table); a disconnected tab answers its last data and sends nothing; a command in flight at a cut is sent once; the chart and ticks come from the host and freeze offline. Mutations checked red: sending while disconnected; confirming the venue on every command; a Binance import in the tab's closure (the static guard found a namespace package the first version of it missed). AC10: `test_the_vps_tab_reaches_no_binance_client.py` (closure of 375 modules, baseline 0) and `test_the_vps_tab_opens_no_connection_to_the_exchange.py` (a clean interpreter loads no exchange client; a whole session opens no socket beyond the loopback, with a control that shows the recorder catches one). Not run: the zero-call test with the Bots tab composed beside it (PR 2), the owner's VPS.

### PR 3a — a lost command is settled from the host's record, and never re-run (merged, #753)
PR 3 is delivered in three pull requests (3a this one, 3b arm and disarm over the host verbs, 3c Add to VPS with the SPEC page, the LEARNING page and the closing of this task).

**Decision (coordinator, 2026-10-28; reversible, reads only, no threshold, no money behaviour, no dependency; the owner may veto).** After a cut, a command whose answer was lost is settled by a question to the host, `outcome_of(request_id)`, answered from the host's audit and control directory (it runs and takes nothing; for an id the host never saw it first appends one **fence** line, added in review round 1: without it "never reached" is true only at one moment, because the old bridge process can still deliver the command's bytes after the new link asked): the tab says "ran" or "did not run" in the host's words, or "never reached the host: send it again if you still want it". **No path re-sends a lost command**, not even Stop or Pause: a lost Start, Edit, Add or Resume must not run minutes later without a fresh answer to the real-money question, and any re-send is a new action of the person under a new request id with a new typed confirmation. Options not taken: (A) re-send the same id, whose host dedup makes it safe against running twice but lets a command that never arrived execute late; (C) auto-resend Stop and Pause only (the owner can ask for it in their own words later). Constitution check: P2 (read the real record, do not infer), P5 (reuse `IHostControlAudit.final_entry_of`, the door's own reply mapping and the bridge's call pattern), P7 (one read-only call, no new machinery), P8 (a test per outcome and a mutation check each), real money untouched.

**The fence (review round 1 of PR 3a, changes "read-only").** The host's audit gains one kind of line, the fence (`EXPIRED`, `FENCE_MESSAGE`), written by the bridge's process; `has_seen` re-reads the file on a miss so the running host honours it. Reversible (a fence only makes an id refuse to run), no money behaviour, no dependency; the coordinator is told in the same report.

**Wire addition (owner and coordinator: desktop and host must be updated together).** One call, `outcome`, on the bridge and one abstract method, `ICommandDoor.outcome_of`. The handshake already refuses a desktop and a host of different builds, so no negotiation was added.

**Reuse (`capabilities.md`):** `IHostControlAudit.final_entry_of` and `DirectoryHostControl`'s reply mapping (the settled entry becomes the same `HostControlReply` a replay gives), `INotifier.notify` (the toast), `UnansweredLedger.settle` (written for this in PR 1), the bridge's read-only call pattern (`serve_candles`).

### PR 3c — Add to VPS, the SPEC, the learning page and the version words (this pull request)
**Reuse (`capabilities.md`):** `ICommandDispatcher` and `ExportBotPlanQuery` (the bot's definition is the one Export plan… writes), `HostControlAction.ADD` and `NewBotEntry` (the host's own `add` verb and wire shape), `LinkHostControl` and `UnansweredLedger` (one request id, never sent twice), `VerbQuestion` and `ask_with_verbs` (the question), `FencedReads` and `UiThreadRelay` (off the UI thread), `INotifier` (the toast and the failure), `bind` of the application container (the handler).

**What it is.** A command of the Bots tab, `AddBotToVpsCommand`, whose handler sends the selected bot's definition to the host as one `add` through a new port `IVpsDelivery` (`bots/contracts/i_vps_delivery.py`). It is not `IHostControl`, which the application binds to the local running host. The shell implements the port over the one VPS link session (`SharedVpsSession`, `VpsDelivery`), which the VPS tab shares.

**Decisions (coordinator may veto; none sets a threshold or changes what a command does with money):**
1. *`add`, not `apply-entry`.* An add only creates (a DRAFT) and the host refuses a name already taken in its words; an apply-entry could also edit an existing bot, and its wish record is for `run --start-planned`. The first is the smaller act and what the charter's Scenario 2 asks for.
2. *No real-money question at Add to VPS.* An add places no order and starts nothing; the typed question belongs to the host's Start in the VPS tab (AC4), where the person sees the host's Checks first. The dialog asks a plain question (Add to VPS / Cancel, Cancel the default) and says nothing starts.
3. *Sending connects the link.* Add to VPS starts the link if the VPS tab was never opened; "a run that never opens the tab makes no connection" still holds for a run that never sends a bot. The first press may find the link not up: the reply says "nothing was sent" and the person presses again.
4. *A reply that never came is never told as a failure to create.* It is told as "may or may not have been created", and nothing is sent again (the AC6 rule).
5. *The menu text is "Add to VPS host…"* because every letter of "Add to VPS" was already another command's access key.
