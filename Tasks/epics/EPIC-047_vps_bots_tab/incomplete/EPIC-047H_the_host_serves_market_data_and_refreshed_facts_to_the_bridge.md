## 1. Context and problem
The VPS tab must connect to nothing at Binance (D1). The decision record's §1 table lists what the detail and the chart read from Binance today and what the host publishes after. Three things have no host source yet: the chart's candles, live candle, last price and mark price; the fills table and the planner's inputs (filters, fees, mid price, daily ATR); the symbol and precision metadata. And the 2026-10-26 D3 left exchange facts as old as the last Start or Resume, which was tolerable only because a desktop screen load re-read them; with the desktop reading nothing, a running bot's facts would age until the next Start. The bridge keeps calling no exchange and loading no key (D2): the host fetches, writes files, and the bridge reads them.

## 2. Acceptance criteria
- [x] **First step, recorded before any code:** every assumption of the "Assumptions to verify" section below is verified as its row says, and the result (value, date, commit, command or log) is written under Implementation notes. The weight table in the decision record §4 and the defaults of D4 are corrected to the measured numbers, and a row that fails reopens the decision it names.
- [x] **The host is the only Binance client.** The recorder reuses the host's existing stream and the mark read each beat already makes; it opens a second Binance connection only if (b) shows the host has none to reuse, and says so in the implementation notes. A test fails if the recorder creates its own exchange client.
- [x] **Market data files (D3).** The host writes the forming candle, last price and mark price for each stored bot's symbol and each published timeframe, owner-only and atomically, at most once a second, with a revision and `heartbeat_s`, on its own daemon thread like `HostFactsPublishing`: a full disk or a slow write delays the file and nothing else. Closed candles are read by the bridge from the host's candle store, read-only. The timeframes are taken from the Bots chart's own list, not copied (P3).
- [x] **Bridge read side.** The bridge turns a change in those files into events with its own per-key revision (the 2026-10-26 D1 rule), and a snapshot first; the wire roots are added to 047A's closed list with a contract test each. A candle window of the chart's size crosses the wire and back equal.
- [x] **Fresh exchange facts (D4).** The host refreshes the facts of each bot with exposure every `vps_facts_refresh_interval_s` (default 120 s, lowest 30 s, 0 = off) and reads static exchange info at start and every 24 h, as `RequestPriority.ROUTINE`, so a refresh waits at the 70 % line and never uses the exit reserve. Both numbers and `vps_facts_weight_ceiling_pct` (default 3, highest 10, enforced in code) are host-profile settings, not constants, changeable without a code change. The ceiling is enforced on the weight the exchange reports (the used-weight header), not on an estimate, and the interval stretches to hold it. A test with a fake clock and a fake exchange proves: the ceiling holds at 1, 5 and 20 bots; a closed gate delays the refresh and does not queue a burst afterwards; a refresh failure leaves the last snapshot and its `read_at` and is logged once per cause.
- [x] **On demand (D4).** A verb through `IHostControl`, judged by the host's gate and audited like the other verbs, refreshes one bot's facts at most once per 30 s, counted inside the ceiling; the answer to a request inside the interval is "already fresh, read at …". The Bots-tab-and-host parity test (`test_the_bots_tab_and_the_host_stay_in_step.py`) lists it.
- [x] **Planner inputs and fills.** The host publishes the planner's inputs (filters, fees, mid price, daily ATR and Bollinger range) and the bot's fills and orders, each with the time it was read; static exchange info (filters, brackets, symbol list) is read at start and once a day.
- [x] **No change to trading.** A test over the composed host proves that with the recorder and the refresher on, the number and order of the exit-guard reads, the placements and the cancels are the same as with them off, and that the recorder never touches a lease, a limit or a key.
- [x] **The bridge still calls no exchange.** 047C's test that the bridge process imports no exchange client and opens no non-loopback connection stays green and is extended to the new read side.
- [ ] **Measured on the owner's VPS**, recorded with its output: the weight actually spent per minute at the real bot count with the used-weight header, the age of a tick and of a facts snapshot seen through the bridge, and the exit reserve untouched. Not run until the owner runs it.
- [x] A fact never published is reported as "not published by the host", not as an empty value (D5).

## 3. Design
The shapes already exist and are mirrored (P5): the facts file and its publisher (047B: atomic owner-only write, revision that grows across restarts, `heartbeat_s`, a daemon thread, failure logged once per cause, readers judge liveness by the host's own cadence); the bot-file revision (2026-10-26 D1); `RecordedVenueFacts` as the place a refresh decorates `IVenueFacts`; `RequestPriority` for the weight reserve. The refresh interval for `n` active bots is `max(60 s, n × measured_weight_per_read / ceiling × 60 s)`. The option tables and the reasons are in the decision record §3; the module's design file under `Docs/MODULES/bots/` and the operations module's description take the new parts when they are built.

### Built, and where it differs from the plan (2026-10-27)
Every criterion is built and proved on the composed host over the fake exchange, except the VPS measurement (owner steps above). Proofs: the weight ceiling (`tests/unit/modules/operations/vps_feed/test_the_weight_ceiling_holds.py`: a simulated three hours; the most spent in any minute was 55, 70, 70 of 72 at 1, 5, 20 bots), the exit reserve (`tests/unit/modules/trading/adapters/binance/test_the_weight_meter_and_the_exit_reserve.py` and `tests/integration/modules/bots/test_the_host_serves_the_vps_tab_on_the_fake_exchange.py`), reads only and no connection from the bridge (`tests/unit/architecture/test_the_vps_feed_reads_only_and_opens_no_connection.py`), the bridge read side (`tests/integration/modules/operations/test_the_bridge_serves_the_vps_tab_its_data.py`). New files: `state/market-data.json`, `state/host-reads.json`; new setting keys and the verb `bot refresh-facts` (`Docs/OPERATIONS/headless_runbook.md`).

Deviations the reviewer and the owner should read:
- The host streams the **1m kline only**; longer timeframes are folded from it, and a candle is `complete=false` after a start until it closes.
- **Candle backfill** uses `market_data`'s own REST client, outside `ExchangeCallPolicy`, so it is charged by estimate (50 per symbol sync, at most one per symbol per 300 s), not by the header.
- Cold facts read 81, warm 20, planner 25, fills 10 per window (A5): planning weights and a median cost model follow.
- Fills and planner ride every fifth round and on demand; the facts every round. The first facts read after a start waits 20 s.
- The **symbol list is not published** (no enumeration port; D6 means no symbol edits in v1).
- A bot has "exposure" when its state is anything but DRAFT or STOPPED.
- The bridge reads closed candles from the host's WAL store `mode=ro` through plain `sqlite3`; the wire codec reaches `support/wire` through the new `IWireCodec` port registered by the shell.
- The feed runs in the headless host only: the GUI entry point sets `operations.vps_feed_enabled` off for its run (review round 1), so a desktop spends no weight on its own IP for files it never reads.
- A read that raises is charged and paced as a failed read; a kind whose median lands above the ceiling is forgotten and re-measured (review round 1).
- `venue_assembly.py` sits at exactly 400 lines; the next edit to it splits it (a `trading` follow-up, not part of this epic).
- `test_workbench_conformance` fails on the base tree too; unrelated.
