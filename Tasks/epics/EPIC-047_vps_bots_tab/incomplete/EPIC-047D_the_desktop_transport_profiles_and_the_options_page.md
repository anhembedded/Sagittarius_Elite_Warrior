## 1. Context and problem
The desktop needs a transport behind a seam: SSH in v1, other protocols later (O6). De-risk R3 on the owner's Windows against the VPS: key-file login, host-key pinning, round trip (asyncssh p50 25.6 ms, p95 65.4 ms) and "no listener" pass; the agent path is untested (no agent held the key); the reconnect took 1909 ms. A1 was false until the owner installed a key, for root. Two traps: `client_keys=None` turns key login off; a blocking call in the client's loop inflated event latency to p95 3.0 s (DERISK §3.3).

## 3. Design
The seam now, the variants later (P7): a transport port with the `asyncssh` adapter; a Unix socket, a VPN or a TLS endpoint are other adapters, not built. The profile store follows the repository's existing settings and Options-page mechanism rather than a new one (P5); credentials are references only. The loop on its own thread fenced per `async-ui-action-rule.md`.

## Implementation notes
- **Where it lives.** `support/wire/desk/` is the desktop's half of the link beside `support/wire/bridge/`: `DeskProtocol` (the conversation, no I/O, driven by lines and a clock like `BridgeSession`), `DeskLink` (a transport plus a reader thread; blocking `call`/`command`), `LinkSupervisor` (connect, notice a cut, reconnect on the profile's policy; one fresh `ConnectionEpoch` and `RevisionGate` per connection), `TransportRegistry` and `default_transports.py` (protocol to adapter; the SSH line, a `Deferred` by path, arrives with the adapter), `asyncssh_transport.py` (the adapter), `ssh_connect_options.py` (the profile as `connect` arguments, a pure function). The profile and its validation are in `core/contracts/link_profile.py` because `support/ui_kit` (the state holder) may not import `support/wire` (boundary guard) and `core` is open to both. `LinkProfiles` is in `support/ui_kit/services/` beside `TickFlashPreference`; the page is `shell/link_options/`.
- **Typed errors decide the retry.** `LinkError.retriable`: unreachable and lost retry on `ReconnectPolicy` (first retry at once, then 1 s doubling to the cap); a refused key, a wrong or unknown host key, a version difference and a missing transport never do (they would be refused again, and repeated key failures are how a host bans its owner). A command lost in flight is `CommandInFlightLost(request_id)`: `DeskLink` never resends; the caller asks again with the same id and the host answers from its audit (047C).
- **The two `asyncssh` traps** are closed in one pure function: `client_keys` is omitted for an agent profile (never `None`); `known_hosts` is always the pinned file, so a missing file is a refusal with first-use words. The profile is the whole configuration (`config=[]`, `preferred_auth="publickey"`): no `~/.ssh/config`, no password, no prompt. A key file that needs a passphrase is `KeyFileUnusable`, with the advice to load it into the agent: the app never asks for or stores one.
- **Loopback figures (this container, not the owner's link):** the supervisor, over the real adapter and an in-process `asyncssh` server with the real bridge behind it, reconnects after an abrupt cut in under 2000 ms (`test_the_supervisor_reconnects_over_ssh_after_a_cut_and_logs_how_long_it_took`, asserted `< 2000`; the figure is the `[link-reconnect]` log line). With the fake transport the same path is `test_an_abrupt_cut_is_reconnected_at_once_on_a_new_transport_and_a_fresh_gate`. The real figure (1909 ms before the slim entry point) is the owner's step 2.
- **What was not run:** a real Windows agent (Pageant, OpenSSH agent), the real VPS, a real `sshd` with the restricted key. The agent code path is proved on loopback by a minimal SSH agent in the test (`ssh_world.py`), which proves the argument handling, not Windows.
- **Not built, by design (P7):** the VPS Bots tab and the snapshot/subscribe application of events (047E); a "test connection" button (the page never connects); a second protocol; `paramiko` (only if D5 fires).
- **Dependency.** Approved by the owner in the author session on 2026-10-27 (their answer "Đồng ý asyncssh" to the question framed per `report-rule.md` §2). `requirements.txt` gains `asyncssh`; `uv pip compile requirements.txt --universal --python-version 3.12 -o requirements.lock` pins `asyncssh==2.24.1` and, as predicted, drops the `sys_platform == 'linux'` marker from `cryptography==50.0.2`, `cffi==2.1.1` and `pycparser==3.0` (locked for Windows too); nothing else moved. `requirements-headless.txt` is unchanged. The owner may still veto in review (SSH record D2): the revert is that one line and a recompile.

- **Review round 1 (PR #744, `49b6c9b`): two blocking, three should-fix, all fixed.** (1) The supervisor read an error's type only when `connect` failed: a link that failed *after* the welcome was redialled at once, forever (44 connections in a second in the reviewer's probe). Now `on_closed` keeps the reason; a reason no retry can change (`BridgeRefusedError`, `VersionDifferenceError`) ends in FAILED; a link that stayed up less than `STABLE_AFTER_S` (5 s) is flapping and spends the policy's next delay (first one at once), so the policy's `max_attempts` bounds it; only a link that held earns a fresh start. (2) No `-Full` run existed because the PR conflicted with master (047H, #743): merged. (3) A first read that fails (`CallFailedError`, `CallTimedOutError`) now closes the link and counts as a lost link, retried on the delays; an observer bug closes the link before the supervisor's last resort logs it. (4) `DeskLink.connect` closes a transport whose `open` raised. (5) A call that times out is removed from the pending tables. Also: the connect-timeout box has a 0.1 s minimum, the Options page says an agent profile also reads the default keys of `~/.ssh` (asyncssh cannot be narrowed to the agent alone: `client_keys=[]` still loads the defaults and `None` turns key login off), and the `TransportRegistry` registration is commented as the link's composition.

- **Review round 2 (`06dde63`): one should-fix, two nits on the adapter, fixed.** A write that raised may already sit in asyncssh's buffer (`stdin.write` queues before `drain`), so "the write raised" does not mean "not sent": `DeskLink` now reports a command whose write raised as `CommandInFlightLostError(request_id)` (a read stays a plain `LinkLostError`), and the adapter cancels the pending write and connect futures on a timeout. The host-key / first-use decision, which reads `known_hosts`, moved out of the loop to `open` on the caller's thread.
