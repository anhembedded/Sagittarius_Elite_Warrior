## 1. Context and problem
`sshd` can start a command for each session, listening on nothing. De-risk R2 showed that a key restricted with `restrict,command="…"` runs only the bridge: a request for `whoami; cat /etc/passwd` returns the bridge's `hello`, a port forward is "administratively prohibited", a terminal is refused, and the bridge ends with the connection (0 left, 6 of 6 runs); a half-open link left 1 bridge after 10 s without a heartbeat and 0 with a 6 s idle watchdog. The bridge's start is dominated by imports: 258–269 ms of ~340 ms; the real reconnect was 1909 ms (DERISK §3.7).

- **From [EPIC-047A](../completed/EPIC-047A_the_wire_codec_and_the_version_handshake.md):** the codec, the handshake (`link_handshake.judge`, whose `Refusal.to_wire()` the bridge sends before any read, then exits 3) and `RevisionGate` exist. The bot record has no revision; this task decides the sender's: a counter in the record (a version-tolerant file codec, together with EPIC-047B's file) or the bridge's own sequence per bot. The envelope and the gate do not change with that choice.

## 3. Design
Mirror the repository's `bot show` pattern (read the files) and its control door; the forced command is OpenSSH's own mechanism (P5; sources in DERISK). The bridge is a second process, not a thread in the host (G7, record D2): it cannot slow the bots and ends with its session. The bridge lives in the app, not the Engine (G8). The `authorized_keys` line is an operator step, written in [EPIC-047G](EPIC-047G_the_runbook_for_the_vps_link.md), not by code.

**Where it lives (decided at start, from the boundary rules).** A module imports another only through `contracts/`, a support package imports no module, and `shell/` may import a module's `module.py` only, which loads the whole module (1.1 s here). The bridge needs the wire layer, the store reader and the control-door writer, so:

| Piece | Where | Why |
| :--- | :--- | :--- |
| The protocol and the session loop, the runner (pipes, threads) | `src/support/wire/bridge/` | no module in it; it knows the protocol and three ports. Inside the `support/wire` zone because a support package may import another's non-contract files only within its own zone |
| The three ports and their values | `src/support/wire/contracts/` | modules implement them; a `contracts` package is importable by every module |
| The bots' read-only reader, the wire roots of `bots` | `src/modules/bots/link.py`, `adapters/store_bridge_bots.py` | the module's slim surface |
| The facts view, the control door with the request id, the roots of `operations` | `src/modules/operations/link.py`, `adapters/file_host_facts_view.py`, `adapters/replaying_command_door.py` | likewise |
| The composition, the entry | `src/shell/link_bridge_main.py`, `src/shell/link_version.py`; `deploy/linux/sew-bridge` is the key's `command=` | the only place that sees every module's `link.py` |
| The lock probe `operations`' door needs | moved to `src/support/instance_lock/` | a new shell import of the legacy `infrastructure` tree is refused by a baseline that only shrinks |

*One rule widened, on purpose:* `shell/` may import a module's `link.py` as well as its `module.py` (`tests/unit/architecture/boundaries/zones.py` → `is_module_entry_point`, layer `link` outermost in `layers.py`; rows pinned in `test_boundary_rules.py`). The alternative, importing `module.py`, makes the entry load everything and AC2 unreachable. *Rejected:* a bridge as a CLI command of `main.py` (the full argument parser, the composition root and the Engine's `App` load first); a thread in the host (record D2).

**The protocol** is in `bridge_session.py`'s docstring: hello (build, one digest per wire root, the heartbeat and the watchdog), the desktop's hello, welcome or refused, then `snapshot`, `subscribe`, `command` calls with ids and `event` lines, and `ping`/`pong`. A revision is the bridge's own counter per bot (decision D1); `snapshot` also carries the host-facts document (`sew.host-facts-document/1`) and its liveness, which is how the desktop assembles the Run step's facts (the tab's question, 047E).

## Implementation notes
- **Revision (D1).** The bridge's per-bot counter, not a field of the record: see [the decision record](../DECISION_2026-10-26_the_bridge_revision_and_the_unbuilt_venue.md). The consequence for 047D: make a fresh `RevisionGate` per connection and take a snapshot first; never keep a gate across a reconnect.
- **What the bridge does not serve.** A bot's fills (`BotFills`) and the readiness reads come from the exchange through the host's ports, so they are not in the bridge; the desktop assembles `BotRunFacts` and the Plan's venue choices from the snapshot's bots and the host-facts document (047E). The roots for those queries stay in the wire list for the day the host publishes them.
- **Where the bridge looks.** `<data root>/state/bots/`; `bots.state_dir` (a key for a test boot) is not honoured. The `app_version` in the hello is `app.version` of `app_config.json` (`0.1.0` today, the same for every commit), so a difference of build is caught by the digests of the wire roots, not by the version: a build with the same wire is the same link.
- **The exit statuses** are the bridge's own (0, 3, 4, 6, `bridge_protocol.py`); they are not `ExitCode`s of the command line, and the runbook (047G) lists them.
- **The log** goes to standard error (standard output is the protocol), which `sshd` hands to the desktop; INFO at start and at the end of a session (counts), WARNING for a refusal, a violation and the watchdog, ERROR with the traceback for a failing door.
- **Known limit.** A bridge started while a desktop's hello is delayed more than 10 s exits with status 4; a desktop on a very slow link must send its hello at once (047D).
- **Review round 1 (PR #739, `44673da`): three Should-fix, all fixed.** (1) Malformed input inside the line bound ended the bridge with exit 1 and a traceback: `RecursionError` in `parse_line`, `OverflowError` in `wait_of`; now status 4 `refused`, and a last-resort guard in `feed`/`tick` ends an unforeseen failure with its own status 5 and a word (an encode failure is no longer taken for a closed pipe). (2) Two overlapping sends of one id gave untrue replies: a send that wrote nothing never withdraws another send's file and says what it saw; another send's scratch file is waited for, never unlinked; the bridge refuses a second call while one with the same request id waits; an id that settled one action is not answered for another. (3) A bot file that is not UTF-8 crashed every session: `JsonBotStore` maps `ValueError` to `UnreadableBotError` (`bot list` had the same crash). Optional items carried: `-P` in the launcher, a log line per command, `served` under its lock, `OverflowError` in the facts decoder. Not carried: `MAX_LINE_BYTES` counts characters (a text stream), recorded as a limit.
- **Gate round 1.** `gate (Rest)` on `44673da`: the `bot list` import test (this PR's, fixed in `6e2f78a`) and `test_workbench_conformance` (red on the base too, run 40419536949).
