## 1. Context
✅ Established on `master-warrior` `7ef62c7` (read 2026-10-15):
- **The core exists and sends nothing.** `EPIC-036A` delivered the hub, the outbox and the lanes; the channel list is empty (`src/modules/alerting/composition/channel_bindings.py:39-40`) and the module reads no other module (`src/modules/alerting/module.py:61`). The headless host says so at every start (`src/modules/operations/application/host_steps.py:63-77`, fed by `NoAlertChannels`, `src/modules/operations/adapters/no_alert_channels.py:10-18`), and the generated unit file says the host is "NOT supported for unattended money until EPIC-036B, 036C and 036E have merged" (`deploy/linux/sew-run.service:4-5`).
- **The planned order delivers nothing to the owner for three pull requests.** Design 036 §14 orders `036B` (all sources, the old handler deleted), then `036C` (Discord and Telegram together, the token migration, Send test, Rotate), then `036E`. A halt reaches no person until the second has merged, and each is L or M on its own.
- **The headless host has no keyring.** On the owner's VPS the keyring store logs "The operating system's keyring cannot be read (...); a mainnet key is read from the environment only [keyring]" (`src/modules/trading/adapters/binance/mainnet/keyring_secret_store.py:73-77`). N3 keeps the Discord webhook in the keyring only, so on that host there would be no webhook and no alert.
- **The host already has a secret route that works.** Mainnet exchange keys come from systemd credentials: the unit lists `LoadCredential=<name>:/etc/sew/credentials/<name>` (`deploy/linux/sew-run.service:39-44`, generated by `scripts/render_service_files.py:113-123`) and `SystemdCredentialStore` reads `$CREDENTIALS_DIRECTORY/<name>` at each call, never writes, and logs no value (`src/modules/trading/adapters/binance/mainnet/systemd_credential_store.py:1-84`). The order of the stores is written once, systemd credential → permission-checked file → keyring (`src/modules/trading/composition/secret_store_order.py:1-20`, `:95-100`). All of these live under `trading`, which `alerting` may not import (open question O2 of the 2026-10-08 record).
- **The stop that gives up is not a typed fact.** After its last automatic retry a Grid stop stays `STOPPING`, appends text to the bot's reason and writes an ERROR log line "until an alert channel exists" (`src/modules/bots/application/kinds/grid/stop/grid_stop_retry.py:1-21`, `:112-124`). `BotStatusEntry` carries the state and that reason as text (`src/modules/bots/contracts/bot_status_report.py:57-69`).
- **The standard for a design.** `EPIC-041` puts a module's design in `Docs/MODULES/<module>.md` with seven views ([`DECISION_2026-10-14_documentation_philosophy.md`](../EPIC-041_documentation_standard/DECISION_2026-10-14_documentation_philosophy.md) D2, D3; `Docs/MODULES/README.md`). The walking skeleton, "the smallest end-to-end slice that exercises every architectural seam", is the shape `PRO-004` and `Docs/HLD/06_enforcement_and_migration.md` §6.3 used for `EPIC-025`.

## 3. Alternatives considered
- **For D2, keep design 036 §14's order (sources, then both channels).** Lost: two L/M pull requests before any alert reaches a person, while the host on the VPS already runs bots. A walking skeleton proves the seams first and turns every later task into a widening (PRO-004 §6.3 for the same reason).
- **For D2, a skeleton to a fake channel only.** Lost: `036A` already proves that (`tests/integration/modules/alerting/test_the_composed_app_delivers_alerts.py`); the unknowns left are the real webhook, Discord's 429 and the secret on the host.
- **For D3, an environment variable** (`EnvironmentFile=/etc/sew/sew.env`). Lost: an environment variable is inherited by every child process and readable in `/proc/<pid>/environ`; the mainnet keys left the environment for systemd credentials for exactly this reason (`systemd_credential_store.py:3-8`, decision O3 of `EPIC-038`). The testnet keys stay there; a webhook that can post to the owner's channel is not a testnet value.
- **For D3, the keyring only (N3 as written).** Lost: no keyring exists on the VPS (§1), so the host would have no channel at all.
- **For D3, a config-file value.** Lost to N3, which stands: no secret in config.
- **For D3, a second systemd reader inside `alerting`.** Lost to P3: two readers of one directory with two sets of name and size rules drift.
- **For D3, `alerting` reading the secret through `trading`'s contracts.** Lost: it makes `alerting` depend on `trading` for something that is not trading, and `trading`'s ordered store reports a mainnet-key source the webhook does not have.
- **For D4, matching the text "automatic retries are used up" in the reason.** Lost: a wording change silences the alert, and nothing would fail (P1).
- **For D5, keep `NoAlertChannels` until `036E`.** Rejected as the recommendation, kept as the owner's option: the host would keep saying "nothing will tell you if a bot halts" when Discord does, and an operator learns to ignore a warning that is false.
