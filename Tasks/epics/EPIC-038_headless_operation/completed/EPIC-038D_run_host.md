## 1. Context and problem
Every headless command boots the app, does one thing and calls `app.stop()` (`src/main.py:57-80`); only the interactive REPL keeps the process up, and it waits on a terminal (`shell.wait_for_exit()`). No handler for SIGTERM exists in `src/` (a `kill` skips `BotsModule.shutdown`, which closes the workers); the Engine's two handlers belong to the Qt watchdog and the audit CLI. A restart currently turns RUNNING/PAUSED bots into RECOVERING and waits for a person to open the order session (`bot_restore_service.py`, `SPEC-004` §2). Operators' reports: a live process is not a live bot, a stop may or may not cancel orders depending on how it ended, a read-only copy that looks alive is worse than none, and a restart loop on a configuration error hides it (R1, R3, R13).

## 3. Design
The host only sequences; it knows no bot. Strategy for the stop policy and the signal source; Observer for the health contributors (038C); the engine's `IHostedService` for lifecycle. The pattern follows Freqtrade's worker (signals, an optional systemd integration) and Hummingbot's explicit `exit` versus window-close difference, made a named option (R2, R3). The host adds no supervision logic: restart belongs to the service manager, and the exit codes tell it which failures to retry. **Alert prerequisite for O2(b):** `--resume-recovering` is implemented behind the flag but its documentation says to use it only once bot events reach the owner; the flag refuses to start (exit 5) unless an alert channel is configured **or** `--i-accept-silent-failures` is given (a deliberate typed acknowledgement, not a default).

## Implementation notes (written when done)
**Order of a `run` (the part that keeps money safe):** the entry point takes the lock; builds the app **without booting it**; refuses what needs no exchange (flags, `--resume-recovering` without an alert channel or acknowledgement, an unconfirmed mainnet `--start-planned`); runs the pre-flight; then listens for signals, boots (modules restore, then the host's steps and `SERVING`), waits, drains, stops. The pre-flight is before the boot because restoring a bot reads the exchange and may cancel orders, which a machine whose key or clock is wrong must not do. This needed two declarations the task did not name: `"requires_writable"` (a held lock exits 3 instead of booting read-only) and `"owns_lifecycle"` (the app is handed to the command unbooted).

**Decisions made (recorded, owner may veto):**
1. *Health cadence.* The module already published a snapshot every 10 s for every writable copy. `run` must change the interval, the state and add two hooks without a second publisher, so `HealthCadence` (one small shared value) is configured before the boot and read by `boot()`. The GUI's behaviour is unchanged.
2. *The clock skew* is measured by a new kernel port, `IHealthProbe` (`declare_probe`), because `operations` may not import `trading` and a contributor may not call the network. The probe reuses the `clock-skew` check's read; it runs on a bounded worker before each snapshot, so a slow exchange cannot hold the snapshot back.
3. *`stream_age_s` is renamed `stream_down_s`* (the stream publishes state changes, not messages) before anything parses it.
4. *The Engine's `Executing query` lines are accepted:* 2 880 a day at 60 s; see `LOGGING.md` §5 and the test that bounds it.
5. *Stderr retarget:* `console_log_to` builds the app with `sys.stdout` pointing at stderr for a machine-format run, because `StdLogger` reads `sys.stdout` when it is built (twice). Only machine formats move; a text report keeps its log on stdout.
6. *Mainnet:* `--confirm-venue` takes one mainnet venue; `--start-planned` is refused wholesale (exit 2, nothing started) if any planned bot at rest is on an unconfirmed mainnet venue, and `--resume-recovering` skips (and names) an unconfirmed mainnet venue. A plan with real-money bots on two venues is started one venue per run.
7. *`--resume-recovering` = open the venue's order session.* Reading `BotEventRouter.on_switch` shows that is exactly what resumes a RECOVERING bot on the screen; the host adds no resume path of its own.
8. *The bots seam is three contract commands* (`StartBotForHost`, `StopBotForHost`, `ResumeRecoveringForHost`) answered by handlers that dispatch the screen's commands, plus `resting_orders` in the status report (an additive key in `bot list` / `bot show` JSON).
9. *The fake futures account gained `canTrade: true`,* which the real endpoint returns; without it every healthy run logged a pre-flight WARNING.

**Findings the task text lacked (for the coordinator and later children):**
- **O2's remedy has no headless path yet.** The WARNING for a RECOVERING bot must say who resumes it, but `bot resume` does not exist, and under O4 (no control of a running host) neither it nor the GUI can run beside the host that holds the lock. The message names the Bots tab and `EPIC-038J` and says so. A person resuming a bot by hand means stopping the host first.
- **`--start-planned` has no plan to read.** `desired_state` is `EPIC-038I`'s; `IBotPlan` is the seam, bound to `NoBotPlan`. **038I must bind a real `IBotPlan`** (added to its task).
- **A first run with no credentials exits 5** with the pre-flight on (`credentials-present`); the "empty host boots" criterion holds with `--skip-preflight`.
- `IAlertChannels` is `operations`' own port, bound to `NoAlertChannels`. `EPIC-036B` (and `036A`'s alerting module) must replace that one binding; the resume refusal and the start WARNING follow it.
- A signal that arrives while the bots are restored is remembered and honoured (listen before boot); without that, a `systemctl stop` during a slow restore would have killed the process with workers half-started.
- `tests/integration/presentation/ui/test_workbench_conformance.py::[True-1024x700]` fails in this container on `master-warrior` itself (`93ff7d0`, a font-metric layout assertion); it is not touched by this change and CI is its authority.
- **The soak is the health machinery's, not the process's.** `tests/health_soak.py` (run as a program by `test_the_health_machinery_over_fourteen_simulated_days.py`) drives the real snapshot, section, probe, line and file code for 14 x 1 440 intervals on a clock it advances, with a stream death at every 24 h boundary and ten-minute outages: 20 160 lines for 20 160 intervals, the skew `na` while the exchange is dead and known after, objects and threads flat and resident memory 24 -> 28 MB (the soak's own 4 MB of log lines). It does not include the Scheduler, the bots' workers or the websocket; the 14-day run of the process and the Windows runs stay open in the epic's phase-2 and phase-3 evidence. Inside pytest the resident size grew by tens of megabytes over the same loop (the harness holds what 80 000 short-lived threads leave), which is why it runs in its own interpreter.
