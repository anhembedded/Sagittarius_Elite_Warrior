## 1. Context and problem
Reads already work on a server: `EnvFirstCredentialsProvider` reads the environment first (`env_first_credentials_provider.py`), and `KeyringSecretStore` reads "nothing stored" with a single INFO line when no keyring exists (`keyring_secret_store.py:63-80`). What is missing is a way to **provision** a secret on a server that is better than putting it in a shell, an unprotected `.env`, or a process environment visible to the same user's tools. The `keyring` project's own recipe for headless Linux needs a D-Bus session and a password on stdin at every boot (R4), which is not unattended. systemd offers credentials (`LoadCredential`, `$CREDENTIALS_DIRECTORY`) that are not inherited by child processes and are access-checked by the kernel (R4). The port's own docstring names "an encrypted file for a machine with no keyring" as the plausible extension and records that the keyring was chosen over a file (D10 of `EPIC-034`).

## 3. Design
Adapters behind the existing port (dependency inversion), ordered by one list (open/closed), the same shape that put environment first and the keyring second. The permission check is its own collaborator (`SecretFilePermissionCheck`), one implementation per OS, so the store has one reason to change. Windows: `keyring` already ships a Windows Credential Manager backend; whether it works for a service account without an interactive profile is **unverified** — this task tests it on a Windows server before recommending it, and falls back to the permission-checked file.

## Implementation notes (written when done)
- **Where the order lives.** `EnvFirstCredentialsProvider` (testnet) never held a store; the mainnet provider did, so the change is in `MainnetCredentialsProvider`. It now reads a new port, `ISourcedSecretStore`, so that the source can be named and a key and its secret are always read from the same store; `OrderedSecretStores` implements it in the trading module (a support adapter could not be imported by `trading/composition` without growing the boundary allowlist, which only shrinks).
- **Order:** environment, systemd credentials, permission-checked files (only when `SEW_SECRET_FILES_DIR` names a directory), keyring last and alone writable. A provisioned key therefore wins over one a person saved in a desktop session; the settings page locks such a key and `enrol`/`remove` refuse it in words.
- **The file store is opt-in by a directory, one file per secret** (`<dir>/<venue>_api_key`, `<venue>_api_secret`) - the same shape as systemd credentials, so the operator's tooling is the same for both.
- **Windows ACL without a new package:** the built-in `icacls`, parsed; anything unreadable is refused, never trusted. The summary line is localised and is **not parsed** (it is skipped; the exit code decides whether the run worked, and only one line may follow the blank line). Built-in group names are compared as printed, so a localised Windows refuses a file until the ACL names the service account alone (the printed fix produces exactly that). Known limits, in the docstrings: the Windows check judges the path, not a handle; only the immediate directory is checked on POSIX.
- **Review hardening (2026-10-13).** The Windows ACL parser fails closed: any `icacls` line it does not understand refuses the listing (it first skipped such lines, so a stranger's entry in an unknown shape was accepted), an undecodable output refuses, and the printed fix removes each named stranger as well as inheritance. On POSIX the file is opened once without following a symbolic link and the checks `fstat` that descriptor, so the file judged is the file read; the directory must not be writable by group or others and must belong to the running user or root. A named pipe is opened non-blocking and refused as "not a regular file" (an ordinary open blocked forever). The port lost `read_sourced` (no consumer); the contract suite covers `OrderedSecretStores`; the sanity boot greps every file under the data root, `state/health.json` included.
- **A blank value reads absent for every store** (the contract suite found the keyring and the test double returned `""`).
- **Preflight** needed no change to say the backend: it already printed `CredentialsSource.value`. A *refused* file shows as "no key is configured" with the refusal in the WARNING log; surfacing the refusal in the report is a possible follow-up.
- **Not decided here:** whether the Windows Credential Manager works for a service account (O3 makes it a condition of recommending it); until someone runs it on a server, the file store is the Windows path that is tested.
- **Dependencies, settings, `pyproject.toml`: none touched.**
