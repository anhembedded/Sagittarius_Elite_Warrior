## 1. Context and problem
The sources agree on what a service needs: restart on failure with a delay and no start limit, no restart on a configuration error, a stop timeout longer than the app's drain, secrets outside the code directory and out of the process environment where possible, a dedicated no-login account, a memory ceiling, bounded logs (R1, R4, R8, R9). On Windows the wrapper stops a console app with Ctrl-C first and waits 1.5 s by default (R10). Freqtrade's updating page says nothing about migrating state (R15); this app's state is the bots' files, the snapshot and the data root.

## 3. Design
Documentation and configuration as code: the unit and the wrapper recipe are the artefacts the tests parse, so the runbook cannot drift from them (the repository's pinned-sentence pattern). Windows: NSSM supervises and rotates and tries a graceful stop first; Task Scheduler's restart settings are coarse and it has no stop-signal control (R10) — documented as the fallback, not the recommendation. ## Implementation notes (written when done)
**The files are generated, not typed.** The brief said the exit codes must not be typed; the same holds for the stop budget and the credential names, so one script renders both files and a test compares them with the render (the pattern of `exit_codes.md`). A second, independent assertion per figure reads the file and the code's constants, so a wrong formula in the generator fails too.

**Decisions made (recorded, owner may veto):**
1. *`Type=notify` with `--host-signal sdnotify`, and no `WatchdogSec=`.* READY=1 then means "the pre-flight passed and the bots were restored", so a start that dies in the pre-flight is a failed start. The watchdog is left off: it could not be exercised under a real systemd here, and a watchdog kill on a slow drain is a failure mode worth running once before shipping. The adapter supports it (`WATCHDOG_USEC`).
2. *`TimeoutStopSec` = ceil(25 + 30 + 2) + 5 = 62 s.* The 2 s is `LEAVE_PUBLISH_SECONDS`, the bounded snapshot write the forced exit makes; the 5 s margin is `STOP_MARGIN_SECONDS` in the generator.
3. *`StateDirectory=sew` is how the data root stays writable under `ProtectSystem=strict`:* systemd creates `/var/lib/sew` owned by the service account, so the runbook has no `chown` step to forget. `MemoryDenyWriteExecute` is deliberately not set (Python and `pyarrow` may need executable memory and nothing here could prove they do not).
4. *Mainnet `LoadCredential=` lines are in the unit for all four names*, because a missing source file stops a unit from starting. The runbook has the operator create an empty file for an unused venue; a blank credential reads as no key (the contract suite of `EPIC-038E`; `test_a_credential_file_left_empty_for_an_unused_venue_reads_as_no_key`).
5. *Testnet keys come from `EnvironmentFile=-/etc/sew/sew.env`:* the systemd store and the file store serve mainnet venues only (`MainnetCredentialsProvider`); the testnet provider reads the environment.
6. *The new `bot-files-readable` check is a WARN, not a FAIL.* A FAIL would refuse to serve and take every other bot down for one unreadable file that the restore service already leaves untouched.
7. *Windows: a virtual service account* `NT SERVICE\sew-run` (no password in a script) and the permission-checked file store for mainnet keys; the Credential Manager question of O3 stays open.
8. *`pwsh` was installed in this environment* (install rule §3) to parse and run the NSSM script; the tests skip with a stated reason where `pwsh` or `systemd-analyze` is absent (CI has both).

**Findings the task text lacked:**
- **`preflight` cannot see a systemd credential outside the unit.** `$CREDENTIALS_DIRECTORY` exists only inside the service, so a hand-run `preflight` for a mainnet venue reports no key. The runbook says to read the pre-flight that `run` performs instead.
- **A restart leaves bots RECOVERING with no headless way to resume them** (the gap `EPIC-038D` recorded): an upgrade therefore ends with a person at the Bots tab, or with `--resume-recovering --i-accept-silent-failures`. Runbook §0 and §8 say so.
- **`--on-stop` belongs to the process being stopped.** An upgrade that wants `stop-bots` needs the running host to have been started with it, so the runbook describes the default (orders left resting) and does not pretend a flag at stop time exists.
- **Re-running the NSSM script resets `AppEnvironmentExtra`.** The script now takes `-SecretFilesDir`, and the runbook says to append testnet variables again afterwards.
- **Plan files** (`bot export`, `bot apply`, `--start-planned`): runbook §8 was written against the command line of PR #476, then re-checked after `EPIC-038I` merged: `bot export`, `bot apply --dry-run` and `bot apply` ran against an empty data root, and `run --start-planned` served after the apply (the exit-5 refusal without a plan is `EPIC-038I`'s process test).
