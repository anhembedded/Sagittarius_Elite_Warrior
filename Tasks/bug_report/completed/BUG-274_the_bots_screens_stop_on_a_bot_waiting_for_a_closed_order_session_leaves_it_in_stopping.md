# BUG-274 — Stop on the Bots screen leaves a HALTED bot in STOPPING: "the budget was refused: the order session is not open"

- **Reported:** 2026-10-27 (the owner, desktop app, Futures USD-M bot `2f3075` "34_USD_26-10" on BNBUSDT, about 10:59-11:00 local; relayed by coordinator session `session_016sGQHsRy729Fp4cY1cTXfu`)
- **Severity:** 🟡 P2 — the owner's real-money bot cannot be stopped from the screen, so its position and orders stay as they were; no order is placed wrongly, and the bot waits visibly, but the wait never ends and says nothing about how to end it
- **Status:** ✅ Fixed (2026-10-27)
- **Board:** The screen's Stop never opened the venue's order session (Resume, Start and the headless `bot stop` do), so after a restart the stop's budget registration was refused and the bot waited in STOPPING for a session nobody opened. A Stop that carries the person's real-money answer now opens it, or is refused in the session's words; an automated Stop opens nothing and its wait says to press Stop (`BUG-274`).
- **Context:** [SPEC-014](../../../Docs/SPEC/SPEC-014_run_a_grid_bot.md) (run a Grid bot; Stop, restart and recovery) → `src/modules/bots/` → `application/use_cases/stop_bot/`, `application/kinds/grid/stop/`, `ui/bots_screen/bot_commands.py`
- **Environment:** Windows desktop app, Futures USD-M bot, master `783462a` (the base of the fix). Venue (testnet or mainnet) not captured in the excerpt. The bot's earlier history (why it was HALTED, whether the app had been restarted) is not in the excerpt.

## Reproduction
1. A Futures Grid bot is waiting (HALTED, or RECOVERING) and the app has been started again: a start always leaves the venue's order session closed (`enabled` is never persisted, `ITradingSession.ensure_ready`).
2. Bots screen → Stop → choose the exit → confirm.
Expected: the bot is cancelled and closed per the choice and reaches STOPPED, or the owner is told plainly why it cannot. Actual: HALTED -> STOPPING, "Stop accepted", nothing cancelled or closed; a second Stop repeats it. Reproduced on the composed app over the fake Futures exchange (the first test below, red before the fix), with a RECOVERING bot, which waits for the session in the same way.

## Symptom
```
10:59:56,753 App.Bots.Screen - Bots screen: Stop 34_USD_26-10
10:59:56,754 App - Executing command: StopBotCommand
10:59:56,774 App.Bots.GridExecutor - Bot 2f3075: HALTED -> STOPPING on stop (user_stop: user_stop) [bot-transition]
10:59:56,787 App.Bots.Screen - Bots screen: Stop 34_USD_26-10 accepted
10:59:56,964 App - Executing command: RegisterOwnerBudgetCommand
10:59:57,148 App.Bots.GridExecutor - Bot 2f3075: STOPPING waits - the budget was refused: the order session is not open
```
The second Stop at 11:00:20 repeats the registration and the same line. The live stream of 10:59:46-47 (a chart's `StartLiveStreamCommand`, cancelled) is unrelated.

## Facts established (and what was ruled out)
- **Closed session, not a halt or a stream.** Only `EmergencyStopCommandHandler` closes the session (`src/modules/trading/application/session/emergency_stop/handler.py:200`, `scope.session_state.disable()`, at `783462a`); a halt does not touch it, and a chart's live stream is market data. No Emergency Stop is in the excerpt. A start of the app leaves every venue's session closed. So the cause is, to the evidence, that the app was started with the bot already HALTED and no deliberate action had opened the session since. This is inferred from the code and the excerpt; the part of the log before 10:59 was not available.
- **Not a missing key.** A missing or rejected key is a different refusal (`CONNECTION_NOT_READY` / `KEY_REJECTED`), worded differently; the line says the session is not open.
- **Not the VPS host's lease.** A second process has its own session state; it can refuse for a foreign position (`BUG-259`), not close this app's session.
- The refusal is `OwnerBudgetRefusal.TRADING_SWITCH_OFF` from `RegisterOwnerBudgetCommandHandler._cheap_refusal` (`src/modules/trading/application/session/register_owner_budget/handler.py:164`, `if not scope.session_state.enabled`), worded by `refusal_text` ("the order session is not open").

## Root cause
At `783462a`: `StopBotCommandHandler.execute` (`src/modules/bots/application/use_cases/stop_bot/handler.py:51-57`) checks the lifecycle table and queues the stop; it never opens the order session. The stop's first step, `GridStopSequence.run` (`.../grid/stop/grid_stop_sequence.py:108`), registers the owner budget, which a closed session refuses; `_budget_refused` (`:135`) then parks the bot in STOPPING with no way out. Every other deliberate bot action opens the session through `order_session_refusal` (`order_session_opening.py`): Start, a Resume from HALTED or RECOVERING, and the headless `bot stop` (`stop_bot_for_operator/handler.py`, whose docstring already names this exact hole: "the screen's Stop does not open the venue's order session ... a Stop is accepted and waits in STOPPING for a session nobody opens"). The owner's answer "B" of 2026-10-17 fixed the host's Stop; the screen's was left, and SPEC-014 still recorded "Stop waited for the same session".

**Second mechanism, found by the reviewer of #742 (round 1) and reproduced here.** Opening the session announces it as opened for the bot that asked (`order_session_refusal` → `opened_for=bot_id`, `BOT-183`). For a RECOVERING bot that is its own wake-up: `GridFacts._apply_switch` reconciles it to RUNNING and `release_held` lays the counter order a fill-while-down left owed, on the worker queue ahead of the Stop already queued behind it. So the first version of this fix, and the headless `bot stop` before it (`stop_bot_for_operator/handler.py` at `783462a`), sent a new real-money order before taking the ladder off. Log of the red probe: `RECOVERING -> RUNNING on reconcile_ok` before `RUNNING -> STOPPING on stop`, one SELL limit sent in between (the reconcile then ran on the switch-on, ahead of the stop; since the fix it runs inside the stop task and `release_held` does not).

**Third effect, found by the reviewer's round-2 question and measured here.** Opening for the person stops the wake-up, but a RECOVERING bot's reconcile was also what booked the fills that landed while the app was closed. Without it the stop's close was measured against a cost lacking those fills: in the probe (0.006 bought while down, the price below every entry) `realised_total` read +363.25 USDT where the reconcile-first path read −14.83. The exposure was right (the close covers the exchange-derived position); the run's record was not. `GridFacts.book_missed_fills`, run by `GridExecutor._run_stop` for a RECOVERING bot, runs `GridReconciler.run` (lease, budget, fills, adoption, exposure check, transition to the prior state or HALTED; it places nothing) before the stop. A RECOVERING bot that reaches STOPPING without it (an automated Stop on a closed session) is `BUG-275`.

Why the gate was green: `booted_futures_bots` and `booted_two_venues` seed the session open by default, so every Stop journey ran over an open session (the blind spot `BUG-250` already named); `test_stop_bot_for_operator*` pin the host's Stop only. No case study: the closing net is the new closed-session journey below, and the blind spot is the same one `BUG-250` recorded.

## Options considered (owner decision, 2026-10-27, chat)
The decision touches real-money behaviour (opening a venue's order session from a click, possibly on mainnet), so the author asked the owner; the owner chose A.

| Option | Behaviour | Tradeoff |
| :--- | :--- | :--- |
| **A (chosen)** | A Stop a person presses opens the closed session as Resume and `bot stop` do, with the venue's position claims (`BUG-250`); on mainnet it asks the real-money question once per session; refused in words if the session will not open | One mechanism for every deliberate action; no new threshold or order type; one extra question on the first mainnet Stop of a session |
| A without the question | The same, no real-money question | Fewer dialogs, but opens a real-money session without the consent every other opening asks for |
| B | Only say why and how to open the session | No change in money behaviour, but the owner has no way out from that bot (a STOPPING bot cannot be resumed) |
| C | Retry on a schedule | Never ends: the session opens only by a deliberate action, never by itself, so that a late order cannot undo an Emergency Stop |

## Fix
The mechanism is "which Stop may open the session", decided once in the Stop use case, so the Spot and Futures paths and every screen caller share it.
- `src/modules/bots/application/use_cases/stop_bot/command.py` → `StopBotCommand.real_money_confirmed` (default `False`): a person's Stop carries the answer to the real-money question, as `ResumeBotCommand` does.
- `src/modules/bots/application/use_cases/stop_bot/handler.py` → `StopBotCommandHandler._session_refusal`: when the command carries the answer and the session is closed, it calls `order_session_refusal` with `venue_position_claims`, as the operator's Stop does; a refusal is returned in the session's words and nothing is queued. An open session is not asked again. A command without the answer (the loss cap's `LossCapStopper`, the host's shutdown policy, the operator's Stop after its own opening) opens nothing: a late order must not undo an Emergency Stop.
- `src/modules/bots/ui/bots_screen/bot_commands.py` → `command_for`: after the Stop dialog it asks `allow_real_money` (remembered per venue and session; a testnet is never asked) and sends the answer. A declined question still stops, opening nothing, because a Stop only reduces exposure.
- `src/modules/bots/application/services/orders/order_session_opening.py` → `order_session_refusal_for_stop`: a Stop's opening is announced as opened for the person (`OpenedByPerson.PERSON`), so no bot is woken, the stopped one included; a RECOVERING bot logs `[recovering-waits]` and the queued Stop runs over the open session. Both the screen's Stop and the operator's `bot stop` use it (one mechanism, `fix-bug-rule` §2).
- `src/modules/bots/application/kinds/grid/grid_facts.py` → `GridFacts.book_missed_fills`, called first in `GridExecutor._run_stop`: a RECOVERING bot's Stop reconciles it first, booking what filled while the app was closed and placing nothing.
- `src/modules/bots/application/kinds/grid/stop/grid_stop_sequence.py` → `GridStopSequence._budget_refused`: the wait an automated Stop (or a declined question) parks in now says "the order session is not open; press Stop to open it", so the owner is no longer left with no way out. Resume's, the reconciler's and the range entry's waits keep their wording.
- `Docs/SPEC/SPEC-014`, `Docs/MODULES/bots/06-runtime.md` and the opener guard `tests/unit/architecture/test_every_order_is_reconciled.py` name the new fourth opener.

Sibling paths scanned: Spot's Stop is the same handler and executor (`GridStopSequence` serves both venue profiles), covered by the unit test for both venues; the other STOPPING waits (`_cancel_tagged` cancels refused by a closed session, `wait_for_rate_limit`, `_confirm`) end through the same re-run when the session opens, and the headless Stop was already fixed. The resume (`grid_resume_sequence.py`), reconciler and range-entry waits are not Stops and are unchanged.
