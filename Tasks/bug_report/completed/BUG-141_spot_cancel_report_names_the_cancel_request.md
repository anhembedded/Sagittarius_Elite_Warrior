# BUG-141 — A cancelled Spot order is reported under the cancel request's id, not its own

- **Reported:** 2026-10-03 (found by the author session while executing `EPIC-029A`, ADR D8, by reading Binance's Spot user data stream documentation against `spot_user_data_event_parser.py`)
- **Severity:** 🟡 P2 — every Spot cancel publishes an `OrderEndedEvent` naming an id the app never placed, so whoever waits on the order (the Open orders row, the protective-order follower, and from `EPIC-029` a Grid bot's book) never learns that it ended.
- **Status:** ✅ Fixed (2026-10-03)
- **Context:** Spot desk Open orders and order ending (`SPEC-013`) → `src/modules/trading/` → `adapters/binance/spot/spot_user_data_event_parser.py`
- **Environment:** Linux container, Python 3.12, `master-warrior` at `d938260e` + `EPIC-029A` C1. Not observed on a live venue; established from Binance's documented payload. No credentials involved.

## Reproduction
1. Place a Spot LIMIT order from the desk (client order id `SEW-…`), then cancel it, from the desk or from Binance's site.
2. Binance pushes an `executionReport` with `x`/`X` `CANCELED`, `"c"` the cancel request's id (generated by Binance when the request names none, which `SpotTradingClient.cancel_order` never does; `web_…`/`and_…` from Binance's site or app) and `"C"` the order's `SEW-…` id.
3. Expected: `OrderEndedEvent.order.client_order_id == "SEW-…"`. Actual: the cancel request's id.

Frequency: every Spot cancel. Not reproduced against a live venue; the fake exchange emits no cancel report (`EPIC-029A` C5 adds one), which is why the gate never exercised this path.

## Symptom
The regression test before the fix:
```
E       AssertionError: assert 'web_3f9a1c2b7d4e4b0c' == 'SEW-a3f9c1-0123456789'
FAILED tests/unit/modules/trading/adapters/binance/spot/test_spot_user_data_event_parser.py::TestCancelCarriesTheOriginalId::test_a_cancel_reads_the_original_id
```

## Root cause
`parse_execution_report` read the order's id from `payload["c"]` for every report (`spot_user_data_event_parser.py:70` before the fix). Binance documents `"c"` as the client id of *this request*: on a NEW or a fill it is the order's own id, on a cancel it is the cancel request's, and the order's id moves to `"C"` (sent as `""` on every other report). Futures' `ORDER_TRADE_UPDATE` keeps the order's id in `"c"` on a cancel, so the Futures parser is not affected. No net covered the path: the parser tests used only fills and NEW reports, and the fake exchange sends no cancel report.

## Fix
`spot_user_data_event_parser.py`: `_order_client_id(payload)` returns `"C"` when `"X"` is `CANCELED` and `"C"` is non-empty, and `"c"` otherwise. The one parser every Spot report goes through now resolves the id, so every consumer of `order_ended` (and `order_filled`, unchanged) receives the order's own id; no consumer learns about `"C"`.

## Regression test
- `tests/unit/modules/trading/adapters/binance/spot/test_spot_user_data_event_parser.py::TestCancelCarriesTheOriginalId::test_a_cancel_reads_the_original_id`: failed before the fix with the cancel request's id (above); passes after.
- Same class: an empty `"C"` falls back to `"c"`; a fill ignores `"C"`.
- `tests/unit/modules/trading/adapters/binance/spot/test_spot_user_data_stream.py::test_a_cancelled_order_publishes_order_ended_and_no_fill`: the cancel report now has a distinct `"c"`/`"C"` and the published `OrderEndedEvent` carries `"C"`.
