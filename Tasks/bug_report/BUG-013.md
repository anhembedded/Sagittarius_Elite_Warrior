# BUG-013 — ResourceScope teardown crash starting a new backtest run (stale native dispose callback)

**Reported:** 2026-08-19 (Windows session, screenshot + traceback)
**Severity:** P1 — crashes the "Chạy Backtest" click itself once triggered
**Status:** ✅ Fixed 2026-08-19 — root-caused, reproduced with a real native host, regression-tested

## Root cause

A reference-script indicator line drawn on the **native** chart host
registers its removal as a dispose callback bound to that specific host:
`IndicatorScriptRunner.draw()` does
`active.scope.add(qualified, dispose=functools.partial(card.remove_indicator, qualified))`.

If the chart host is then rebuilt — specifically via
`BackTestPresenter._fallback_to_python_after_unsupported_native_feature()`
(triggered by any `NativeUnsupportedFeatureError`, e.g. an out-of-scope
script region/info/marker) — the *old* native `QQuickWidget` gets
`deleteLater()`'d, but nothing told `IndicatorScriptRunner` that its
dispose callback is now stale. The next "Chạy Backtest" click's
`clear_from_chart()` unconditionally calls `dispose_all()`, which invokes
that stale callback — `NativeBacktestChartHostAdapter.remove_indicator()`
— against the now-deleted widget, and `_assert_owning_gui_thread()` crashes
trying to read `self._widget.thread()` on it.

This is the exact same class of bug already fixed for
`_on_chart_mode_changed()` on 2026-08-18 (chart-mode round-trips losing
indicator lines) — that fix added
`BackTestPresenter._reset_indicator_bookkeeping_after_host_rebuild()`
(then named inline) to drop stale bookkeeping after a rebuild, but only
wired it into the mode-change path. `_fallback_to_python_after_unsupported_native_feature()`
is a **second, independent rebuild path** that fix never touched — this bug
is that gap.

## Why this needed a sanity test, not a unit test

The crash lives inside `NativeBacktestChartHost`'s own
`_assert_owning_gui_thread()`, reading `self._widget.thread()` on a real
`QQuickWidget`. The existing unit-level fallback tests mock
`NativeBacktestChartHost` (`Mock(spec=NativeBacktestChartHost)`), which
never executes that real method body — it only records the call — so a
first attempt at a unit-level regression test silently passed without the
fix at all (confirmed empirically, twice, before switching tiers). A real
native host is required, exactly why this bug was only ever found through
real interactive use, never through existing coverage.

Reproducing it also needed forcing a genuine C++ deletion: plain
`QApplication.processEvents()` does **not** reliably flush a posted
`DeferredDelete` event (an object stayed `shiboken6.isValid() == True`
after 5 consecutive `processEvents()` calls, verified empirically) —
`QCoreApplication.sendPostedEvents(None, QEvent.DeferredDelete)` is
required to force it directly.

## Fix

Extracted the stale-bookkeeping reset from `_on_chart_mode_changed()` into
a shared `BackTestPresenter._reset_indicator_bookkeeping_after_host_rebuild()`
and call it from **both** rebuild paths:
`_fallback_to_python_after_unsupported_native_feature()` (this bug) and
`_on_chart_mode_changed()` (2026-08-18's fix, unchanged in effect).

## Regression test

`tests/sanity/test_bug013_native_fallback_stale_script_dispose.py` —
constructs a real `BackTestPresenter` against the real DI container with
`backtest.chart.backend=native` (mirrors `test_backtest_native_chart_di_sanity.py`),
registers a script-drawn indicator line against the real native host,
triggers `_fallback_to_python_after_unsupported_native_feature()`, forces
the old native widget's deferred deletion to actually run, then calls
`clear_from_chart()` on the new host. Confirmed failing with the exact
original traceback before the fix; passes after it.
