# when Phase 4 deletes the legacy tree." Measured rather than assumed: moving
# `screens/data_management` into `modules/market_data/ui/` in PR 4.4b did not

# and `shell/legacy_screens.py` are the *permanent* screen-registration
# mechanism (Trading and Dev Board keep the identical shape after PR 1.4's
# "become a surface"), not legacy debt Phase 4 dissolves. What Phase 4 deletes

# import itself survives, now pointing at `modules.<name>.ui.module`, which
# `boundaries/rules.py::is_module_entry_point` does not recognise (it only

# `BoundedContextModule` shape -- not a screen's registration class one level
# deeper). That import moved to `allowlist_module_boundaries.txt` instead
# (PR 4.4b's own entry), because *this* file is scanned only for imports into
# `LEGACY_ZONES`, and `modules.market_data.ui.module` is not one. This file is
# genuinely empty only when Phase 5 replaces `AbstractScreenModule`/
# `ScreenRegistry` with the Engine's `NavigationService` -- which was always
# this file's *other* row's own prediction, just not this one's.
