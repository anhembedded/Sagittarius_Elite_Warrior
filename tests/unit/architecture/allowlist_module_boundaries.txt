# One line per (importing_module, imported_module) pair, no line numbers, so an
# unrelated edit never churns this file. The guard fails on any pair NOT listed
# here (a new violation) and on any pair listed here that no longer exists (the
# fix landed - delete the line in the same commit). This list only shrinks.
#
# Every entry names the phase that deletes it. An entry with no exit is not an
# entry, it is a permission - and this file grants none.
#
# History of the count: 10 as found (2026-09-13) -> 8 after PR 0.3 -> 41 after
# PR 0.4a -> 38 after PR 0.4a-2 -> 34 after PR 0.5.
#
# 0.5 is the first time an entry retired because a **consumer moved onto a
# published port** rather than because code moved into the module: four screens
# asked market_data for a sync by building its command, and now ask
# `IMarketDataSync` instead.
#
# The jump at 0.4a is not a regression: it moved
# ~60 files into modules/market_data/, and every legacy screen that dispatches
# one of its commands directly became a visible, counted violation instead of an
# indistinguishable same-tree import. Phase 1 replaces each dispatch with a port
# call, and this file returns to single digits. 0.4a-2 is the first such
# repayment: inverting who parses a CLI line let the two market_data commands
# move into the module, trading 5 dispatch entries for 2 handler-class ones.

# ---------------------------------------------------------------------------
# presentation -> modules.market_data.application: the transitional dispatch
# surface (27 entries).
#
# What these are: a legacy screen or CLI command builds a market_data Command or
# Query object and hands it to the Engine's ICommandDispatcher. The import is
# only for the *type*, never for a handler - so the coupling is a data shape,
# which is why it was tolerable to leave standing for one phase rather than
# rewrite 20 screens in the same pull request that moved 60 files.
#
# Why they are not simply published in contracts/: publishing them would make
# this coupling permanent and correct-looking. It is neither. Phase 1 replaces
# each dispatch with a call on a narrow port (IHistoricalKlines, IMarketDataSync,
# IMarketStream, ISymbolCatalog, IRangeCoverage), and each replacement deletes
# its line here. Nothing new may be added to this block: a new caller uses a
# port, or there is a new port.
#
# Where they go, by phase:
#   Phase 1  - the data_management.* lines (8), with the same port replacement as
#              every other dispatch. They were written down as "PR 0.4b, when
#              that screen is rebuilt", on the assumption that 0.4b moves the
#              screen into `modules/market_data/ui/` and turns these into
#              intra-module imports. It cannot: measured, the move needs 35 NEW
#              entries pointing the wrong way — `modules/market_data/ui/` ->
#              `presentation.ui.{kit,assets,common,components,state,qml}` —
#              because a module's `ui/` may import `support/ui_kit` and
#              `support/charting`, and neither exists before Phase 4. Trading 8
#              forward entries for 35 backward ones inverts the number this
#              epic actually watches. EPIC-025A §1.8 records the measurement.
#   PR 0.5   - DONE: the four `sync_market_data.command` lines, via
#              `IMarketDataSync` — the module publishes the capability, the
#              screens depend on the contract
#   Phase 1  - the remaining `get_historical_klines` and `start/stop_live_stream`
#              lines. They need `IHistoricalKlines` and `IMarketStream`, the two
#              ports `EPIC-025A` §1 assigns to Phase 1 with `modules/trading`;
#              0.5 deliberately published one port rather than three, so the
#              mechanism is proved by a consumer that runs, not by three
#              contracts written at once
#   PR 0.4a-2 - DONE: the sync/stream CLI lines left when those commands moved
#              into `modules/market_data/cli/`
